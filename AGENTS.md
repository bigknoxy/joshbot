# AGENTS.md - Coding Agent Guidelines for joshbot

## Project Overview

joshbot is a lightweight personal AI assistant (~38,300 LOC Go non-test, 2,113 test functions across 234 test files — measured 2026-08-13) with self-learning memory, auto-skill-creation from tool usage patterns, and Telegram and Discord integration. Architecture: goroutine-based message bus decoupling chat channels from a ReAct agent loop backed by multi-provider LLM via OpenRouter-compatible APIs.

Module: `github.com/bigknoxy/joshbot`. Go 1.25.9.

## HARD RULE: all work goes through PRs and gh issues

**Never push work directly to `main`.** Every change that alters code, docs,
config, or observable behaviour ships as a pull request opened against `main`,
and every feature/bug/refactor is tracked in a `gh issue`. This is a hard rule,
not a guideline:

1. Open (or reference) a `gh issue` for the work before starting.
2. Do the work on a **feature branch** (`feat/...`, `fix/...`, `docs/...`).
3. Open a **PR** from that branch to `main` when ready; do not merge it to
   `main` directly.
4. The PR must pass CI and be reviewed (use the panel-review workflow for
   anything touching tool execution, config, or public surface).
5. Only merge/close after the issue and PR are in step.

The #194 delegate_subagent change was pushed directly to `main` in error; do not
repeat that. If work ends up on `main` directly, revert it to a branch and open a
PR rather than leaving it merged.

### Behavioural eval harness (`internal/agent`)

`evalharness_test.go` runs the **real ReAct loop** against a scripted provider that
replays a fixed sequence of model turns and records every request. No network, no
API key, no clock dependence — it runs in normal CI.

```bash
go test ./internal/agent -run 'TestEval_' -v
```

Add a scenario by declaring a `trajectoryScenario` (scripted turns, tool outputs,
seeded history, budget/window knobs) and passing it to `runTrajectoryEval`. Assert
on the **trajectory** — `res.requests` (what was sent to the model), `res.invocations`
(what was dispatched), `res.sess` (what was persisted) — not on the reply text.

Always call `assertProtocolInvariants(t, res)`. It enforces the wire-format rules an
OpenAI-compatible provider rejects with a 400: every tool message carries a
`tool_call_id`, every id answers a call announced by an earlier assistant message, and
every announced call receives a result. Two shipped bugs were found this way, both of
which broke only long conversations. Keep this call in every new scenario so evals
added later inherit the checks.

Do not confuse this with `prompt_eval_test.go`, `prompt_optimizer_test.go` and
`prompt_variants_test.go` — those are a **prompt lint**. They score the system prompt
string with `strings.Contains` and never invoke the agent, a model, or a tool. They
cannot catch behavioural regressions.

### Imports

- **Group imports** by stdlib, third-party, then local (separated by blank lines)
- **Use import aliases** for clarity when needed (e.g., `ctxpkg "github.com/bigknoxy/joshbot/internal/context"`)
- **Avoid blank imports** except for drivers/side effects

### Error Handling

- **Return errors as values** - don't panic in library code
- **Wrap errors with context** using `fmt.Errorf("operation failed: %w", err)`
- **Tools return error strings** (`return fmt.Sprintf("Error: File not found: %s", path)`) - don't return errors that require handling
- **Graceful degradation** with fallbacks
- **Check errors explicitly** - don't ignore return values

### Naming Conventions

| Element          | Convention         | Example                          |
|------------------|--------------------|----------------------------------|
| Packages         | lowercase, single  | `tools`, `bus`, `config`         |
| Types            | PascalCase         | `Agent`, `WebFetchTool`          |
| Functions/methods| PascalCase (exported), camelCase (unexported) | `BuildSystemPrompt`, `parseResponse` |
| Private fields   | camelCase          | `cfg`, `running`                 |
| Constants        | PascalCase or UPPER_SNAKE_CASE | `MaxOutput`, `MAX_QUEUE_SIZE` |
| Interfaces       | PascalCase + "er" suffix | `Provider`, `ToolExecutor` |

### Data Modeling

- **Structs** for data types (InboundMessage, LLMResponse, Session, etc.)
- **Embed interfaces** for composition
- **Use struct tags** for JSON/field mapping (`json:"field_name"`)
- **Functional options pattern** for complex configuration

### Interfaces & Extension Points

- **Small, focused interfaces** (prefer 1-3 methods)
- **Interface segregation** - define interfaces where they're used
- **Registry pattern** for tools (`Registry`) and providers
- **Functional options** for flexible construction (`Option func(*Type)`)

### Concurrency Patterns

- **Goroutines** for concurrent operations
- **Channels** for message bus (`chan InboundMessage`, `chan OutboundMessage`)
- **sync.Mutex/sync.RWMutex** for shared state
- **sync.WaitGroup** for goroutine coordination
- **context.Context** for cancellation and timeouts
- **select** for multiplexing channel operations

### Logging

- **charmbracelet/log** for structured logging (`log.Info`, `log.Debug`, `log.Warn`, `log.Error`)
- `log.Debug()` for routine operations, LLM request/response details, tool execution results
- `log.Info()` for significant events (tool execution, service start/stop)
- `log.Warn()` for recoverable issues, empty content detection
- `log.Error()` for failures

**Debug Mode:** Use `--debug` flag to enable DebugLevel logging:
```bash
joshbot agent --debug
joshbot gateway --debug
```

Debug logging provides visibility into:
- LLM response details: content_length, content_preview, tool_calls_count, finish_reason
- HTTP response status codes and model information
- Tool execution results with result_length and preview
- Empty content warnings with model and iteration info for troubleshooting

### String Formatting

- **fmt.Sprintf** for formatted strings
- **String concatenation** with `+` for simple cases
- **strings.Builder** for building complex strings efficiently

### Documentation

- **Package comments** at top of file (starts with "Package X ...")
- **Exported types/functions** must have doc comments
- **Example functions** for usage documentation (`ExampleTool_Execute`)

## Architecture Quick Reference

```
channels/ --> bus/MessageBus --> agent/Agent --> providers/LiteLLMProvider
(CLI,         (chan-based)      (ReAct loop)    (HTTP -> LLM API)
 Telegram,                          |
 Discord)
                               tools/Registry (filesystem, shell,
                                                 web, message)
                                      |
                               skills/SkillDetector
                                   → Extractor → Loader.Create
                                   (auto-skill-creation pipeline)
```

- **Message bus** decouples channels from agent via `InboundMessage`/`OutboundMessage` channels
- **ReAct loop**: LLM -> tool calls -> reflect -> repeat (max 20 iterations)
- **Memory**: `MEMORY.md` (always in context) + `HISTORY.md` (grep-searchable event log)
- **Skills**: Markdown files with YAML frontmatter, progressive loading (summary -> full content)
- **Sessions**: JSONL files in `~/.joshbot/sessions/`
- **Config**: `~/.joshbot/config.json`, JSON-validated, env vars with `JOSHBOT_` prefix
- **Prompt caching**: Static system prompt cached with mtime-based invalidation (`internal/agent/context.go`)
- **Model-centric config**: Provider auto-detected from model prefix, fallback chains supported (`internal/config/config.go`)

## Panel Review (agent-assisted code review)

A repo-scoped review workflow that runs five expert perspectives over a change,
has them debate, and produces a scored verdict. Useful before merging anything
that touches tool execution, config, or public surface.

**Files** (none of this is joshbot runtime code — it configures coding agents):

| Path | Role |
|---|---|
| `.claude/skills/panel-review/SKILL.md` | The workflow: frame → analyse → debate → score → report |
| `.claude/skills/panel-review/references/experts.md` | **Canonical charters for all five experts** |
| `.claude/skills/panel-review/references/scoring.md` | Rubric, default weights, report template |
| `.claude/agents/panel-*.md` | Claude Code agent-type wrappers that point at `experts.md` |

**The five experts**: `panel-agent-security` (prompt injection, tool abuse, trust
boundaries), `panel-llm-evals` (is the behaviour verifiable, would a silent
regression be caught), `panel-agent-experience` (onboarding, config, over-blocking,
failure legibility), `panel-oss-growth` (adoption, positioning, doc drift),
`panel-go-systems` (goroutine lifecycle, loop termination, build tags, coverage).

**Running it from any harness.** `references/experts.md` is the single source of
truth and deliberately does not depend on Claude Code's agent registry, so the
panel is portable:

1. Read `SKILL.md` for the workflow and `references/experts.md` for the charters.
2. Write the framing block (subject, artifacts, decision, constraints) once and
   give the identical block to every expert.
3. Spawn five subagents **concurrently**, each given only the framing block plus
   its own `## panel-<name>` section from `experts.md`. Keeping them isolated in
   this round is the point — experts who see each other's drafts converge early
   and the debate round stops being useful. If your harness has no subagents, work
   the five charters sequentially yourself, writing each verdict down before
   reading the next charter.
4. Give every expert the other four reports and require each to challenge at least
   one finding and to concede or hold on challenges against it.
5. Score with `references/scoring.md` (weighted composite, 0–10 per expert, high is
   good, `N/A` allowed) and report using its template. Any blocking concern
   overrides the composite.

**Claude Code shortcut**: invoke the `panel-review` skill, or spawn
`subagent_type: panel-agent-security` and so on. The agent registry is read at
session start, so newly added `.claude/agents/*.md` need a new session before they
resolve — fall back to a general-purpose agent pointed at `experts.md`.

**Scaling**: one or two experts for a focused single-lane question, all five for a
normal change, five plus a second debate round for direction-setting decisions.
Say which experts you skipped and why.

Charters carry joshbot-specific grounding (known weak points, file paths, the
OpenClaw CVE threat model). Verify those claims against the code before citing
them — the repo moves faster than the charter, and a finding built on a stale
charter is a false finding.

## Gotchas

- **Telegram formatting is authored as Markdown and sent as HTML, and the plain-text fallback must send the *pre-conversion* source (#315).** `MarkdownToHTML` (`internal/channels/telegram_html.go`) runs at the wire in all three outbound paths -- `telegram.go`'s per-part text send, `telegram_attachment.go`'s caption, and `telegram_stream.go`'s `writeLocked` final edit -- flipping `ParseMode` from `Markdown` to `HTML`. Legacy Markdown rejects ordinary LLM prose with `400 can't parse entities` and the recovery then strips formatting off the whole answer; HTML escapes three characters where MarkdownV2 escapes eighteen. Four rules. **The fallback sends the Markdown source, not the HTML** (`plain`, `plainCaption`, `s.buf`): an HTML body delivered with no parse mode renders its entity references literally, so the reader sees `&amp;` where the model wrote `&`; `TestSendAttachments_CaptionFallbackSendsThePreConversionSource` pins it. **Splitting happens on the Markdown**, with the existing fence-aware `splitMessage`/`splitOnce`, so no tag can straddle a part boundary. **`TelegramStreamer.buf`/`shown` stay the Markdown source** -- only the bytes on the wire change -- so `Finish`'s `delivered && !broken && shown == buf` suppression contract is untouched. And **the 4096 limit is measured after entities parsing**, not in bytes: conversion adds bytes (`<pre>` vs ```` ``` ````, `&amp;` vs `&`) while only ever shrinking rendered length, so a raw payload over 4096 is still legal -- a test asserting `len(text)` there is asserting the wrong thing, which is why the rollover test measures `renderedLen`. The converter treats an unterminated marker as literal text (no shorter marker may claim it), never parses inside code spans or fences, and allowlists link schemes to `http`/`https`/`tg`.
- **`channels.telegram.api_url` raises an outbound cap only, and the cap is a memory bound (#280).** The key points the channel at a self-hosted `telegram-bot-api` server; empty means `api.telegram.org`. Four things. It is validated as an `http`/`https` URL with a host and a failure returns `fatalConfigError` — an ordinary validation error makes `config.Load` log "Config unusable, using defaults" and substitute `Defaults()`, discarding every provider, key and allowlist, which is the same trap `validateTimeout` sits in. There is **one** limits rule, `channels.TelegramAttachmentLimitsFor`, read by `TelegramChannel.AttachmentLimits` and — through `outboundAttachmentLimits` in `cmd/joshbot` and `tools.WithAttachmentLimits` — by `SendFileTool`; a second copy drifts and the symptom is `send_file` refusing a send the transport would have accepted. The raise is gated on `channels.telegram.enabled`, because an `api_url` in a config with Telegram off would otherwise raise the tool's cap toward a transport that never runs. And `LocalAPIDocumentMaxBytes` is 50 MiB, not the local server's 2 GB, because the payload is held in memory from the tool call until the upload finishes — raising it raises peak heap per turn, and #305 tracks the fd-carrying rework that would make a bigger number safe. Inbound limits (`providers.MaxImageBytes`, `providers.MaxDocumentBytes`) are deliberately untouched: they bound what a model is billed to read.
- **`channels.telegram.reactions` acknowledges on the *user's own* message, and three details decide whether the ack ever appears (#314).** `setMessageReaction` (Bot API 7.0) **sets** rather than appends, so 👍 replaces 👀 with no clearing call — do not add one. The completion emoji is 👍 and **not** ✅: ✅ is premium-only in Telegram's free reaction set and is rejected with `REACTION_INVALID`, so the ack silently never appears; `TestReactionEmojiAreInTheFreeSet` pins both emoji against the documented list. The gate is **opt-in with `omitempty`** for the `api.webui` reason — a `Config` bool without it is written into every saved config and its default can then never be flipped without a schema migration (the `streaming` v4→v5 trap) — and it is opt-in at all because a bot in a group lacking the reaction permission would log a failure on every single turn. `telebot.Bot.React` reads only the id half of `MessageSig()` (the chat comes from the recipient), so the target is a dedicated `ackTarget int` Editable: a bare `&telebot.Message{ID: n}` nil-dereferences its `Chat` inside `MessageSig`. The reaction fires from a goroutine off the reply path and its failure is logged at debug — a reaction is an ornament on the turn, never part of it — and it is **outbound only**, so no `allowed_updates`/`message_reaction` subscription is involved.
- **`channels.telegram.stream_drafts` streams through `sendMessageDraft`, and a draft is not a delivery (#308, #309).** With it on, `TelegramStreamer` pushes each delta into an ephemeral draft slot (`internal/channels/telegram_draft.go`) instead of the send/edit loop, and `Thinking()` shows an empty-text draft as Telegram's own "Thinking…" placeholder before the first token. Five things. **A draft write must never set `delivered`** — the reference calls a draft "a temporary 30-second preview" and requires an ordinary `sendMessage` to persist the text, so `Finish`'s `delivered && !broken && shown == buf` suppression rule stays about what actually reached the chat, and the persisting send still runs every turn; setting it there loses the whole reply on a turn that only drafted. **The first API refusal disables drafts for that turn and falls through to the edit loop on the same delta**, without setting `broken`: telebot v3.3.8 has no wrapper for the method so the call goes through `Bot.Raw` (which turns `{"ok":false}` into an error), and a Bot API server older than **10.0** — the version that allowed empty text, changelog dated 8 May 2026, *not* the 9.3/9.5 issue #308 claims — must cost the animation and not the answer. **It is private-chat only**: `privateChatID` requires a positive numeric id, because the reference documents `chat_id` as the target private chat and a group would spend a request per delta to earn an error per delta. **`draft_id` must be non-zero and is one per turn** (a package-level `atomic.Int64` whose `Add` starts at 1), since clients animate changes to drafts sharing an id — one id per turn is what makes the growing answer a single animated slot. And **`draftTail` cuts on a rune boundary**, not at byte 4096: a slice through a multi-byte rune is invalid UTF-8 and Telegram rejects the whole request. Note a test for that is only meaningful with **3-byte** runes — with 2-byte runes the cut parity can never land mid-rune, so the mutation stays green.
- **The HTTP API serves the agent, not a provider, and has no unauthenticated mode**: `internal/api` runs every `POST /v1/chat/completions` through `agent.Process`, so `GET /v1/models` advertises exactly one id (`api.ModelID` = `joshbot`) and the request's `model` field is accepted and ignored — a client hardcoded to `gpt-4` must keep working. Four rules hold it together. **`api.New` fails closed**: it drops blank entries from `api.api_keys` and returns `ErrNoAPIKey` when nothing usable is left, before anything is listening, because a caller reaching this endpoint reaches the shell and filesystem tools; keys are compared with `subtle.ConstantTimeCompare` and every configured key is checked even after a match. **A client `system` message is dropped, never forwarded** — joshbot's own system prompt carries the tool and safety rules and a caller prepending to it is a way to argue the agent out of them; only the last `user` turn is used. **The `user` field becomes a session key (`api:<user>`), so it goes through `session.ValidateSessionID`, a separate `:` check, a 64-character cap and a letters/digits/`.`/`_`/`-` charset** before it can build a path — `ValidateSessionID` stops traversal but says nothing about length or shape, and this value ends up as a filename and as a name an operator reads in `joshbot sessions`. Two requests carrying the same `user` are **serialised, not parallel** (#236) — see the session-lock gotcha below. One limit used to be "documented rather than fixed": a client that disconnects mid-turn cancels the context and aborts the in-flight LLM work. The in-flight work is still aborted, but **the turn's session write no longer dies with it** — `Process` routes every post-loop persistence step through `persistenceCtx`, which swaps a spent turn context for a fresh 10s-bounded one (`internal/agent/agent.go`), so the accumulated messages, checkpoint and topic are saved rather than dropped. That same mechanism is what keeps a timeout or max-iteration turn from losing its whole session (#283). **The error path persists on *any* spent turn budget**, not just a deadline: a client-disconnect cancellation (`context.Canceled`) used to fall to the generic error branch and return before the save, dropping the turn — it is now covered by the same `ctx.Err() != nil` gate (pinned by `TestCancelledTurnPersistsSession`). Two honesty notes. The 10s bound is enforced at `Manager.Save`'s entry (`internal/session/manager.go`); the marshal and `writeFileAtomic` inside are not context-aware, so a hung filesystem can exceed the bound while holding the per-session lock — the bound holds for a healthy FS, and save failures are warned, never silent. And the generic provider-error path (a live budget that returns a 401/network error) still does **not** save, which is unchanged pre-existing behavior — only spent-budget turns are rescued, because a failed LLM call with an intact context is a normal error, not a dropped conversation. And **`agent.Process` reports LLM failures in band**, so the handler translates them with `agent.ReplyError`: pre-stream that is a 502, mid-stream it is an error in the stream with no `finish_reason: "stop"`, never a 200 carrying `"Error processing request: ..."` as the answer. Streaming replays only the remainder of the reply when the deltas are a prefix of it, and usage rides the final SSE frame only. **Error bodies split on origin (#238)**: `writeError` sends joshbot's own package constants verbatim and `writeUpstreamError` redacts anything whose text came from outside. Running everything through `safeErrorMessage` made the 401 read `Send it as 'Authorization: Bearer [REDACTED]'.` — `redact.String`'s `Authorization:` header rule ate the `<key>` placeholder that tells a caller what to present. The redaction is not optional on the other side: a provider error carries the operator's upstream key, and an API caller is authenticated but is not the operator. The mid-stream error frame is built by hand rather than by `writeError`, so it needs `safeErrorMessage` applied explicitly — it was missing there, which is a leak a non-streaming caller was protected from.
- **`POST /v1/audio/transcriptions` is the one API route that is not the agent, and three rules keep it safe.** It transcribes with the `stt` provider directly -- no ReAct loop, no session -- and answers **501 naming `stt.provider`** when none is configured, because a 404 reads as "joshbot cannot do this" and a 200 with an empty transcript is indistinguishable from silence; a broken `stt` block is fatal at `serve` startup, not at the first request. The body goes through `r.MultipartReader`, never `ParseMultipartForm`: the latter spills past its memory budget to temp files, so an authenticated caller gets a disk-fill primitive and the audio touches disk unredacted. The size cap is enforced twice -- `http.MaxBytesReader` on the whole request (cap plus `multipartOverheadBytes` of slack, so a file exactly at the cap is still uploadable) and a `LimitReader` at `providers.MaxAudioBytes+1` on the part, the +1 being what makes over-limit distinguishable from truncated. And **content decides the type**: `providers.SniffAudio` reads the bytes, because the multipart filename and its declared Content-Type are both caller-written, so a 25 MiB text file named `voice.mp3` would otherwise be uploaded to the operator's provider and billed. `model`/`language`/`prompt`/`temperature` are accepted and ignored; provider errors go through `writeUpstreamError` (redacted), joshbot's own through `writeError` (verbatim). Note the route calls `providers.TranscribeAudio`, **not** the `Provider.Transcribe` interface stub, which is unimplemented and carries the openrouter-default anti-pattern.
- **`POST /v1/embeddings` orders vectors by the response's `index`, never by array position, and its caps run before the provider is dialled.** The OpenAI schema carries an `index` on every embedding object precisely because the array may come back reordered, and a vector attached to the wrong input is the one failure mode nothing detects: the caller stores it, retrieves the wrong text, and no error is ever raised -- so `providers.Embed` (`internal/providers/embed.go`) places by index and treats a duplicate, out-of-range, missing or empty vector as an error rather than a best effort. Three more things. The route is **not exempt from `MaxRequestBytes`**, and `maxEmbeddingInputs` (128) and `maxEmbeddingInputBytes` (64 KiB) are checked in `parseEmbeddingInput` *before* `s.embedder` is called, because a limit reported after the upstream call has already been billed has not limited anything. **`buildEmbedder` deliberately does not require an API key** -- the one place it diverges from `buildTranscriber` -- because ollama is keyless and is the main local case; everything else (provider configured, enabled, resolvable `api_base`, resolvable model) is still fatal at `serve` startup naming the key, never a per-request 501 the operator reads as a missing feature. And `embeddings.timeout` is a `config.Duration`, not a `time.Duration`: a new timeout key written as the latter is the #240 nanosecond bug, restored.
- **The web UI is a second authentication path bolted beside the bearer one, and the bearer path must stay first and ungated.** `requireAuth` (`internal/api/server.go`) checks `Authorization: Bearer` first and returns immediately on a match -- no origin check, no CSRF header, no cookie -- because every existing OpenAI client depends on that being the whole story; the cookie rules live entirely in `cookieAuthOK` and run only when no valid bearer was presented. Five things hold it together. **`api.webui` is the single gate and it must be a real one**: `New` allocates `webuiSessions` *unconditionally*, so a cookie is refused because `s.webui` is false and not because a map happened to be nil -- gating by accident is not a guard, and the mutation test for it stays green when the map is the gate. With it false, `registerWebUI` is never called and every route (`/`, `/webui/static/`, `/webui/login`, `/webui/logout`, `/webui/config`, `/webui/session`) 404s as if absent, which is deliberate: the page is a login form accepting an `api_keys` value that reaches the shell tool, and it must not appear on every existing bind at upgrade. **`api.webui` carries `json:"webui,omitempty"` and defaults false**, which is the only reason it needs no schema migration -- a `Config` bool without `omitempty` is written into every saved config and its default can then never be flipped (the `streaming` v4->v5 trap). **The login route reuses `keyMatches` and `s.rejections.note()`**, not a second comparison and a second limiter: a bespoke check is how one path ends up non-constant-time or unthrottled while the other is audited. **CSRF is checked only on the cookie path and only on non-GET/HEAD**, constant-time against a per-session token that `GET /webui/config` serves *only* to cookie sessions -- serving it to anyone makes double-submit meaningless. And **`/` is not a catch-all**: Go's `ServeMux` matches `/` as a prefix, so the handler 404s any path that is not exactly `/`, or every unknown URL would return the app shell with a 200 and the missing-route signal would be gone. The transcript route is read-only by design (`transcriptReader` in `cmd/joshbot/serve.go` filters to user and assistant turns, dropping tool, system, compaction and empty-content messages); "New conversation" rotates the browser's session key and deletes nothing, because a destructive button should not be reachable through a cookie.
- **Telegram message limit**: Telegram Bot API enforces 4096 char max per message (not retryable on failure). `Send` splits longer content via `splitMessage` in `internal/channels/telegram.go`, closing and reopening markdown code fences across the boundary. Parts may exceed `maxLen` by up to 4 bytes because of the reopened fence. `splitMessage` indexes by byte, not rune.
- **Telegram chat actions expire after 5 seconds**: one `sendChatAction` is not enough for an agent turn that runs 30-90s. `startTyping`/`stopTyping` in `internal/channels/telegram.go` keep one keep-alive goroutine per chat (keyed by `Recipient()` under `mu`), re-sending every `typingInterval` (4s). `Send` stops the keep-alive once a recipient is resolved, and every goroutine also selects on `stopCh`, so shutdown reaps them. Do not go back to a one-shot send.
- **The slash-command table is `internal/commands.All`, and every channel forwards every command to the agent.** `botCommands` in `internal/channels/telegram.go` is rendered from it and is both what `SetCommands` publishes and what the unknown-command fallback treats as known; Discord's list, the CLI's Tab completion and the agent's `/help`/`/start` render from the same table. **No channel answers a command locally any more** — a local help text drifted from the agent's three ways, and a local "Starting new session…" ack made `/new` answer twice; adding a command is one table entry plus a `case` in `handleCommand`. telebot routes a registered command to its own handler and only falls through to `OnText` when nothing claimed it, so `handleMessage` sees unknown commands only. Adding a `bot.Handle("/x", ...)` without adding it to `botCommands` still leaves `/x` invisible in the UI and absent from the fallback's "available commands" list. Keep the two in step. Every command is registered through the `forwardedCommands` slice (also rendered from the table): `setupHandlers` registers a shared `handleCommandForward` for each, which re-checks the allowlist (telebot dispatches known commands outside `handleMessage`, so the gate must be applied there too) and forwards the raw `msg.Text` to the bus with `is_command: true` metadata. `TestTelegramChannel_CommandMenuAndHandlersInStep` enforces the menu⇄handler parity. **The menu is scoped to the allowlist and clearing it is a different API call.** `registerCommands` publishes a `BotCommandScopeChat` menu per numeric `allow_from` entry and deletes the global all-private-chats menu, so a stranger sees no menu; a username-shaped entry cannot be resolved to a chat id until that user speaks, so any username in the allowlist keeps the global menu. Three traps. **`SetCommands` cannot clear a scope**: telebot's `CommandParams.Commands` carries `json:"commands,omitempty"`, so an empty slice omits the field and the Bot API rejects the call — clearing is `DeleteCommands` or nothing, which is why the `telegramNotifier` interface carries both. **A per-chat scope for an allowlisted user who never started the bot returns "chat not found"**, so the loop logs and continues (returning the first error) — one such user must not cost every other user their menu. And an **empty allowlist denies every sender** (`IsAllowed`), so it takes the delete branch rather than publishing a menu to nobody. This completes command *names* only; Telegram cannot complete paths or arguments.
- **Telegram token validation retries transport failures and must never leak the token**: `ValidateToken` in `internal/channels/telegram.go` is the network boundary onboard uses. Three rules keep it safe. A malformed token is rejected **offline** by `validateTokenFormat` (a `^\d+:[A-Za-z0-9_-]{30,}$` shape check) before any request — a garbage-token unit test must not need network. Transport failures (dial, TLS handshake timeout, timeout, connection reset while reading the body) are retried up to 3 times and wrapped with the exported sentinel `ErrTelegramNetwork`; a definite API rejection (400/401/404) is never retried. And the transport error must stay unwrapped to its cause: `http.Client.Do` returns a `*url.Error` whose string form is `Get "https://api.telegram.org/bot<token>/getMe": ...`, which prints the credential into setup output — the reported failure was exactly this, a valid token plus one TLS hiccup printing the full token to the terminal and aborting setup. The `io.ReadAll` of the body is *also* a network boundary — a reset or timeout that lands after the headers arrived must be wrapped in `ErrTelegramNetwork` too, or a mid-body drop is reported as a rejected token and never retried. On the wizard side (`setupTelegram` in `cmd/joshbot/main.go`), validation runs through the stub-able `validateTelegramToken` package var, re-prompts once on failure, and on persistent failure **keeps an existing working token** rather than returning nil — returning nil made `runOnboard` save the config with Telegram disabled and silently disconnected a live bot. The same return-nil hazard exists when the user aborts a token *change* with `cancel`/empty input: with an existing token present that must also return the existing configuration, not nil. `onboard --force` is genuinely non-interactive now: it reuses the existing API key without reading stdin, so do not reintroduce a prompt in the force path.

The same keep-existing hazard covers the **API key prompt**, not just the token: `promptProviderAPIKey` in `cmd/joshbot/main.go` shows "Enter new API key (or press Enter to keep current)" when a key exists, and pressing Enter must return that existing key. An earlier version returned `""` on Enter, and `runOnboard`'s `if apiKey != ""` gate then skipped the whole provider-config block, so a keep-current reconfigure of a working NVIDIA install saved a config with only the disabled `openrouter` default and `joshbot agent` died with "no providers enabled: 1 provider(s) found in config (openrouter)". Empty input with an existing key is "keep it", not "drop the provider" — same contract as the Telegram token. (`TestRunOnboard_Interactive_KeepCurrentAPIKey` pins it.)
- **CLI stdin blocking**: `bufio.NewReader(os.Stdin).ReadString('\n')` blocks on stdin and can't be interrupted by context cancellation
- **Session key format**: `"channel:senderID"` (e.g., `"cli:cli-user"`, `"telegram:johndoe"`). Computed from `Channel:SenderID` — no explicit SessionKey field
- **A turn is serialised per session key, and `handleResumeCommand` must call the unexported `a.process`**: a turn is a read-modify-write over one session file — `GetOrCreate` loads it, the ReAct loop appends, `Save` rewrites the whole thing. `Manager.mu` guards each Load or Save individually but is released between them, so two overlapping turns for one key both loaded the same prefix and the later save published a file missing the other turn's messages entirely (#236); it is reachable by default through the HTTP API, where two requests carrying the same `user` land on one session. `Agent.Process` now acquires `session.Manager.LockSession` for the whole span. Four things hold it together. `SessionLocker` is an **optional interface checked by type assertion**, like `session.Archiver`, so test doubles and alternative `SessionManager` implementations are not forced to implement it. The lock is acquired **after** the timeout context is built, so a turn queued behind a long one waits against its own deadline and reports a timeout instead of hanging — which is also why `keyLock` is a capacity-1 channel and not a `sync.Mutex`, whose wait cannot be cancelled. `Process` is split into a locking wrapper and an unexported `process` body **because `handleResumeCommand` re-enters the loop**; routing `/resume` back through `Process` deadlocks on a lock that goroutine already holds, and the symptom is a hang, not a failure. And the lock map is **reference counted and deleted when idle**, including on the cancelled-waiter path — session ids on the API surface come from the client's `user` field, an unbounded key space, so an entry outliving its last holder is a memory leak any authenticated caller can grow. The lock is process-local: two joshbot processes sharing one sessions directory can still interleave, which is the pre-existing state and is documented rather than fixed. One consequence lives outside the package: `bus.MaxConcurrentHandlers` is acquired on the **dispatcher** goroutine before the handler is spawned (`internal/bus/bus.go`), so a queued turn now holds its semaphore slot for `wait + turn` rather than just `turn`. That is the open loop #245 closed: because the slot is held across the key-lock wait, a flood on one session key -- every overlapping turn for that key parking on the one held token -- could once hold an unbounded number of dispatch slots and stall dispatch for every *other* user, bounded in practice only by `agents.defaults.timeout`. The per-key cap stops it. `acquire` (`internal/session/keylock.go`) gates the running per-key ref count under the same mutex that guards the token (`MaxConcurrentTurnsPerKey`, 8), so once the cap-th holds the token every later overflow turn for that key returns `ErrKeyLockBusy` at once -- no ref, no wait -- instead of parking. `Agent.Process` maps that to an in-band backpressure reply via `ReplyPrefix` ("too many turns in flight"), so a non-interactive caller still translates it out of the band the way it does every Process failure: `agent -m` exits 1 and the HTTP API answers 502, because a turn that did not run is a failure, not an answer; a `context.Canceled`/deadline on the gate is reported as a timeout, not a busy rejection. `TestLockSessionRejectsOverflowPerKey` pins the exact admission math (`busy == num - (MaxConcurrentTurnsPerKey - 1)`), which is red before the cap and green after.
- **`/new` is the one turn routed *ahead* of the per-key lock, and a `generation` fence is what makes that safe (#319).** A reset that queues behind the stuck turn the user is trying to escape is not a reset — and under `MaxConcurrentTurnsPerKey` it is not merely slow, it is refused outright with `ErrKeyLockBusy`. So `agent.Process` checks `isResetCommand` right after building the timeout context and calls `a.process` directly, bypassing `LockSession`. That bypass is only sound because `session.Session.Generation` fences it: `Manager.ResetConversation` clears the transcript and bumps the generation, and `Manager.Save` refuses any write whose generation is older than the sidecar on disk (`ErrSessionSuperseded`), so the concurrent turn that loaded its prefix before the reset cannot republish it. Five traps. **`Save`'s sidecar-presence condition must count `Generation > 0` as presence** — a reset clears every other metadata field, so the existing `else` branch would `os.Remove` the sidecar and erase the fence, and the very turn the reset was racing would then write its transcript back. **`readGenerationLocked` fails *open***: an unreadable or unparseable sidecar reads as generation 0, because this gate exists to drop a stale write and refusing every write over a momentarily unreadable sidecar loses live conversation to protect a reset that may never have happened. **Both `Save` call sites in `agent.process` must treat `ErrSessionSuperseded` as success** and log at debug — surfacing it turns the fence working into an error the user sees. **`SessionResetter` is optional, checked by type assertion**, exactly like `SessionLocker`, so a test double or an alternative `SessionManager` is not forced to implement it; a store that does not keeps the old clear-in-place-under-the-lock behaviour. And **the archive-based `Manager.Reset` in `internal/session/inventory.go` is a different method with the same exposure** — it deleted the sidecar outright, so it now calls `bumpGenerationLocked` instead; my clearing reset is named `ResetConversation` precisely because that name was taken. Note the filed issue's premise was wrong: the lock already covered `/new`, and Telegram's `handleNew` does no local clearing (it publishes to the bus with `is_command: true`), so the paths could not drift. `Generation` carries `omitempty` and is zero for a never-reset session, so no schema migration is needed.
- **`session.Manager.Load` reads the `.meta.json` sidecar even when the session has no messages**: it used to return early on an empty message list, before touching the sidecar, so a checkpoint, model override or personality set on a session with no transcript yet was silently dropped on the next load. Command turns are not appended to the transcript, so `/model` or `/personality` as the very first thing a user does hit exactly that case.
- **Per-session model and personality live in the `.meta.json` sidecar, and `/model --global` mutates the config in place**: `Session.ModelOverride` and `Session.Personality` are persisted via the meta sidecar (`internal/session/manager.go`), not the JSONL message stream — they ride alongside `ConversationTopic`/`ConversationContext`. Resolution order is session override, then the runtime global override (the `a.modelName` field, guarded by `a.modelMu sync.RWMutex` because it is read on every model resolution), then the config default. `handleModelCommand`/`handlePersonalityCommand` save the session; `/model <name> --global` sets `a.modelName` under the write lock and calls `config.Save(a.cfg)`. Do not read `a.modelName` or `a.cfg.Agents.Defaults.Model` without holding the read lock — a concurrent `/model --global` writes `a.cfg` under the write lock. `/new` clears both overrides but preserves `ConversationContext`. The meta sidecar is **removed, not rewritten**, when every meta field is empty — a stale sidecar would re-inject a cleared override or personality on the next Load (pinned by `TestMetaSidecarRemovedWhenCleared`).
- **`/model --global` writes the whole config while holding `modelMu`, and the cfg-reading helpers come in locked and unlocked variants**: `setGlobalModelAndPersist` must hold the write lock across `config.Save`'s marshal (a concurrent `/model` list on another session reads the same fields), and `modelList`/`resolveModelSpec`/`modelForSession` must use the `...Locked` variants when they already hold the read lock — `sync.RWMutex` is not reentrant, so calling the plain `getModelName()` from inside a locked `modelList` deadlocks. `TestRace_ModelListVsGlobal` (throwaway, removed) proved the write path raced the marshal before this fix; keep the lock across the whole `Save`.
- **Interactive TTY mode routes logs to stderr, never stdout.** The logger's default writer is `os.Stdout` (`internal/log/logger.go`); `runAgent` in `cmd/joshbot/main.go` redirects it to `os.Stderr` when `isTTY(os.Stdout)` is true, because the editor paints a full-screen view on stdout and any INFO/WARN landing there (Processing message, Message processed, tool execution, skills review) corrupts the prompt. JSON modes redirect in the same spot; only non-interactive `-m/--message` text keeps logs on stdout so tool output and logs share the operator's capture stream. Do not write to stdout from inside the interactive loop — use `log.Get()` (now on stderr) or a `cliProgress` callback. `go test ./cmd/joshbot` runAgentLoop tests use `bytes.Buffer` (non-TTY), so they never exercise this branch.
- **The interactive editor's `render()` cursor math is `rows - cursorRow`, not `rows-1`.** After printing each row plus a trailing `\r\n`, the terminal cursor sits `rows` lines below the view's top; the cursor-up sequence must be `\x1b[<rows-cursorRow>A`. An off-by-one leaves the cursor on the line below the view, the next `hide()` cannot clear the prompt line, and every keystroke reprints a stale `● model ❯` line (the TUI-clobber bug). `TestEditor_RenderCursorUpIsSingleRow` pins the gap.
- **A tool-progress line and the streamed answer are separated by a blank line.** `cliProgress.onStreamEvent` prepends `\n` when a `⏺ tool(...)`/`⎿ ok` line was shown this turn (`toolShown`), so the reply does not glue onto the trailing `⎿ ok`. `toolShown` is reset in `beginTurn` and cleared on the first delta. `TestCLIProgressStreamEventSeparatesFromToolLine` pins it.
- **The interactive CLI editor must never be offered unless stdin is a real `*os.File` terminal**: `runAgentLoop` in `cmd/joshbot/main.go` activates the editor only when `input.(*os.File)` succeeds, `isatty.IsTerminal(fd)` is true **and** `isTTY(output)` is true; otherwise it keeps the buffered `> ` prompt path. `main_test.go`'s runAgentLoop tests pass `bytes.Buffer`/`blockingReader` as input (never `*os.File`), so they exercise the buffered path and must keep passing untouched. The editor owns exactly **one** reader goroutine for its whole lifetime (`startReader`/`close` in `editor.go`) — a per-`ReadLine` goroutine would outlive its call, stay blocked in the next terminal read, and swallow the first bytes of the following line; `TestEditor_HistoryNavigation` would catch a regression here. `editor.close()` (via `defer`) stops the goroutine, which may still be blocked in `ReadKey` until a byte arrives or the descriptor closes — the same acceptance as the buffered reader goroutine in `runAgentLoop`.
- **The editor path must NOT also spawn the `bufio` reader goroutine**: both read the same fd 0, and a terminal delivers each byte to exactly one blocked reader, so the two would nondeterministically steal keystrokes from each other. The `lines` goroutine is therefore created only when `editor == nil` (inside the `else` path of the TTY check) — keep it that way. The editor's `ReadLine` selects on `ctx.Done()` for shutdown, so it needs no separate `done`/`lines` plumbing.

- **Session writes go through `writeFileAtomic`, and `Load` is deliberately lenient**: `internal/session/manager.go` writes the JSONL, its `.meta.json` sidecar and any quarantine file at `0600` (they hold full conversation content and tool output — treat them like the credential store). The temp file name must be unique per writer; `os.CreateTemp` provides that. The old `<path>.tmp` was a fixed name shared by every process using `~/.joshbot/sessions`, so a running `gateway` and a concurrent `agent -m` wrote into the same temp file and the surviving rename published a torn mix — the `sync.RWMutex` never crossed process boundaries. On the read side, an unparseable line is **skipped, not fatal**: the parseable messages load, the original bytes are copied to `<session-id>.jsonl.corrupt`, and one warning is logged. Do not restore the hard error. There is exactly one session per `channel:senderID` and no CLI to delete one, so a fatal parse means that Telegram user gets an error on every subsequent message with no recovery short of `rm`.
- **A compaction record is stored in the session and must stay singular**: once the history crosses `agents.defaults.compaction_threshold`, `checkAndCompactContext` summarizes it and `applyCompaction` replaces the summarized prefix with one `session.Message` carrying `Compaction: true`, always at index 0. Three rules keep it correct. The write-back happens **after** `reactLoop` returns, not inside it, because `Process` slices `sess.Messages[startSessionLen:]` for the history log and shrinking the session first would slice out of range. `buildMessages` holds the record out of the memory-window truncation — letting the window slide over it silently discards the whole earlier conversation. And the replaced messages are appended to `<session-id>.history.jsonl` via the optional `session.Archiver` interface before they leave the live session; if that append fails the compaction is abandoned, since recomputing a summary is cheaper than destroying history. Note `checkAndCompactContext` runs only **after tool execution** inside the ReAct loop, so a turn that answers without calling a tool never compacts at all — a test scripted without tool calls exercises nothing. Three more rules from #346, where every one of these was violated at once. **The live turn is never summarized**: `compactionPrefixLen` ends the prefix `compactionKeepTail` (6) messages *before* `compactionState.turnStart` — the index of this turn's user message, set in `Process` — backed up over any tool result so the kept tail never opens with one; the tail itself is taken from the request slice, not rebuilt from the session, so the turn's image and document bytes survive. The tail is **anchored to the turn start, not the end of the session**, because the turn grows with every tool iteration and an end-anchored boundary would move on every pass and defeat the "already compacted this exact prefix" check — and a prefix under a quarter of the threshold is skipped outright, since the excess is then in the tail and summarizing the prefix recovers nothing. **`context.Registry` must not default an unknown model to 4096**: every current hosted model is unknown to it, `ComputeBudget` then went negative against the 8192 `max_tokens` default and was clamped to 256 tokens, and compaction fired at ~700 chars of history; the default is now `DefaultContextWindow` (131072) and an over-reserved window falls back to a quarter of itself. And **`Compressor.CompressMessages` asks the provider to summarize the whole conversation whenever it has one** — it used to do so only above 50 messages, and its other provider path summarized a join already cut to the budget, so at a small budget the "summary" was one message.
- **Everything joshbot prints or logs is redacted; session files are not**: `internal/redact` wraps the log writer (`internal/log/logger.go`) and `joshbot status`, so a credential appearing in a tool result never reaches the log. Session JSONL is deliberately exempt — rewriting content on save would mangle legitimate text and add a second corruption path, so data at rest relies on the `0600` mode instead; `TestSessionContentIsStoredVerbatim` pins that boundary, and `internal/redact` documents it. Three traps if you extend the patterns. **The scheme is kept and the token is redacted, never the reverse**: an `Authorization` value is `<scheme> <credential>`, and an earlier version recognised only `Bearer|Basic`, so GitHub's own `Authorization: Token <secret>` fell through to the assignment rule, which blanked the word `Token` and published the credential after it. Both the header rule and the assignment rule now capture an optional leading scheme word and preserve it. **A name fragment must end the identifier**, apart from a plural `s` and separator-led segments (`SECRET_KEY_ID`): matching it as a bare substring rewrote `Author:`, `unauthorized:` and `secretariat:`, all routine tool output. That is also why `AUTH` is in `redact.SecretNameFragments` — which widens the shell-environment screen in `internal/tools`, sharing the list on purpose — but is excluded from the assignment rule by `assignmentFragments()`. **And the cheap gate in front of each regex must never be narrower than the regex itself** — gating on the underscored `api_key` spelling silently let `api-key: <secret>` through. All-numeric values are exempt on purpose — `Max tokens: 8192` in `joshbot status` matches TOKEN plus a plural `s`, and no detected key class is bare digits. The assignment gate is a hand-written walk (`hasAssignmentCandidate`) rather than a substring test, because Go's regexp costs ~650ms per megabyte on a case-insensitive alternation and `token`/`key`/`secret` appear constantly in ordinary prose without being assignments; the walk mirrors the regex's name part exactly, so widening one means widening the other.
- **`joshbot sessions` is not a resume feature, and `.jsonl` alone does not identify a session**: sessions are keyed `channel:senderID` and loaded on every inbound message, so there is one per user per channel and nothing to select; the subcommands exist to inspect and clear. Two traps live here. `internal/session` now owns sidecars that also end in `.jsonl` — `.history.jsonl` (compaction archive) and `.jsonl.archive-<ns>` (reset) — so anything enumerating the sessions directory must go through `isSessionFile`, never a bare `strings.HasSuffix(name, ".jsonl")`; the compaction archive was reported as a phantom session named `<id>.history` until that was centralised. And urfave/cli v2 **stops flag parsing at the first positional argument**, so a flag written after an id is silently dropped — `prune <id> --force` declined without deleting, and `show <id> --last 2` printed the whole transcript. `parseSessionArgs` in `cmd/joshbot/sessions_cmd.go` reads those trailing flags — all three of them, including `--older-than`, whose omission made `prune <id> --older-than 30d` report an unknown flag; any new subcommand taking both an argument and a flag needs the same treatment. A third trap: an `Info` for a session that would not scan must carry the file's real mtime, because `PruneOlderThan` compares `UpdatedAt` and a zero time reads as infinitely old — a transient read error was enough to make `--older-than` delete a session of any age. Session IDs are attacker-influenced (the sender half comes from Telegram), so `ValidateSessionID` gates every path-building entry point.

- **Service cross-platform**: `internal/service/` uses build tags (`factory_linux.go`, `factory_darwin.go`, `factory_other.go`) — each must export the same function signature. Also has `systemd.go`, `launchd.go`, `openrc.go`, `unsupported.go`
- **launchd needs a domain *target*, not a domain name**: `launchctl bootstrap gui/<uid> <plist>` and `bootout gui/<uid>/<label>`. `Start` shipped `bootstrap gui <plist>` for several releases and failed on every Mac, while `Stop` was correct — nothing compared them. The strings now come from `serviceID`/`domainTarget`/`serviceTarget` in `internal/service/launchd.go`; the plist `Label` must equal `serviceID()` or `bootout` and the `launchctl list` grep in `isRunning` both silently miss the job. Note only `launchd.go` + `factory_darwin.go` compile on darwin — `systemd.go`/`openrc.go` are `//go:build linux` and `unsupported.go` is `!linux && !darwin`, so darwin coverage numbers for this package cover the launchd path only, and anything touched here must be checked with `GOOS=linux go vet ./internal/service/` and `GOOS=windows go vet ./internal/service/`.
- **Cron schedules are durations, not cron expressions**: despite the package name, `internal/cron` understands only `delay:<duration>` (fire once) and `every:<duration>` (repeat). The `cron` tool accepts `30m`, `2h`, `1d`, `1h30m` and rejects `0 9 * * *` with an error naming the accepted format. There is no calendar scheduling, so "every weekday at 9am" cannot be expressed — say so rather than approximating it silently with `every:24h`. `AddJob` validates the schedule and refuses anything it cannot run, so a bad job fails at creation instead of being stored and never firing.
- **A one-shot cron job's countdown survives the process**: `AddJob` converts a `delay:` duration into an absolute `Job.DueAt` (`json:"due_at"`, always present; a zero value means none recorded) and persists it, so a restart waits out the *remaining* time, not a fresh full duration. A job that came due while joshbot was stopped fires after `overdueGrace` (50ms) rather than being dropped. Jobs written before `due_at` existed have none: `loadLocked` backfills them as due one duration from load — the old behaviour, chosen so an old `jobs.json` does not fire everything at once — and saves the backfill so the deadline does not slide on each reload. `every:` jobs leave `DueAt` zero and keep plain `time.Ticker` semantics with no drift correction. One-shot jobs retire themselves once they fire (`retireJob`) — without that they replay on every boot forever. Recurring jobs run until deleted.
- **The `cron` tool is registered only when a scheduler exists**: `tools.WithCronService(svc, defaultChannel)` gates it, so the agent is never offered a tool whose jobs nothing would deliver. This is the wiring step whose absence was issue #90 — the skill taught a `cron` command that no tool implemented.
- **`osKeyReader.peekByte` must leave the byte in `pending`**: it is a peek, and every caller (`readEscape`, `readCSI`) consumes it explicitly with `readByte`. The fresh-read path used to pop it while the buffered path did not, so `readCSI`'s "consume `[`" ate the sequence's final byte and every arrow key blocked until the next keystroke. A test for the CSI decoder hangs rather than failing when this regresses, so bound it with a timeout.
- **`go run` is detected by the go-build cache, never by `/tmp`**: `runningFromGoRun` in `cmd/joshbot/main.go` is the single source for this. Three call sites — `update`, `uninstall` and `detectRunningContext` — each carried their own `strings.Contains(exePath, "/tmp/")`, which is not a property of `go run` at all: it made a joshbot installed anywhere under `/tmp` permanently unable to update or uninstall itself, and reported the cause as `go run`. A guard like this fixed in one place is not fixed; grep for the other copies.
- **The bundled skills are embedded in the binary, not read from disk**: `internal/skills/bundled/` is pulled in with `//go:embed` (`internal/skills/bundled.go`). It used to be the repo-root `skills/` directory found via the *relative* path `filepath.Join("skills")`, which resolves against the process working directory — so the bundled set loaded only when joshbot was run from a checkout of its own source tree, and every real installation reported "No skills found" while `trust.go` claimed they "arrive with the binary". Consequences to keep in mind: a bundled skill's `Path` is now an embed path, not a filesystem path, so its content is cached at discovery and `Delete` refuses it; `Loader.bundledDir` is empty in production and exists only so tests can substitute a fixture directory; and adding a skill means adding a directory under `internal/skills/bundled/`, which requires a rebuild to take effect.
- **A skill naming a tool that does not exist fails only at runtime**: nothing at build time connects `internal/skills/bundled/*/SKILL.md` to the registry, which is how a cron skill survived for months with no cron tool. `TestBundledSkillsOnlyReferenceRegisteredTools` (`internal/tools/skill_tool_drift_test.go`) closes that loop by matching the phrase ``the `x` tool`` in bundled skills against every tool name in the package. Keep that phrasing when a skill introduces a tool, or the lint will not see it. "the `gh` CLI tool" deliberately does not match — `gh` is an external binary.
- **`StripProviderPrefix` must not touch poolside model IDs**: joshbot routes on a model prefix (`groq/…` → Groq) and strips it before sending, because for most providers the prefix is joshbot's own routing hint. Poolside is the exception — its published IDs *are* `poolside/laguna-s-2.1`, so stripping produces a name the API rejects with `404 {"error":"please check the model you provided"}`. `prefixesPartOfModelID` in `internal/config/config.go` holds that exception; add to it when onboarding any provider whose `/v1/models` listing includes the prefix in the `id`. Check the provider's real listing before assuming — this bug shipped for months and made poolside unusable, including its own registered default `poolside/laguna-m.1`. Both the streaming and non-streaming call sites go through this one function, so fixing it there covers both.
- **A model ID belongs to one provider, and the fallback chain must respect that.** `MultiProvider.resolveModel` (`internal/providers/multiprovider.go`) honours the requested model only for the provider the request was *addressed to*; every fallback is asked for its own `entry.Model`. Forwarding it verbatim was a live bug and it looked exactly like the `StripProviderPrefix` bug above: a 429 on nvidia for `z-ai/glm-5.2` fell through to poolside as `z-ai/glm-5.2`, which answers `404 {"error":"please check the model you provided"}` — and since 404 is not a fallback-worthy status, that 404 was returned as *the* failure, hiding the rate limit and blaming a provider the user never chose. Two rules keep it fixed: `screenForImages` resolves models the same way (it decides vision capability per candidate, so a stale model there silently drops the wrong providers), and a non-fallback error from a *fallback* provider no longer short-circuits the chain — only the addressed provider's does. The aggregate error names every provider and its error, because "the last provider's 404" is the least informative thing that happened.
- **Transient provider failures retry in place before the chain moves, and the retry default lives in the wiring, not the library**: `MultiProvider.tryWithRetry` (`internal/providers/multiprovider.go`) retries fallback-class errors (429/5xx/network) on the same provider with jittered exponential backoff, honouring an upstream `Retry-After` carried on `providers.FallbackError.RetryAfter` (parsed from the header in `LiteLLMProvider.parseError`). A `Retry-After` longer than `maxInTurnWait` (20s) is not waited for: the provider is cooled down for that span and the chain moves on now. The cooldown table (`internal/providers/health.go`) *deprioritizes* a failing provider — moved to the end of `getFallbackChain`, never dropped — so a wrong guess costs latency, not availability; any success resets it, and the in-chat `/status` shows it (type-asserted `HealthSnapshot`, optional like `session.Archiver`). Three traps. **A bare `MultiProvider` retries nothing**: `Register` leaves `MaxRetries` 0 and `registerProviders` in `cmd/joshbot` raises every provider to `providers.DefaultMaxRetries` (2) before applying `providers.<name>.max_retries` overrides — a test asserting call counts, or a library caller, is not retried unless it calls `SetMaxRetries`. **`max_retries` is a `*int`**, because an explicit 0 ("fail over immediately") must be distinguishable from absent (default 2); `Validate` bounds it 0–10. And the time source and sleep are injectable fields (`mp.now`, `mp.sleep`) — tests fake them (`installFastClock` in `health_test.go`) instead of sleeping.
- **The fallback notice rides the reply text, and on the streaming path the buffer and the reply must stay identical**: `providers.WithFallbackNotice` (`internal/providers/notice.go`) carries a per-request callback the way `agent.WithSink` does; `MultiProvider` fires it only when a provider other than the addressed one answers, with the addressed provider's error class as the reason (`"cooldown"` when it was never dialled). The agent prepends `formatFallbackNotice` to the reply rather than sending it out of band, so every channel carries it with no per-channel wiring; `agents.defaults.quiet_fallback` (bool, deliberately inverted so the zero value shows notices — a default-true bool would need a schema migration, the streaming v4→v5 trap) suppresses it. **The notice is captured once per turn, not once per LLM call** (`turnStream`, a stack value in `reactLoop` — never an `Agent` field, for the same reason the sink rides the context): a turn that calls a tool makes two or more LLM calls, and a per-call notice reached Telegram twice at the top of a reply and a third time glued mid-sentence onto the narration before the tool call (#339). Three rules. On the streaming path the notice is emitted **lazily, right before the first content delta of the turn** — eagerly it would surface for a tool-call-only response that shows no text — and `reactLoop` prepends the same notice to the *final* reply, so the session and every non-streaming consumer record what the user saw. **A tool-call iteration's stored message never carries it**: the model would read its own earlier reply as opening with a warning and echo it. And `streamChat` inserts a `\n\n` separator delta (sink only, not content) before a later iteration's first delta when the earlier narration did not end its line, so "Let me check that." and the answer are not one glued sentence on any channel. The same rule covers the replies the loop synthesizes itself: `narrationSeparator` (#347) puts the `\n\n` ahead of the timeout and max-iteration text on the sink only, deciding from the turn's last assistant message in the session (`sess.Messages[startSessionLen:]` in `Process`, `turnMessages` via `compactionState.turnStart` in `reactLoop`) because `turnStream` is a `reactLoop` local the timeout path in `Process` cannot see; it emits nothing with streaming off, when no delta could have preceded it. And **the full notice is once per outage, not once per turn (#348)**: the turn's callback compares `fallbackNoticeKey(n)` (addressed provider, plus `|retired` for 404/410) against `session.Session.FallbackNoticed` through `sameOutage` — a `cooldown` continues whatever outage is recorded for that provider, since it is the chain declining to dial a provider that already failed — and emits `formatFallbackMarker` (`↪ answered by X (model)`) instead of the full text when it matches. A deferred func in `reactLoop` records the key on the session when a notice fired and clears it when the turn had no notice **and** some LLM call succeeded (`turnStream.answered`); a turn where nothing answered leaves the key alone. `FallbackNoticed` rides the `.meta.json` sidecar with `omitempty`, counts as sidecar presence in `Save`, and is cleared by `ResetConversation`. A retired-model notice also carries the model picker on Telegram: `agent.WithFallbackObserver` fires with the notice **only when it is shown in full** (so the picker appears once per outage), `Picker.NoticeKeyboard` gates on `FallbackNotice.ModelRetired()`, and the gateway hands it to `TelegramStreamer.SetFinalMarkup` — the final edit swaps the interim Stop button for the picker, and a final markup forces the final edit even when the text is already shown, or the keyboard never appears — or to the bus reply's `reply_markup`. The observer is read after `Process` returns under a mutex, because the provider may fire it from another goroutine.
- **The interactive CLI is not a `Channel`**: `runAgentLoop` in `cmd/joshbot/main.go` drives it directly, with a `> ` prompt. `internal/channels` contains only the `Channel` interface and `TelegramChannel`. A dead `cli.go` implementing `Channel` used to sit there with no callers; it was deleted after it misled a diagnosis of #104 into the wrong file. Do not reintroduce a CLI channel unless you also wire it up.
- **Never leave a blocking read inside a `select` with `default:`**: that pattern made `joshbot agent` unkillable (issue #104) — shutdown was checked only between reads, so a signal arriving at the prompt was never seen. Read on a goroutine and select over input, `done` and `ctx.Done()` together. Related: `signal.Notify` **disables Go's default termination** for every signal it registers, so a handler that consumes one signal and returns leaves the process deaf to SIGINT/SIGTERM forever. `setupGracefulShutdown` now loops and exits immediately on a second signal; keep it that way.
- **A Telegram parse-entity rejection is silent data loss, not a normal error**: sending with a parse mode set returns `400 ... can't parse entities` whenever the text contains malformed Markdown/HTML, which LLM output produces routinely (a stray `_`, an unclosed backtick, a bare `<tag>`). `isRetryable` has no case for it, so before the fallback existed the reply was abandoned and the user saw nothing at all. `Send` now retries each part once with `ParseMode` cleared; `isParseEntityError` matches Telegram's specific description substrings, case-insensitively. Do **not** widen it to match bare `400` — that would silently downgrade `chat not found` and similar real failures to unformatted sends and hide them.
- **Telegram allowlist is deny-by-default**: `TelegramChannel.IsAllowed` returns `false` on an empty `allowSet`, not `true` — a shell-capable bot must fail closed. `Start` logs a loud, actionable warning naming `channels.telegram.allow_from` when the allowlist is empty. Do not "restore" the old allow-all-when-empty convenience; it was the one-click-RCE shape flagged in #140. Tests that exercise message handling on an empty allowlist must pass an allowlisted sender (`newTestTelegramChannel("<id-or-username>")`).
- **Discord has its own retry classifier and its own stop-channel lifecycle**: `isDiscordRetryable` (`internal/channels/discord.go`) is deliberately separate from Telegram's `isRetryable` — Discord reports permanent failures as `discordgo.RESTError` codes (50007 cannot send to this user, 50001 missing access, 10003 unknown channel, 10013 unknown user, 50013 missing permissions), which Telegram's string matching would retry through the full backoff inside the single `consumeOutbound` goroutine, and its unclassified-error log line names the wrong channel. 429 retries, any other 4xx does not. Separately, `stopCh` belongs to one Start/Stop cycle: `Start` allocates a fresh one and `Stop` closes it under `mu` behind a `stopClosed` latch. Reusing a single channel made a restarted channel deliver nothing (its `consumeOutbound` returned at once, every `Send` aborted its retries) and panicked the process on the second `Stop`. Read it through `stopChan()`, never the field, or the reallocation is a data race.

- **`isRetryable` treats Telegram 403s as permanent**: `bot was blocked`, `user is deactivated`, `message to reply`, and `chat not found` all return `false` — retrying them just burns backoff inside the single `consumeOutbound` goroutine and stalls every queued message behind the doomed send. Unknown errors still default to retry but log at Debug so an unclassified error surfaces. This is orthogonal to `isParseEntityError`, which drives the plain-text fallback in `Send` — keep both.
- **Web tool refuses non-public addresses at dial time**: `NewWebTool` installs `guardedDialControl` on its transport (`internal/tools/web.go`), so the client rejects any connection to loopback, RFC1918, link-local or other non-public addresses regardless of which code path issued the request. Two consequences: an `httptest` server (which listens on `127.0.0.1`) cannot be reached through `WebTool.httpClient`, so test HTTP paths by extracting the decision into a function and testing that directly; and `WebToolConfig.SearchAPI` cannot point at a LAN or localhost search engine. Do not weaken the guard to make a test pass — it is the enforcement point that survives DNS rebinding, and `validateURLForSSRF` alone does not.
- **`--config` names a file, and the home follows it**: `config.LoadFrom(path)` loads exactly that path and anchors `DefaultHome` to its directory, so sessions, media, cron, the skills trust store and `Save` all agree with the config that was loaded. Resolve the config file through `config.ConfigPath()`, never `filepath.Join(DefaultHome, "config.json")` — that ignores an explicitly chosen file name. CLI commands must read config via `loadConfig(c.Path("config"))`, not `config.Load()`, or the flag silently does not reach them. A missing path is an error, never a fallback to defaults.
- **Workspace skills require operator approval**: a `SKILL.md` under `<workspace>/skills/` becomes part of the agent's instructions — its description always, and with `always: true` its whole body on every request, permanently. So workspace skills are inert until approved via `joshbot skills trust <name>`. Approval lives in `~/.joshbot/skills.trust`, **outside the workspace**, so a command confined to the workspace cannot approve skills for itself, and binds to a SHA-256 of the **entire skill directory tree** (every regular file's relative path + content, walked in sorted order), so editing, adding, or removing any file in the directory — not just `SKILL.md`, but a sibling script it tells the agent to run — revokes approval. A legacy digest from an older joshbot that hashed only `SKILL.md` no longer matches and safely revokes (re-inspect and re-trust) rather than crashing. `Loader.Create` (the agent's `skill_registry` tool) writes but never approves — if writing implied trust the gate would be decorative. Bundled skills ship with the binary and are exempt. Do not "helpfully" auto-approve on first run.
- **Shell sandbox is opt-in, fails closed, and is now per-platform**: `tools.shell_sandbox` (`"off"` default, `"workspace"` to enable) confines commands — filesystem plus outbound TCP denial, `$HOME` and the shared temp unreachable, private scratch at `<workspace>/.joshbot-tmp` with `TMPDIR` pointed at it. Enforcement mechanism differs by build target and each lives in its own `sandbox_<os>.go` behind `SandboxAvailable()`/`SandboxSupported()`/`newSandboxCommand()`: **Linux** = Landlock, applied in the `__sandbox-exec` re-exec helper (Landlock is irreversible and inherits to children, so it must never be applied in joshbot's own process); **macOS** = Seatbelt, the command wrapped in `/usr/bin/sandbox-exec` with a deny-by-default SBPL profile built from the same `DefaultSandboxPolicy` (no re-exec helper — `ApplySandbox` is unused on darwin; paths are symlink-resolved because Seatbelt matches real paths and `/tmp`→`/private/tmp`); **other** = no OS sandbox, so enabling it is a startup error. An unknown value or a host that cannot enforce is a startup error, never a silent unconfined run — do not "fix" that by falling back to off. On platforms with **no** sandbox available (`!SandboxAvailable()`, e.g. Windows/BSD) the shell tool **defaults to allowlist-only** (`defaultUnsandboxedAllowlist` in `shell.go`) when no `tools.shell_allow_list` is set, because the deny list alone is bypassable; Linux/macOS keep the unrestricted default. Test containment by asserting the kernel's refusal (`sandbox_linux_test.go`, `sandbox_darwin_test.go`), never by checking command text.
- **`buildGatewayDeps` is the gateway's single wiring point, and the end-to-end test drives it**: `runGateway` subscribes `gatewayHandler(buildGatewayDeps(...))`, and `TestGatewayEndToEnd_TelegramUpdateToWire` (`cmd/joshbot/gateway_e2e_test.go`) runs the same function against a fake Bot API (httptest) with a real bus, agent, session files and `TelegramStreamer` — so a wiring change (sink on the wrong context, shared streamer, broken `Finish` suppression) fails a test instead of only failing in production. Two things keep the test honest: assertions run against the chat's **final state** (`fakeBotAPI.finals`, sendMessage creates / editMessageText overwrites), because a raw call count cannot tell an edit from a duplicate message; and the scripted provider spaces its deltas wider than `defaultStreamInterval` (3s), because a turn that finishes inside one throttle window never puts an interim message on the wire and the loss/duplication assertions then have nothing to bite on — a mutation check on the `Finish` suppression stays green without it.
- **The shell approval gate fails closed by carrying the approver on the context, not on the tool**: `tools.shell_approval` (`"off"` default, `"interactive"`, `"always"`) makes `ShellTool` ask before running. `ShellTool` stores only the *mode*; the `Approver` itself rides the request context (`tools.WithApprover`), for the same reason `agent.WithSink` does — a struct field would be shared across the concurrent `Process` calls Telegram makes and would hand one user's prompt to another's turn. Four properties are load-bearing. `ApproverFromContext` **never returns nil**: with no approver it hands back `DenyAll`, so an unattended turn (cron, heartbeat, the gateway, piped `agent -m`) is refused immediately rather than blocking a background goroutine or auto-approving. `Deny` is the **zero value** of `Decision`, so every path that fails to produce a real answer — timeout, cancellation, an approver that errors, `Approve` returned *alongside* an error — lands on deny without anyone remembering to. `ExecuteAsync` is gated too; without that, `async=true` is one boolean away from no gate at all. And the gate runs **after** the deny list and allowlist, so a command that would be refused anyway never produces a prompt — prompting for those trains the operator to approve on reflex. `ParseApprovalMode` returns `ok=false` on a typo and `cmd/joshbot` turns that into a startup error, mirroring `ParseSandboxMode`. Two approvers exist. `runAgentLoop` installs `cliApprover` when `isTTY(output)`; the terminal read runs on its own goroutine because a bare `Read` on a TTY ignores the context deadline entirely. The gateway installs `channels.ShellApprovalCoordinator.ApproverFor` (#311) per turn via `gatewayDeps.approverFor`, which posts the command with an inline keyboard and blocks on the callback press, bounded by the turn's context — but only for Telegram turns whose inbound message carries its own chat id (never the stored proactive-recall fallback), so cron and heartbeat turns keep DenyAll; a press is matched by pending id *and* chat, first press wins, and an unknown action or cross-chat press is a denial.
- **Telegram and Discord can both be enabled at once — the bus fans out outbound messages per consumer.** `bus.OutboundChannel()` is sugar for `RegisterOutboundConsumer`, which hands the caller a *private* channel; `processOutbound` drains the single arrival queue (`outboundCh` — still what `Publish` writes to, still what a full queue means as backpressure) and copies each message to every registered consumer's channel, non-blocking per consumer so one channel implementation falling behind never stalls delivery to another. Each channel's `consumeOutbound` still filters by `msg.Channel == d.name || msg.Channel == "all"` exactly as before — that filter was never the bug. The bug was that every channel called the same method and got back the *literal same* channel, so two channels running together raced an ordinary Go channel receive over each message and the loser silently never saw it — no error, no log line. Do not revert `OutboundChannel()` to returning `outboundCh` directly; that reintroduces the race. `TestOutboundChannelAccess_TwoConsumersEachSeeEveryMessage` (`internal/bus/bus_test.go`) is the regression test.
- **The shell allowlist screens the whole command, not the first word, and refuses chaining.** `checkAllowList` (`internal/tools/shell.go`) rejects any command containing `;`, `&`, `|`, a newline, a carriage return, a backtick, `$(`, `<(`, `>(`, `$'`, `>` or `<` while an allowlist is in force, because the command reaches `sh -c` unchanged and `echo hi; id` passed a first-word match. **Redirection belongs in that list and was missing**: `echo PWNED > /outside/escaped.txt` passed both the allowlist and the deny list and the shell wrote the file. `>` and `<` are matched as substrings, which covers `>>`, `2>`, `&>`, `<<` and `<>` without enumerating them. It does not exempt quoted occurrences on purpose — a boundary that depends on a quoting parser matching the shell's exactly is not a boundary, and `ls | wc -l` being refused costs a caller one extra call. `defaultUnsandboxedAllowlist` also no longer contains `find`, `go`, `git`, `rg` or `sort`: each launches a program of the caller's choosing (`find -exec sh -c`, `go run`, `git -c core.pager=...`, `rg --pre PROGRAM` once per file, `sort --compress-program=PROGRAM` on spill). Screening flag values instead was rejected — it has to be exhaustive to hold. The criterion for anything added to that list is "cannot, by itself, execute a second program of the caller's choosing"; `TestDefaultUnsandboxedAllowlistHasNoExecutors` pins it by asserting each known executor is both absent from the list and unreachable at runtime. Both `Execute` and `ExecuteAsync` go through the one helper — adding a third entry point means calling it too.
- **`EvalSymlinks` cannot tell a dangling symlink from a missing file**, so `resolveSymlinks` (`internal/tools/path_guard.go`) must resolve every re-appended component, not just the nearest existing ancestor: `ws/evil -> /outside/x` with no `/outside/x` returned the lexical path, passed `isWithinBase`, and was then written. Resolution narrows but does not close the TOCTOU window either — a component can still be swapped between the check and the open — and `O_NOFOLLOW` was not enough on its own, because it constrains **only the last component** while the kernel still follows every intermediate one. Replacing `ws/sub` with a symlink to `/outside` after the check put the write at `/outside/file.txt`, and read paths used bare `os.ReadFile` with no `O_NOFOLLOW` at all. **Every filesystem-tool path now opens through the one helper in `internal/tools/openat.go`** — `openInRoot` / `mkdirAllIn` / `safeReadFile` / `safeWriteFile` / `readDirIn`, built on Go 1.24's `os.Root`, which holds the containment root as a descriptor and resolves each component with `openat(2)`. `writeNoFollow` is gone. Three things to keep in mind. `os.Root.MkdirAll` and `ReadDir` became available once this module moved to Go 1.25, but `mkdirAllIn` still walks the levels itself rather than using them — the manual walk was written when the module targeted 1.24 and migrating it to the native API is a separate, untaken change — and it must `Lstat` before treating `EEXIST` as benign, since `Mkdir` on a name that is already a symlink also returns `EEXIST`. `relInRoot` absolutizes both sides, because `filepath.Rel` cannot relate a relative path (`NewFilesystemTool(".", …)`) to an absolute root. And `containmentRoot` (`filesystem.go`) picks the root — workspace, matching `allowedPaths` entry, else the workspace base, i.e. fail-closed — so a new operation must call it rather than pass a path straight to `os`.
- **An allowlist entry's *shape* decides which field it may match**, on Telegram as on Discord: an all-digits entry matches only the numeric user ID, a non-numeric entry only the username/display name. Matching every entry against every field is an authentication bypass — display names are attacker-chosen and unvalidated, so a stranger could set theirs to the operator's numeric ID.
- **`mach-lookup` in the macOS Seatbelt profile is an allowlist (`macMachServices`), not a blanket grant** — an unrestricted `(allow mach-lookup)` reaches XPC services running outside the profile that will act on the sandboxed process's behalf, which hollows out the file and network rules. Adding a service name is a security decision and gets justified in place. Two related traps in `sandbox_darwin.go`: `GOCACHE` is usually unset on macOS (the toolchain defaults it to `~/Library/Caches/go-build`, not under `~/.cache`), so it is resolved via `go env GOCACHE` and granted explicitly or `go build` fails under the sandbox; and a path that does not exist yet is silently dropped from the profile by `existingPaths`, so `newSandboxCommand` creates the workspace and its scratch dir up front rather than rendering a profile with no write grant. Note the profile is passed with `-p`, so it (and the workspace path) is visible in `ps` to any local user.
- **A bus or channel object that can be restarted must not keep a per-run channel in a per-object field.** `MessageBus.Start` hands each goroutine the context it created rather than letting them read `mb.ctx`, which a later `Start` reassigns while the previous run's un-joined goroutines are still reading it; `DiscordChannel` allocates a fresh `stopCh` per `Start` and latches the close, because a channel-lifetime `stopCh` stayed closed after the first `Stop` (making `consumeOutbound` return instantly and every `Send` abort its retries) and a second `Stop` panicked the process. `mcp.Client` has the same shape: `doneCh` belongs to the connected process, is snapshotted by `call`, and is closed by the `readLoop` that was handed it — a per-client channel left every call after a failed handshake reporting "server stopped" forever.
- **The heartbeat's publish pattern and its check-off pattern must be the same regex.** They were two, and every line they disagreed on (`-[ ] task`, `* [ ]task`) published on every tick forever. `internal/heartbeat` now has exactly one `uncheckedRE` and a `parseTask` that returns both the task text and the rewritten line. A task is checked off only after `bus.Send` accepts it — flipping the box on a dropped send loses the task silently — and `HEARTBEAT.md` is rewritten with a `writeFileAtomic` using a uniquely-named temp file, since the read-modify-write spans a tick and a user may be editing the file inside it.
- **A configured MCP server is inert until its *manifest* is approved, and the gate must not be "simplified" into an execution gate.** `internal/mcp/trust.go` holds a `TrustStore` at `~/.joshbot/mcp.trust` (mode `0600`) keyed by server name and valued by `HashManifest(tools)` — a SHA-256 over every advertised tool's name, description and input schema, sorted by name and **length-prefixed** (without prefixing, `{"ab","c"}` and `{"a","bc"}` collide and a server could swap one for the other while keeping approval). `registerManifest` in `internal/tools/mcp_tool.go` is the single gate; it is split out of `registerOneMCPServer` deliberately so the decision can be tested without spawning a process. Four things to preserve. An unapproved server **is** still connected and asked for `tools/list` — that is the only way to learn what it advertises, and anyone who can edit `mcp.servers.<name>.command` can already run commands; what the store governs is what reaches the model, not whether the process runs. `trust.IsTrusted` is a **nil-receiver method returning false**, so a caller that forgot to load a store loses MCP tools rather than gaining unapproved ones — do not "fix" the nil check by skipping the gate. `LoadTrustStore` treats a missing file as empty but a malformed one as an error, because silently disabling every server gives the operator nothing to act on. And `joshbot mcp trust` refuses an unreachable server, since recording a digest it never read would approve a manifest sight unseen.

- **`web_fetch` strips script/style/comment *elements*, and every tag match is ASCII case-insensitive.** `WebTool.removeTag` (`internal/tools/web.go`) once found `<script` and the next `>` and deleted only that span, so the *body* — script source, CSS, comment text — reached the model on every fetch: token burn plus a prompt-injection surface on attacker-controlled pages. It now finds the matching `</script>` and deletes the whole element, and a dangling open tag with no close drops the remainder rather than trusting it. Two rules keep it correct. **Matching folds case**, because tag names are case-insensitive in HTML and the *page* picks the case: a `strings.Index` search leaves `<SCRIPT>…</SCRIPT>` intact, which is exactly the bypass the strip exists to prevent — `TestWebTool_RemoveTag`'s uppercase and mixed-case subtests go red the moment it is narrowed back. And the shared `indexFold` (`internal/tools/mcp_tool.go`) **walks bytes instead of lowercasing the haystack**: `unicode.ToLower` can change a string's byte length, so an offset taken from a `strings.ToLower` copy does not index the original — and `sanitizeMCPDescription` slices at exactly that offset to defang envelope tags, so a description carrying one length-changing rune ahead of a `</skills>` would have mis-sliced and defanged nothing.
- **`promptEnvelopeTags` must be widened whenever a new system-prompt section is added.** `sanitizeMCPDescription` (`internal/tools/mcp_tool.go`) defangs joshbot's own envelope tags in server-supplied descriptions — otherwise `</skills>` in a description closes a section joshbot opened and the rest reads as joshbot's own instructions. It matches those names only, case-insensitively, and replaces the brackets rather than deleting the text (so `joshbot mcp list` still shows what the server sent, and the `<path>`/`<name>` placeholders real servers use survive). `TestPromptEnvelopeTagsCoverAgentContext` greps `internal/agent/context.go` and `internal/agent/agent.go` for closing tags and fails on any not covered — it caught a missing `personality` the day it was written. `ctx_compress` is exempt on purpose: it delimits a block stripped from model *output*, not a section of the prompt. Descriptions are also capped at `mcpMaxDescriptionChars` (1024) because a description is prompt text on every single request.

- **`internal/tools/web.go`'s `exaSearch` is not an MCP client and is correctly outside the trust gate.** It is one HTTP POST to a hard-coded endpoint that returns *search results*, never tool definitions — nothing it returns becomes callable or reaches the system prompt as instructions. `internal/mcp` is a stdio client that spawns processes; there is no second implementation to consolidate, only a shared wire format. If it ever grows into "ask the endpoint what tools it has", it must move onto `internal/mcp` and behind the trust store first.

- **MCP servers are wired into `cmd/joshbot` now.** `setupComponents` calls `registerMCPServers`, and every long-lived entry point defers `closeMCPServers` to reap the child processes; the manager is a package var because exactly one setup runs per invocation. Startup is fail-soft by design — a server that will not start is logged and skipped, never a startup abort. Docs claiming MCP is "not yet wired" are stale.
- **`setupComponents` starts background services nobody holds a handle to, so they must be stopped explicitly**: cron, the heartbeat and the memory consolidator are started at the end of `setupComponents`, and `learning.Consolidator.Start` runs its first pass *immediately* from a goroutine, writing into `workspace/memory`. Each one now registers its `Stop` with `registerBackgroundService`, and every long-lived entry point defers `stopBackgroundServices` next to `closeMCPServers`. Two things keep it correct. The stoppers are **one-shot** — `heartbeat.Stop` and `Consolidator.Stop` close a channel and panic on a second call — so `stopBackgroundServices` takes the slice and clears it under the lock, which is what makes it safe to call twice. And a **test** calling `setupComponents` must register the stop *after* its temp home is created (`setupConfig` does this), because `t.Cleanup` runs LIFO: registered earlier, the goroutines are still writing while `t.TempDir` is being removed, and the run fails with `TempDir RemoveAll cleanup: ... directory not empty` in whichever subtest lost the race. That flake took main CI red on `ac13b2f`.
- **Guard a discipline you cannot reach behaviourally at the source level, and prove the detector fires.** `runGateway`'s bus handler is an anonymous closure that only a full gateway stand-up would exercise, so `TestGatewayHandlerHasNoDirectConsoleWrites` (`cmd/joshbot/audit_sweep_test.go`) parses `main.go` with `go/parser` and fails on any `os.Stdout`/`os.Stderr` write inside it — a direct write bypasses both the redacting log writer and the configured level. The version before it called `joshlog.Debug` directly, which asserted the logging library's level filtering and would have stayed green with the leak put right back. A companion test runs the same detector over a fixture containing the regression, so the guard cannot silently stop detecting anything.
- **`SandboxMode` zero value is `""`, and `""` means off**: `SandboxMode` is a string, so a bare-constructed `ShellTool` (via `NewShellTool*` without `SetSandbox`/`NewShellToolFromConfig`) leaves `sandbox` empty, not `SandboxOff`. Empty must be treated as off, or the tool takes the sandbox path and `sandboxPreflight` refuses on any host without Landlock (macOS, where releases are cut) — which silently reddened the shell/security regression tests (#138). Both the fast-path check in `buildExecCmd` and `sandboxPreflight` normalize `"" → off`, `SetSandbox` maps `""` to `SandboxOff`, and the constructor initializes the field. Keep all four: `""` behaving as anything but off is a regression. CI runs a `macos-latest` leg (build + test, no coverage gate) so a non-Linux-only break is caught.
- **Channel allowlist entries are matched by shape, not against every field**: `internal/channels/discord.go` partitions `allow_from` at construction — an all-digits entry lands in `allowIDs` and matches only the numeric user ID, anything else lands in `allowNames` and matches only username / global display name. Matching every entry against every field was an auth bypass: global display names are free-form and not unique, so a stranger could set theirs to the operator's snowflake and be admitted. **Telegram still has the flat-set shape** (`IsAllowed` in `internal/channels/telegram.go`), where a numeric entry can be matched by a name built from `firstName`/`lastName`; it is pre-existing and should get the same partitioning.
- **`HashSkillFile` covers symlinks by name and raw target, never dereferenced**: reading through a link would let a skill dir hash whatever it points at, so the digest folds in the link name plus `os.Readlink`'s raw target. Adding, repointing or removing a symlink inside an approved skill therefore revokes trust like any other file change.
- **Spawned commands get an allowlisted environment**: `runCommand` assigns `execCmd.Env = sanitizedEnv()`. The allowlist and the credential screen live in **`internal/childenv`** (`childenv.Sanitized` / `childenv.IsSecretName` / `allowlist` / `allowPrefixes`), not in `internal/tools` — MCP server processes need the identical screen and `internal/tools` imports `internal/mcp`, so keeping it here would mean duplicating it there. `internal/tools/shell_env.go` is now thin aliases; `cmd.Env` is never left nil on either path. A nil `Env` inherits this process's, which hands every provider API key to any command the model runs — readable with a bare `env`, so no sandbox and no deny-list rule would catch it. If a command legitimately needs a variable, add it to `childenv`'s `allowlist`/`allowPrefixes`; do not switch the mechanism to a deny-list, because a miss there is a leaked credential. Note the allowlist is screened again by `isSecretEnvName`, so a credential-shaped name cannot ride in on a broad prefix rule.
- **`restrict_to_workspace` does not confine what a command touches**: it only validates the `working_dir` *parameter* (`internal/tools/shell.go:120-130`, `340-350`). A command body is still free to read anything the process can — `cat ~/.ssh/id_rsa` works with `restrict` on. Treat the flag as "where the command starts", not "what it can reach". Real confinement needs an OS boundary (issue #75).
- **SSRF checks belong on the resolved address, never the hostname**: an attacker controls their own DNS, so a name carries no signal about where it points. `validateURLForSSRF` resolves every hostname and fails closed when the lookup fails. Use `isBlockedIP`, not `isPrivateIP`, for "is this safe to reach" — `isPrivateIP` covers only RFC1918-style ranges and excludes link-local, which is where every cloud metadata endpoint lives.
- **`agent.Process` reports LLM failures in band, so every non-interactive caller must translate them back**: it returns `"Error processing request: ..."` as reply *text* with a nil error, because a chat channel has to show the user something. `agent -m` exited 0 over a completely unreachable provider until `agentReplyError` (`cmd/joshbot/main.go`) turned that prefix back into an error — text mode exits 1, JSON mode sets `"is_error": true` on the result document and writes a `{"type":"error",...}` document to stderr. Any new non-interactive entry point calling `Process` needs the same translation; treating the string as a normal answer is the bug. The rule runs both ways: a **new failure path inside `Process` must use `agent.ReplyPrefix`**, not a prefix of its own. The session-lock acquisition returned `"Error: Failed to load session: ..."`, which `ReplyError` does not match, so a turn that gave up waiting reached the HTTP API as a 200 whose answer was an error string and `agent -m` as exit 0.
- **`providers.ListModels` refuses an empty `APIBase` instead of defaulting to OpenRouter**: the old fallback to `https://openrouter.ai/api/v1` meant credential validation for *any* other or unknown provider dialled openrouter.ai and printed "✓ validated". It now errors, which is what lets `configure.ValidateProviderCredentials` report "could not verify ... no API base URL configured" for the providers with no fixed endpoint (azure, custom, litellm). Do not reintroduce the default.
- **Credential validation is a one-token chat completion, never a models listing**: `providers.ProbeCredential` (`internal/providers/probe.go`) is what `configure.ValidateProviderCredentials` runs, because several providers' `/models` endpoint is unauthenticated — OpenRouter answers 200 to *any* Authorization header, so ListModels-based validation printed "✓ validated" for a typo'd key and the user's first real message got the raw 401. The return contract is three-valued and the middle matters: 401/403 is `ErrCredentialRejected` (say "your key was rejected"), a 429 is **success** (a rate limit is issued to an authenticated key), and every other failure — 404 model, network, 5xx — is indeterminate: report "could not verify", never print the checkmark. `ProbeCredential` still refuses an empty `APIBase` for the same reason `ListModels` does — dialling a default endpoint validates some other provider's credential.
- **Agent progress callback is carried per-request via the context, not on the Agent struct**: `agent.WithSink(ctx, fn)` attaches a `ProgressFunc` to the `context.Context` passed to `Process`. The ReAct loop in `internal/agent/agent.go` reads it via `progressFromContext(ctx)` — nil means zero behavior change for callers that don't opt in (Telegram, non-interactive `agent -m`, tests). `cmd/joshbot/main.go`'s `runAgentLoop` attaches the sink only when `isTTY(output)` is true, to drive the interactive CLI's tool-call lines (`⏺ tool(args)` / `⎿ ok (1.2s)`) and "thinking..." spinner. Because the sink lives on the context, concurrent `Process` calls on the same `Agent` never cross-deliver events (issue #115).
- **Non-TTY detection lives in `cmd/joshbot/main.go` as the `isTTY` package var**, not a plain function — this is deliberate so tests can override it (`isTTY = func(io.Writer) bool { return true }`, restored via `t.Cleanup`) instead of depending on whether the test process happens to have a real terminal attached. Production detection type-asserts the `io.Writer` to `*os.File` and calls `github.com/mattn/go-isatty` (already an indirect dependency, promoted to direct — pure Go, no cgo); anything that isn't a `*os.File` (a `bytes.Buffer` in tests, a pipe) is correctly treated as non-TTY without special-casing. Both the tool-call progress lines (`⏺ tool(args)` / `⎿ ok (1.2s)`) and the "thinking..." spinner are gated on this — never print `\r` or ANSI clear codes when it's false, or piped/scripted `joshbot agent` output (and `scripts/verify-local.sh`) breaks.
- **The spinner goroutine's lifetime is exactly one `startSpinner`/`stopSpinner` pair** (`cliProgress` in `cmd/joshbot/main.go`), scoped around a single blocking `agentInstance.Process(ctx, msg)` call inside `runAgentLoop`'s per-message loop — not around the whole loop. `stopSpinner` closes a cancel channel and then blocks on a "done" channel the goroutine closes on exit, so it cannot return before the goroutine has actually stopped; there is no separate leak-detection mechanism, that join is the whole guarantee. Both the spinner and the tool-progress printer (`onToolEvent`) share one `sync.Mutex` on `cliProgress`, because the spinner ticks from its own goroutine while `onToolEvent` is invoked synchronously from inside `Process` on the caller's goroutine — without the shared lock their writes to `output` interleave mid-line.

- **MCP servers are started during component setup**: `internal/mcp` is a stdio JSON-RPC 2.0 client (newline-delimited messages, not LSP Content-Length framing) with lazy start and clean process reaping. `tools.RegisterMCPTools(ctx, reg, cfg.MCP)` connects enabled servers, enumerates `tools/list`, and registers each as `mcp__<server>__<tool>` (namespacing is a security control — it makes shadowing `shell`/`filesystem` impossible, since built-ins never carry the prefix and the registry refuses duplicate names). It returns a `*mcp.Manager` whose `Close()` MUST be called at shutdown to reap the child processes. Three bounds keep a server from taking the process with it: a result is truncated at `mcpMaxOutputChars` (4,000), a single message read is capped at `maxMessageBytes` (4 MiB) by `readLine` — `bufio.Reader.ReadBytes` grows without limit, so an unbounded reply was a heap exhaustion — and the child gets `childenv.Sanitized` rather than a nil `cmd.Env`, so it never inherits provider API keys. The import direction is `tools → mcp` and `tools → config`; `internal/mcp` must never import `internal/tools` or it creates a cycle. Config lives at `mcp.servers.<name>` (`Command`/`Args`/`Env`/`Enabled`), and `config.json`'s out-of-workspace location is the trust boundary (see SECURITY.md). `setupComponents` in `cmd/joshbot/main.go` calls `registerMCPServers` right after `RegistryWithDefaults`; the manager is held in a package var and reaped by `closeMCPServers`, which `runAgent` and `runGateway` defer. Startup is fail-soft — a server that will not start or list tools is logged and skipped, never a startup abort. Two client invariants: the read-loop done channel is **per process**, allocated in `Connect` and closed by the readLoop it was handed (a per-Client channel left a failed handshake permanently "stopped" even after a later successful Connect), and `dispatch` deletes the pending entry before replying and sends non-blocking, so a server answering the same id twice cannot wedge the read loop.
- **Outbound attachments are a typed field, contained twice, and sniffed — `send_file` is its own tool for a reason.** `send_file` (`internal/tools/send_file.go`) is deliberately not a flag on `message`: `MessageTool.Execute` rejects empty content and a caption-less file send is legitimate. Six rules. The transport is `OutboundMessage.Attachments []bus.Attachment` (`internal/bus/attachment.go`), a **typed slice, never a `Metadata` key** — a mistyped map key sends nothing and returns success, which is the failure mode nothing detects. The path goes through **both** containment layers, `FilesystemTool.resolvePath` *and* the `containmentRoot` + `openInRoot` walk; mutation testing showed each refuses an escape alone, so removing "the redundant one" is removing half a boundary. **Content decides the type**: the head is sniffed with `http.DetectContentType` + `providers.IsSupportedImageMIME`, never `filepath.Ext` — same rule as inbound images. **There is exactly one egress route and it must stay that way**: `Data` is always populated, read through the very handle `openInRoot` opened, and `Attachment.SourcePath` is a workspace-relative *label* nothing ever opens. The earlier two-route design published an absolute `Path` above a 10 MB inline threshold and let `telebot.FromDisk` re-open it — an uncontained `os.Open`, on the channel goroutine, after a bus hop, again on every retry, with `att.Size` stale by then: swapping the leaf for a symlink to `~/.joshbot/config.json` exfiltrated the provider keys. Re-introducing *any* downstream open, or an absolute `SourcePath`, restores it. That is also why `DefaultDocumentMaxBytes` is 10 MiB and not Telegram's 50 MiB — the payload is in memory, so the cap is a memory bound and #280 raising it raises memory with it. And the size constants are reached through `AttachmentLimits()`/`Limits()`, not hardcoded per use site. **The recipient is not an argument**: the tool has no `channel` parameter; `Agent.process` sets `tools.WithChannel(ctx, msg.Channel)` before the ReAct loop and `send_file` reads it back, refusing an empty one rather than defaulting — the old `""`/`"same"` → `"cli"` fallback failed on Telegram with `no chat ID stored for channel: cli` and on the CLI *succeeded while delivering nothing*, which taught the model to pass an explicit address. On Telegram (`internal/channels/telegram_attachment.go`) the retry **rebuilds the payload every attempt** — a `telebot.FromReader` payload retried as-is uploads zero bytes — the parse mode is cleared for the **caption only** on a `can't parse entities` error, and a caption over `TelegramMaxCaptionLen` (1024) is re-sent as its own message rather than truncated. A channel that cannot send attachments must **degrade honestly** (`describeUnsentAttachments` in `internal/channels/discord.go` appends name, size and the workspace-relative `SourcePath` — an absolute one would print the operator's home directory into chat) — a silent drop looks like a successful send to the model, which then says the file was delivered. **The gate that closes the last gap (issue #304): `tools.send_file_approval` runs *after* both containment layers, never before** — a path already refused by containment must not reach a human as a prompt, the same ordering rule the shell deny list follows ahead of its own approval gate. It reuses `tools.WithApprover`/`ApproverFromContext` verbatim rather than a second mechanism: `SendFileTool.SetApproval` mirrors `ShellTool.SetApproval`, `ApprovalRequest{Tool: "send_file", Command: "send <file> (<size>) to <channel>"}` renders through the identical CLI/Telegram prompt code (both already keyed off `req.Tool`/`req.Command` generically, not hardcoded to shell), and an unattended turn is denied immediately for the same reason. `tools.shell_approval` and `tools.send_file_approval` are independent config values — an operator may trust one tool and not the other — but the CLI and Telegram install exactly one approver per process, so `combinedApprovalMode` (`cmd/joshbot/approval.go`) picks whichever of the two is more restrictive (`always` beats `interactive` beats `off`) to construct it, and each tool still gates on its own configured mode when deciding whether to ask at all. `tools.send_file_disabled` (inverted-polarity bool, `omitempty`, same reason `dream_mode` and `api.webui` are strings/opt-in rather than a bare bool — a `Config` bool without `omitempty` is written into every saved config and its default can never be flipped without a migration) removes the tool from the registry entirely for an operator who wants no outbound-file capability at all.
- **The workspace is now an egress surface, not just a read surface.** `send_file` can deliver any file the filesystem tool can read, so "anything joshbot must not disclose does not belong in the workspace" is load-bearing rather than advisory — and the workspace fills itself: `web_fetch` output, inbound Telegram documents and every file the agent writes all land there, so its contents are partly attacker-influenced. The boundary also *widens with configuration*: `tools.restrict_to_workspace = false` makes `containmentRoot` return `/` and every file on the machine becomes sendable, and `tools.filesystem`'s `allowed_paths` — until now a read allowlist — is now an egress allowlist too. Adding a path there is a disclosure decision.
- **Images are carried as bytes on the turn, screened before the network, and never persisted**: `providers.Message.Images` is `json:"-"` and the wire form is produced by `Message.MarshalJSON`, which keeps a text-only fast path so an ordinary message serializes exactly as it did before attachments existed; images become a `content` parts array with `image_url` data URLs. Because every provider (Anthropic included) is dialled through the OpenAI-compatible serialization point, that one method covers them all — do not add a per-provider image path. Four rules hold the design together. **Content decides the type, never the name**: `providers.NewImage` sniffs the bytes, so a `.png` that is prose and a Telegram document declaring `image/png` are both refused; a declared MIME may only decide whether a download is worth spending (`providers.IsSupportedImageMIME`), never what the bytes are. **The capability gate runs before the first network call**, in `screenForImages`, from both `Chat` and `ChatStream` — `SupportsVision` fails closed on unknown models, because guessing "yes" turns a typo into a provider 400 mid-conversation while guessing "no" produces an error naming the model. **Sessions store `session.ImageRef` (type, size, SHA-256) and deliberately not the bytes**: session JSONL is exempt from redaction and relies on its `0600` mode, and stored images would be reloaded and re-billed on every later turn inside the memory window; `TestImageRefSurvivesRoundTripWithoutTheBytes` pins that boundary. **And on Telegram the download happens strictly after `IsAllowed`** — it carries a file id to the Bot API on the sender's behalf and confirms the bot is live — with an over-limit photo refused from its declared `FileSize` before any transfer and the body read through a `LimitReader` at `MaxImageBytes+1` so over-limit is distinguishable from truncated. A failed attachment ends the turn with an error in the chat; forwarding it as a text-only `[Photo]` gets a confident answer about nothing. `--image` paths on the CLI are **not** workspace-contained on purpose: containment exists to bound the model, not the operator, so `loadImageFlags` enforces only what the operator cannot see for themselves (a regular file, real image content). Text documents follow the same claims-vs-bytes rule via `isTextLikeDocument`/`readTextDocument` (`internal/channels/telegram_documents.go`): the declared MIME or extension decides whether to download, the bytes must be NUL-free valid UTF-8 to be inlined (capped at `telegramTextDocMaxBytes` with a visible marker), and a binary document is refused honestly rather than forwarded as its filename. Voice transcription (#276): `stt.provider` names an existing provider whose key and endpoint are reused (`buildTranscriber` in `cmd/joshbot/main.go` validates at startup — unknown/disabled/keyless provider, no api_base, no default model are all fatal, naming the key); `providers.TranscribeAudio` refuses an empty APIBase rather than defaulting one (the ListModels/ProbeCredential rule — note the pre-existing `Provider.Transcribe` interface stub still carries the openrouter-default anti-pattern and is unimplemented; do not wire it). The channel refuses over-limit voice from *declared* duration/size before any download, never persists audio, and with no transcriber wired keeps the honest refusal. The transcriber field is set once before Start and read lock-free on the message path.

- **PDF documents ride the same rail as images, with a *separate* capability list (#278)**: `providers.Document` mirrors `Image`, is carried on `providers.Message.Documents` (`json:"-"`), and is serialized at the same single point — `Message.MarshalJSON`'s text-only fast path is now `len(m.Images) == 0 && len(m.Documents) == 0`, and a text-only message must still serialize byte-identically (`TestTextOnlyMessageSerializesByteIdentically` compares exact JSON bytes). The wire form is OpenAI's Chat Completions `file` content part: `{"type":"file","file":{"filename":…,"file_data":"data:application/pdf;base64,…"}}`. Four rules. **`SupportsDocuments` is not the vision list** — llava reads images and cannot parse PDFs — so it is its own substring list (`internal/providers/documents_capability.go`), fails closed on unknown models, and its `ErrDocumentsUnsupported` **names the models tried**, which is the whole point of the gate. **`screenForDocuments` is a separate function from `screenForImages` and is called from BOTH `Chat` and `ChatStream`** — missing the `ChatStream` call site is a live bug class here, since streaming is on by default. **Content decides the type**: `NewDocument` requires the `%PDF-` magic, so a PNG named `report.pdf` is refused and a PDF named `shot.png` is not smuggled through the image path; the declared MIME and `FileSize` decide only whether a download is worth spending. And the caps are `providers.MaxDocumentBytes` (8 MiB) and `MaxTotalDocumentBytes` (16 MiB), refused from the declared size *before* the transfer and then read through a `LimitReader` at cap+1 so a lying declaration is refused rather than truncated — a compile-time assertion in `internal/channels/telegram_documents.go` keeps the per-document cap under Telegram's 20 MB bot-download ceiling. Sessions persist `session.DocumentRef` (label, type, size, SHA-256) and never the bytes, for the same reason images are not stored; a PDF is more sensitive than a photo, not less. A PDF that fails to read **ends the turn** with an honest chat error rather than degrading to `[Document: x.pdf]`, following `attachTextDocument`'s `(value, bool)` contract. There is no `--document` CLI flag: this is a Telegram inbound path only.
- **GitHub Copilot authentication is two-step, and the OAuth token is not the API credential**: the device flow stores a GitHub OAuth token, which `api.githubcopilot.com` rejects. It must be exchanged at `GET https://api.github.com/copilot_internal/v2/token` (`authorization: token <githubToken>`) for a short-lived Copilot token used as `Authorization: Bearer`; `CopilotProvider.ensureAPIToken` caches it until a minute before `expires_at` and clears it on a `401`/`403` so a stale exchange is not replayed. Three traps live here. `CopilotAPIURL` **has no `/v1`** — chat is `<base>/chat/completions` and models is `<base>/models`; adding the segment 404s every request. **A zero `expires_in` means no expiry, not expired now** — GitHub's OAuth-App device flow returns none, and the old unconditional `now + expires_in` stamped every fresh token as already dead, which `LoadToken` then rejected on the next read. And `https://models.github.ai/catalog/models` is the **GitHub Models catalog, a different product** — it is not what Copilot will accept as model ids. Requests also need the integration headers (`Copilot-Integration-Id: vscode-chat`, `Editor-Version`, `Editor-Plugin-Version`, `Openai-Intent`, `X-Github-Api-Version`), all set in one place by `setCopilotHeaders`.
- **Flipping a bool config default needs a schema migration, because the field is serialized either way**: `Config` bools have no `omitempty`, so every config joshbot has ever saved contains `"streaming": false` — written by onboard, by `configure`, by any save at all — whether or not the operator ever saw the key. `loadFileConfig` does `cfg := Defaults()` then unmarshals over it, so a stored `false` beats the new default and a straight flip in `Defaults()` reaches nobody upgrading. `agents.defaults.streaming` going on by default (#119) is therefore a v4 → v5 migration in `migrateConfig` that resets an inherited `false` once and logs it; a `false` stored at v5 is a genuine opt-out and is left alone. Migration is in-memory only — `loadFileConfig` does not rewrite the file — so the reset re-runs on every load until something saves the config, which is correct but means the log line is not once-per-install.
- **A `time.Duration` in a config struct decodes as nanoseconds, so every timeout key is a `config.Duration`**: `encoding/json` marshals and unmarshals a `time.Duration` as its underlying `int64` of nanoseconds, and joshbot's config decoding is plain `encoding/json` — the `mapstructure:` tags are vestigial, there is no viper. So `"timeout": 600` set a six-hundred *nanosecond* timeout and every request to that provider failed instantly with `context deadline exceeded`, a symptom indistinguishable from a dead provider (#240). `config.Duration` (`internal/config/duration.go`) reads a duration string (`"600s"`, `"10m"`, `"1h30m"`) or a bare number of seconds and always marshals the string form back, so a config joshbot saves is one a human can edit. Four things to keep straight. A bare integer **at or above `legacyNanosecondCutoff`** (one second in nanoseconds) is still read as nanoseconds, because that is what an older joshbot *wrote* — `joshbot configure` set `p.Timeout` and saved, so configs in the wild carry `900000000000`; as a seconds value that is over thirty years, so the ranges cannot collide in practice. **`Config.Validate` rejects a nonzero timeout under a second**, naming the key, because the parser cannot catch a genuine unit mistake like `"500ms"` and an unvalidated one fails at the first request and blames the context. **Zero means unset everywhere** — `agents.defaults.timeout` carries `omitempty` and `agent.WithTimeout` ignores a non-positive value, which is what lets `cmd/joshbot` pass the config value through with no special case and no schema migration (the trap the `streaming` bool hit at v4→v5). And **a new timeout key must use this type, not `time.Duration`** — a plain field is the bug, restored.
- **`providers.<name>.timeout` reaches every provider, and a bad timeout is a *fatal* config error**: the key was consumed only by ollama while the docs described it as universal, so `registerProviders` (`cmd/joshbot/main.go`) now passes `p.Timeout.Duration()` into every `providers.Config` — a zero is defaulted by each factory (300s for ollama, 120s elsewhere), which is what makes passing it unconditionally safe. `agents.defaults.timeout` also reads from `JOSHBOT_AGENTS__DEFAULTS__TIMEOUT` via `parseDurationEnv`, under exactly the file's rules, so a bare `600` means seconds in both places; an unparseable value is reported, never dropped, because an ignored override leaves the operator on the default they were raising. And `validateTimeout` returns a `fatalConfigError`, not a plain error: `config.Load` answers an ordinary validation failure by logging "Config unusable, using defaults" and substituting `Defaults()`, so a mistyped `"500ms"` would silently take every provider, API key and allowlist with it. Note the duration grammar is `time.ParseDuration`'s exactly — `internal/cron.ParseDuration` additionally accepts a `d` suffix, and `"1d"` in a config timeout is an error, not a day; `internal/config` cannot import `internal/cron` to share it, because cron imports `internal/bus`.
- **A registry-backed provider registers through the generic arm, not a new bespoke `if` arm.** `registerProviders` (`cmd/joshbot/main.go`) has a bespoke arm only for the providers whose registration carries logic a generic form cannot express: openrouter (the default), nvidia/groq (fallback priority), poolside (a default model), ollama (a default base + 300s timeout) and github-copilot (token auth). Every other registry-backed provider -- openai, anthropic, azure, custom, litellm, and any that joins `providers.IsProviderRegistered` later -- routes through one `for name, p := range cfg.Providers` loop, gated on `providers.IsProviderRegistered(name)` and skipped for those six names. **Do not add a new bespoke `if p, ok := cfg.Providers["x"]` arm for a plain LiteLLM-based provider**: it duplicates the generic arm (the register map dedupes by name, but then two code paths have to stay in step), and a hand-copied config field list is exactly how a field silently falls out of sync -- the bespoke `custom` arm's `model := p.Model; if model == "" { model = p.Model }` was a no-op that #235 removed by folding `custom`, `openai` and `anthropic` into the one generic arm. Gate on the registry so a configured-but-unknown name still fails loudly (`noProvidersRegisteredError`, #71) rather than silently. `TestRegisterProvidersRegistersOpenAICentricProviders` pins that `openai`/`anthropic`/`azure`/`litellm`/`custom` all register through that one loop; before it, a legacy config for any of them registered nothing while a valid `configure` kept writing it. **And every name in that loop is canonicalized first** (`providers.CanonicalProviderName`): the registry aliases and lowercases (`local` -> ollama, `nim` -> nvidia, `Ollama` -> ollama), so a skip list, a fallback-order lookup or a `Register` call keyed on the raw config name disagrees with the registry it is gating on -- a config key of `local` slipped past the exact-match skip and registered a *second* ollama entry in the chain, built without the bespoke arm's default base and 300s timeout, under a name nothing else looks up. Neither duplicate errors. `TestRegisterProvidersSkipListMatchesAliasAndCaseVariants` pins it.
- **Dream is off by default and its mode is a string, not a bool**: `agents.defaults.dream_mode` is `""`/`"off"`/`"record"`/`"full"` with `json:"dream_mode,omitempty"`, precisely so it needs no schema migration — a `Config` bool has no `omitempty`, is written into every saved config, and therefore cannot have its default flipped without one (see the `streaming` v4→v5 note above). Three more things to know. `Manager.AppendHistory` is the **only** Stage-1 hook; a turn that never appends history records nothing, so a test that skips it consolidates an empty log and passes vacuously. `SearchSimilar` reads `dream_consolidated.jsonl` off disk, **not** the in-memory vector store — the store is rebuilt per `Consolidate` and holds raw records, so a restarted process would otherwise find nothing; and it truncates to `k`, so `SearchSimilar(ctx, "", 0)` returns nothing, which is why `ListConsolidated` exists for "show me everything". And `Consolidate` persists before it clears the raw log: a crash between the two costs a re-run, the other order costs the records.
- **A subagent output schema errors rather than returning prose, and a background run must convert its own cancellation**: `subagent.Config.OutputSchema` is a deliberate small subset of JSON Schema (required keys, optional per-key types). Three things hold it together. The required keys ride the **user turn**, not the system prompt, next to the task they apply to. A mismatch gets **exactly one** repair round-trip and then errors — returning the prose as success repeats the `agent -m` anti-pattern of reporting success over work the caller cannot use. And the repair gets its **own** turn via an internal `repairBudget` rather than spending one of the caller's `MaxIter`, because a `MaxIter` of 1 would otherwise make every schema'd run fail by construction. Separately, `Runner.RunBackground` settles the `*Handle` (store result, `close(done)`) **before** calling `notify`, so a callback that inspects the handle does not race it, recovers a panic into the error instead of taking the process down, and re-checks `runCtx.Err()` — because `Runner.Run` reports a cancelled context as a `TimedOut` result with a **nil error**, which is right for a chat turn that should still show partial output and wrong for a handle nobody is reading partials from.
- **Every spawning tool shares one gate, and `concurrency` is not a limit**: `parallel_subagent`, `chain_execution` and `delegate_subagent` all go through `spawnGate` and `childContext` (`internal/tools/subagent_limits.go`) — the guard was duplicated in `delegate_tool.go` only, and the other two had neither a width cap nor a depth increment, so one top-level call fanned out to an unbounded number of full ReAct loops with shell access, all at the caller's own depth and therefore outside the nesting budget `Runner.Run` enforces. Three things to keep straight. **`concurrency` bounds simultaneity, never total volume** — capping it does nothing about cost; only `MaxParallelTasks` (8) and `MaxChainSteps` (16) do, and both are checked before any subagent starts, because a limit that reports an error after the work has run has not limited anything. **The runtime gate must test `depth >= 1` *and* `role == RoleLeaf`, never role alone**: `RoleLeaf` is the zero value, so the top-level agent — which is not a subagent at all — also reads as leaf, and a gate on role alone refuses `parallel_subagent` for every ordinary turn. **And a subagent spawned with `Config{}` is a leaf**, so `depth >= 1` with no role set is correctly refused; a test that wants an allowed nested call must set `RoleOrchestrator` explicitly.
- **`config.Load` returns `Defaults()` with a *nil* error when the file is unreadable or unparseable**: it is deliberately lenient so joshbot still runs. Any caller that intends to `config.Save` back must use **`config.LoadStrict`** (or `LoadStrictFrom`), or a damaged config file is silently replaced by defaults — every provider, key and setting gone. Checking the error from `Load` does not help: there is no error. `joshbot auth github-copilot` shipped exactly that bug (#39), and a "fixed" version that still called `Load` was equally destructive. Distinguish "no config file yet" (safe to write) from "file present and unusable" (never write) with `os.Stat(config.ConfigPath())`.
- **A provider with no streaming endpoint returns `providers.ErrStreamingUnsupported`, never a bare error**: streaming is on by default and `internal/agent` picks `streamChat` whenever a sink is attached, so a plain error there kills every interactive turn on that provider. The ReAct loop falls back to `Chat` when `errors.Is(err, providers.ErrStreamingUnsupported)` matches — safe only because the stream never opened, so nothing has reached the sink. `github-copilot` is the only such provider today (`internal/copilot/provider.go`).
- **A synthesized reply generated *after* streaming must go through the stream sink, or every consumer drops it**: `reactLoop`'s max-iteration reply and `Process`'s timeout reply used to be returned as plain text with a nil error, and both the CLI (`progress.didStream()`) and the Telegram streamer (`Finish`'s `delivered && !broken && shown == buf`) decide "was the answer shown?" by "did anything stream this turn?" — so a turn that streamed narration then hit the limit delivered *nothing* (#283). Both replies are now emitted with `sink(StreamEvent{Delta: resp})` at their return sites. Do not reintroduce a plain-text return on a path that runs after the sink was created; if a new synthesized reply is added there, it must follow the same pattern. The general `"Error processing request: ..."` path is deliberately *not* covered (the error is reported out of band as a non-200/non-`stop` stream, so nothing to swallow) — it remains a documented follow-up.
- **A stream that dies before any content retries invisibly; one that dies mid-text keeps the marker**: `streamChat` returns the `errStreamDiedEmpty` sentinel (wrapped, so `errors.Is` matches) when the accumulator rejects a stream and `accumulatedContent` is still empty — nothing has reached the sink, so `reactLoop` retries once through `a.provider.Chat`, which brings the whole retry/fallback chain with it, and the reply arrives unstreamed (the `ErrStreamingUnsupported` delivery path, which every sink consumer already handles). The empty-content check is the whole safety argument: retrying after a delta has been emitted would duplicate text on screen, so the mid-text paths still append the visible `[stream error: ...]` marker and return the partial as a successful response. The old behaviour — marker even when nothing had streamed — existed to avoid the "I've processed your request." non-answer; the retry supersedes it, and the doubly-failed case now surfaces the real error via the in-band `ReplyPrefix` contract instead.
- **Telegram streaming state is per-turn and lives on `TelegramStreamer`** (`internal/channels/telegram_stream.go`), created in `runGateway` for each message and reached only through `agent.WithStreamSink` — the same rule as the tool-progress sink, and for the same reason: a field on `TelegramChannel` would let two chats generating at once be shown each other's text, which is the highest-priority test in `telegram_stream_test.go`. Four rules hold it together. **Interim edits go out as plain text and the configured parse mode — Markdown by default since the Telegram-UX pass, which is safe only because of this fallback — is applied only to the final edit** — a half-written code fence would otherwise fail every interim edit with `400 can't parse entities`; the final edit still falls back to plain text via `isParseEntityError` if it is rejected. **Edits are throttled** (3s minimum gap) and skipped when the text is unchanged, because an unchanged edit is a Telegram API error rather than a no-op. **On a 4096-byte rollover the buffer advances only after the head write lands**, and head and tail both come from `splitOnce` (`internal/channels/telegram.go`), the single-step form `splitMessage` itself loops over. Re-joining `splitMessage`'s later parts would carry the fences it added per part and compound a duplicated ``` on every lap; re-deriving the tail by trimming a closing fence off the head is worse, because that inference is not invertible — a part ending in a fence the model wrote is indistinguishable from one `splitOnce` closed, so a genuinely closed block at the split point got a spurious `` ``` `` prepended to the remainder and inverted fence parity for the rest of the answer. **And the bus publish is suppressed only when `Finish` reports the whole answer reached the chat** — `delivered && !broken && shown == buf`, mirroring the CLI's `didStream()` rule; keying it off the config flag instead loses the whole answer whenever the first send fails. The `shown == buf` term is the delivery contract: `Finish` returning true suppresses the fallback, so returning it because an earlier interim edit landed means one failed final edit silently destroys the reply, leaving only a WARN line. A partial stream plus a republished copy is duplication; a suppressed publish is loss. The inverse error is just as easy: `broken` is set only when nothing has ever been delivered, **never** on `s.msg == nil`, because a rollover clears `s.msg` while several complete messages are already on screen — gating there made a later failure declare the turn undelivered and the bus repeat everything. Because `Process` reports LLM failures in band as reply text with a nil error, `runGateway` passes `agentReplyError(response)` to `Finish` on the success path too, or a turn that streamed and then failed ends with partial text and no reason. A 429's `retry_after` must be recovered from the error *text* as well as from `telebot.FloodError.RetryAfter`: that struct embeds an unexported error (so it cannot be constructed outside telebot) and telebot populates the field only for descriptions in its static table. Heartbeat turns never stream. **Tool progress rides the same message slot**: `TelegramStreamer.Status` shows a best-effort progress line that the first content delta then edits away in place — it is skipped (never queued) inside the throttle window, refuses to write once `buf` is non-empty, must never set `delivered` (that means reply text landed, and `Finish`'s suppression contract depends on it), and `Finish` deletes a status message no reply ever replaced so the bus-fallback answer does not land under a stale "⚙️ ..." line.
- **Anything derived from the user's words and injected into the prompt must be labelled as derived, and never cut mid-word with an ellipsis.** `inferTopic` once produced `Current topic: ha! you son of a gun!  i'm actually wanting to do a new topi...` and the model answered that "cut-off message" instead of the real one. `session.ConversationSummary` now labels the line `Topic hint (auto-derived ..., not a message)`, `inferTopic` cuts on a word boundary (`topicMaxLen`) with no `...`, and the prompt states a tool result is the agent's own output. The live-eval probe `tool_result_is_not_user_input` covers the tool-result half.
- **The Stop button cancels the turn *directly* and is keyed by a per-turn token, not the session (#310).** `channels.StopCoordinator` (`internal/channels/telegram_stop.go`) owns the `stop` namespace; `gatewayHandler` wraps a streamed turn's context in `WithCancel` and `armStop` registers the cancel func, so a press on the poller goroutine calls it at once. Three rules. **It must never go through the bus or `LockSession`** — the turn being cancelled holds both, and a Stop queued behind it is a no-op until the turn ends on its own (and under `MaxConcurrentTurnsPerKey` it would be refused outright). **A token is honoured only while its turn runs and only from its chat** (`Release` on settle, `chatID` match on press); the token is a base-36 counter, so `callback_data` carries no sender or chat id. **A stopped turn is reported as `errTurnStopped` ("stopped by you") through `Finish`, or `stoppedReply` when nothing streamed** — never the raw `context canceled`, and `streamChat` skips its `[stream error: ...]` marker when `ctx.Err()` is `Canceled` so the chat does not show two failures for one press. The button is `TelegramStreamer.interimMarkup`: on every interim send/edit (status line included) and omitted from the final edit, which is what removes it; drafts cannot carry it.
- **The `/model` and `/personality` pickers reuse the command turn; a press is the presser's own session, and a switch never resets (#313).** `channels.Picker` (`internal/channels/telegram_picker.go`) owns the `model` and `persona` callback namespaces; the gateway attaches its `Keyboard` to a *bare* `/model`/`/personality` reply on Telegram only, and only when `agentReplyError` is nil (a picker under an error invites a press into the same failure). A press synthesizes an inbound `/model <spec>` with `SenderID: telegram_<presser>` and calls `agent.Process` — so it queues on the per-key session lock like a typed command, the payload is exactly an `agent.Choice.Spec` that `resolveModelSpec` accepts, and nothing a button can send bypasses the command's validation — then edits the picker message in place through `pickerTarget` (which carries the chat id: `Edit` reads both halves of `MessageSig`, unlike `React`). A spec whose envelope exceeds 64 bytes is left off the keyboard, never truncated, because a truncated envelope decodes as a *different valid* choice. The agent and channels packages do not import each other; `pickerBackend` in `cmd/joshbot` converts `agent.Choice` to `channels.PickerChoice`. And the keep-history decision is deliberate and stated in the switch reply: a one-tap button must not wipe the transcript.
- **A Telegram inline button is a routed action, not a synthetic user message** (`internal/channels/callback.go`): `handleCallback` decodes `callback_data` as a `namespace:action:payload` envelope and hands the registered `CallbackHandler` a typed `CallbackPress`; only data that fails to decode falls back to the legacy `[Callback: %s]` bus inbound. That fallback is the compatibility path, not the design -- re-typing a payload the code produced as user text spends a whole ReAct turn to re-derive it, and the model may decline. Four rules. The envelope is split with `SplitN(data, ":", 3)`, so **only the first two fields are structural** and a payload may contain `:` (a model id is `openrouter/z-ai/glm-5.2`). `Encode` **errors at build time** on the 64-byte `callback_data` cap rather than truncating, and returns `""` on failure: a truncated envelope decodes as a *different valid action*, so a caller ignoring the error must not be able to send anything. `DecodeCallback` trims a leading `\f` -- telebot prepends it to the data of a unique-endpoint button. And `RegisterCallback` refuses a duplicate namespace, because a silently-replaced handler routes another feature's buttons. `ctx.Bot().Respond(cb)` is called **before** the dispatch decision, so a slow handler does not leave the client's spinner turning. Related trap: `buildReplyMarkup` asserted `markup["inline_keyboard"].([][]map[string]any)`, a concrete Go type JSON-decoded metadata can never satisfy (`encoding/json` yields `[]any` of `[]any` of `map[string]any`) and which no in-process producer used either -- both keyboard branches were dead code returning an empty markup with no error. `normalizeKeyboardRows` accepts both shapes; in-process callers should pass a `*channels.Keyboard` instead.
- **A proactive reply resolves its recipient from the persisted chat-id map, and an id-less inbound must never clobber it**: cron and heartbeat inbounds carry no chat id, so `resolveChannelID` (`cmd/joshbot/main.go`) falls back to `BusMessageSender.GetChatID`, whose map survives restarts via `EnablePersistence` (`~/.joshbot/chat_ids.json`, 0600, atomic temp+rename). Two rules: `gatewayHandler` stores an inbound's chat id only when it is non-empty — a cron inbound used to overwrite the stored id with "" and erase exactly the recall its own reply depended on — and a live in-memory id beats a stale persisted one at load. A damaged file degrades to an empty map rather than failing gateway startup: the cost is no recall until the user speaks, which is the pre-persistence behaviour.
- **A non-`Always` skill's full content is reachable only through `skill_registry`'s `get` action, never `read_file`.** `Loader.LoadSummary` (`internal/skills/skills.go`) never carries a filesystem path for a skill in its XML summary, so telling the model to "use read_file to load full skill content" gave it an instruction with no way to satisfy it — and a **bundled** skill (5 of the 6 shipped skills, all `always: false`) has no real path at all: it ships embedded via `//go:embed` (`internal/skills/bundled.go`) and its `Path` is a virtual `bundled/<name>` string `read_file` cannot resolve. `Loader.LoadFullSkillContent` always worked correctly (it reads `Skill.content`, pre-populated at discovery for bundled skills, cached from disk for workspace ones) — it just was not wired to anything the model could call. `SkillRegistryTool.getSkill` (`internal/tools/skill_tool.go`) is that wiring, and it enforces the same trust boundary `LoadSummary` does: an unapproved workspace skill refuses to load by name, so `get` cannot be used to bypass `joshbot skills trust`.
- **`afterReActDetection`'s skill-extraction LLM call runs in its own goroutine with its own bounded context, never inline on the turn's context or on `context.Background()` unbounded.** It used to do both — call `a.extractor.Extract(context.Background(), ...)` synchronously, before `Process` returned the reply. That meant an ordinary tool-using turn (>=3 tool calls plus a word like "steps" in the answer is enough to cross `SkillDetector`'s confidence threshold) could hang the user-visible reply behind a *second* full LLM call that entirely ignored `agents.defaults.timeout` — up to the provider's own client timeout (300s for ollama). `extractAndCreateSkill` now runs via `go a.extractAndCreateSkill(...)` under `skillExtractionTimeout` (60s). A test asserting on the written `SKILL.md` must poll for it rather than checking immediately after `Process` returns (see `waitForGlob` in `coverage_wave2_test.go`) — that polling requirement is itself the proof the fix works, not a workaround for it.

## Provider Enabled Flag

Providers require `"enabled": true` in config to activate. This is a required boolean field:

```json
{
  "providers": {
    "nvidia": {
      "api_key": "nvapi-...",
      "enabled": true
    }
  }
}
```

Environment variables also set `enabled: true` automatically when a provider is configured via env var.

## Env Var Format

All config values can be overridden with `JOSHBOT_` prefix env vars using `__` as path separator:

```bash
# Canonical format (use provider routing key):
export JOSHBOT_PROVIDERS__OPENROUTER__API_KEY="sk-or-..."
export JOSHBOT_PROVIDERS__NVIDIA__API_KEY="nvapi-..."

# Model-centric format:
export JOSHBOT_MODELS_CONFIG__AGENT__MODEL="smart"
export JOSHBOT_MODELS_CONFIG__MODELS__0__NAME="fast"
export JOSHBOT_MODELS_CONFIG__MODELS__0__MODEL="groq/llama-3.3-70b-versatile"
export JOSHBOT_MODELS_CONFIG__MODELS__0__API_KEY="gsk_..."
```

Shorthand forms like `JOSHBOT_OPENROUTER_API_KEY` and `JOSHBOT_NVIDIA_API_KEY` are also accepted for backward compatibility.

## HARD RULE: documentation ships with the change

**A change that alters observable behaviour updates the docs in the same PR.** Not a
follow-up, not an issue. A change is not done until the docs match. See the table in
`CLAUDE.md` for which file covers what.

Non-negotiable parts:

- **Verify before writing.** Read the source — or run the command — for every documented
  command, flag, config key or behaviour. Config keys must match the `json:`/`mapstructure:`
  struct tags exactly.
- **No unverifiable numbers.** LOC, test counts, tool counts, binary sizes: measure them
  when you write them, or leave them out. A stale number reads as authoritative.
- **Removing a stale claim matters as much as adding a true one.** Drift runs both ways.
- **`site/index.html` and `site/architecture.html` are in scope.** They drift fastest
  because nothing fails when they are wrong.

This rule exists because the softer version did not work: `CLAUDE.md` already said the
site MUST stay in sync while the site sat eight releases out of date.

1. Push changes to main first
2. **WAIT** for CI to pass (green checkmark on the commit) — do not push the tag until CI is green
3. Only then cut the release tag with `git tag vX.Y.Z && git push origin vX.Y.Z`
4. Monitor both the CI workflow and the Release workflow until all jobs are green
