# joshbot — Architect's Guide

joshbot is a self-hosted Go personal AI assistant (~39.3K LOC non-test, 2,145 test functions across 241 test files in cmd+internal — measured 2026-08-14). Single binary, zero runtime deps.

**`AGENTS.md` (repo root) is the full agent guide** — key interfaces, code style, naming, concurrency and logging patterns, complete gotchas list. Read it before non-trivial work. This file is the quick index.

## Key facts

- **Go 1.25.9**, module `github.com/bigknoxy/joshbot`
- **~19MB binary** (darwin/arm64, measured 2026-08-10)
- **Architecture**: goroutine message bus → ReAct agent loop → multi-provider LLM
- **Channels**: CLI (readline) + Telegram (long-polling, telebot) + Discord (gateway websocket, discordgo)
- **Providers**: openrouter, openai, nvidia, groq, ollama, anthropic, poolside, azure, custom, litellm, github-copilot (device-flow auth via `joshbot auth github-copilot`)
- **Config**: `~/.joshbot/config.json`, env vars with `JOSHBOT_` prefix, two formats (legacy + model-centric)
- **Memory**: MEMORY.md (always in context) + HISTORY.md (appended event log) + fact extraction + consolidation
- **Skills**: SKILL.md files with YAML frontmatter, auto-discovered from workspace, progressive loading
- **Tools**: filesystem, shell (deny-listed), web (exa-cli/DuckDuckGo/MCP), message, skill_registry, memory_search, cron, send_file (outbound attachments)
- **Sessions**: JSONL files at `~/.joshbot/sessions/`, keyed `channel:senderID`
- **Cron**: Scheduled reminders via the `cron` tool (create/list/delete); jobs persisted as JSON at `workspace/cron/jobs.json` (see `internal/cron`)
- **Heartbeat**: Unchecked task scanner via HEARTBEAT.md

## Commands

No Makefile — standard Go tooling.

```bash
go build -o joshbot ./cmd/joshbot
go run ./cmd/joshbot agent -m "hello"        # single-message, non-interactive
go test ./...                                # all tests
go test -v ./internal/tools -run TestShell   # single test
go vet ./... && gofmt -l .                   # CI gates on both
./scripts/verify-local.sh                    # build + onboard + smoke-test heartbeat
```

## Layout

`cmd/joshbot` entrypoint. Under `internal/`: `agent` (ReAct loop), `bus` (message bus),
`channels` (channel.go = Channel interface, telegram.go, discord.go), `providers` (registry.go = provider routing keys),
`copilot` (github-copilot device-flow auth + provider), `tools`, `memory`, `skills` (+ `skills/bundled/` = the skills embedded in the binary)
(+ `skills/trust.go` = workspace-skill approval store), `session`, `context`, `config`,
`configure`, `cron`, `heartbeat`, `mcp` (stdio MCP client + server manager), `subagent`, `service` (build-tagged per-OS), `learning`,
`api` (OpenAI-compatible HTTP server behind `joshbot serve`),
`integration`, `log`, `redact` (credential and home-path stripping for logs and printed output).

## Important gotchas

- `internal/` is the source of truth. A stale `pkg/` duplicate of `bus` and `channels` was deleted in the 2026-08 audit sweep — if a doc or search result still points there, it is out of date.
- The interactive CLI is `runAgentLoop` in `cmd/joshbot/main.go`, not a `Channel` implementation. `internal/channels` holds only the `Channel` interface and the Telegram and Discord implementations; a dead `cli.go` that implemented it was deleted in v1.42.x after misleading a bug diagnosis.
- **Interactive TTY mode routes logs to stderr, never stdout.** The logger's default writer is `os.Stdout`; `runAgent` in `cmd/joshbot/main.go` redirects it to `os.Stderr` when `isTTY(os.Stdout)` is true, because the editor paints a full-screen view on stdout and any INFO/WARN landing there (Processing message, Message processed, tool execution, skills review) corrupts the prompt. JSON modes redirect in the same spot; only non-interactive `-m/--message` text keeps logs on stdout so tool output and logs share the operator's capture stream. Do not write to stdout from inside the interactive loop; use `log.Get()` (now on stderr) or a `cliProgress` callback.
- **The interactive editor's `render()` cursor math is `rows - cursorRow`, not `rows-1`.** After printing each row plus a trailing `\r\n`, the terminal cursor sits `rows` lines below the view's top; the cursor-up sequence must be `\x1b[<rows-cursorRow>A`. An off-by-one leaves the cursor on the line below the view, the next `hide()` cannot clear the prompt line, and every keystroke reprints a stale `● model ❯` line. `TestEditor_RenderCursorUpIsSingleRow` pins it.
- **A tool-progress line and the streamed answer are separated by a blank line.** `cliProgress.onStreamEvent` prepends `\n` when a `⏺ tool(...)`/`⎿ ok` line was shown this turn (`toolShown`), so the reply does not glue onto the trailing `⎿ ok`. `toolShown` is reset in `beginTurn` and cleared on the first delta. `TestCLIProgressStreamEventSeparatesFromToolLine` pins it.
- `agent.Agent` carries its tool-progress callback **per-request via the context** (`agent.WithSink`), not as a struct field — so concurrent `Process` calls (e.g. Telegram) never cross-deliver events. `runAgentLoop` wires it up only when stdout is a real TTY, to drive the interactive CLI's tool-call lines (`⏺ tool(args)` / `⎿ ok (1.2s)`) and "thinking..." spinner. Non-TTY detection is the `isTTY` package var in `cmd/joshbot/main.go` (type-asserts to `*os.File` + `github.com/mattn/go-isatty`), overridable in tests instead of probing a real terminal.
- A blocking read inside a `select` with `default:` makes shutdown unobservable; `signal.Notify` also disables default termination, so a one-shot signal handler leaves the process unkillable (issue #104).
- All CLI commands work non-interactively (agent -m, onboard --force, configure --provider --api-key, uninstall --force, etc.)
- ExtraBody support for providers needing custom JSON body fields (poolside chat_template_kwargs, etc.)
- Model names are routed by prefix and the prefix is stripped before sending — except for providers listed in `prefixesPartOfModelID` (`internal/config/config.go`), where the prefix is part of the real model ID. Poolside is the only one today: `poolside/laguna-s-2.1` must be sent whole, or the API answers 404.
- **A model ID belongs to one provider, and the fallback chain must respect that.** `MultiProvider.resolveModel` (`internal/providers/multiprovider.go`) honours the requested model only for the provider the request was *addressed to*; every fallback is asked for its own `entry.Model`. Forwarding it verbatim was a live bug and it looked exactly like the `StripProviderPrefix` bug above: a 429 on nvidia for `z-ai/glm-5.2` fell through to poolside as `z-ai/glm-5.2`, which answers `404 {"error":"please check the model you provided"}` — and since 404 is not a fallback-worthy status, that 404 was returned as *the* failure, hiding the rate limit and blaming a provider the user never chose. Two rules keep it fixed: `screenForImages` resolves models the same way (it decides vision capability per candidate, so a stale model there silently drops the wrong providers), and a non-fallback error from a *fallback* provider no longer short-circuits the chain — only the addressed provider's does. The aggregate error names every provider and its error, because "the last provider's 404" is the least informative thing that happened.
- **Transient provider failures retry in place before the chain moves, and the retry default lives in the wiring, not the library**: `MultiProvider.tryWithRetry` (`internal/providers/multiprovider.go`) retries fallback-class errors (429/5xx/network) on the same provider with jittered exponential backoff, honouring an upstream `Retry-After` carried on `providers.FallbackError.RetryAfter` (parsed from the header in `LiteLLMProvider.parseError`). A `Retry-After` longer than `maxInTurnWait` (20s) is not waited for: the provider is cooled down for that span and the chain moves on now. The cooldown table (`internal/providers/health.go`) *deprioritizes* a failing provider — moved to the end of `getFallbackChain`, never dropped — so a wrong guess costs latency, not availability; any success resets it, and the in-chat `/status` shows it (type-asserted `HealthSnapshot`, optional like `session.Archiver`). Three traps. **A bare `MultiProvider` retries nothing**: `Register` leaves `MaxRetries` 0 and `registerProviders` in `cmd/joshbot` raises every provider to `providers.DefaultMaxRetries` (2) before applying `providers.<name>.max_retries` overrides — a test asserting call counts, or a library caller, is not retried unless it calls `SetMaxRetries`. **`max_retries` is a `*int`**, because an explicit 0 ("fail over immediately") must be distinguishable from absent (default 2); `Validate` bounds it 0–10. And the time source and sleep are injectable fields (`mp.now`, `mp.sleep`) — tests fake them (`installFastClock` in `health_test.go`) instead of sleeping.
- **The fallback notice rides the reply text, and on the streaming path the buffer and the reply must stay identical**: `providers.WithFallbackNotice` (`internal/providers/notice.go`) carries a per-request callback the way `agent.WithSink` does; `MultiProvider` fires it only when a provider other than the addressed one answers, with the addressed provider's error class as the reason (`"cooldown"` when it was never dialled). The agent prepends `formatFallbackNotice` to the reply rather than sending it out of band, so every channel carries it with no per-channel wiring; `agents.defaults.quiet_fallback` (bool, deliberately inverted so the zero value shows notices — a default-true bool would need a schema migration, the streaming v4→v5 trap) suppresses it. **The notice is captured once per turn, not once per LLM call** (`turnStream`, a stack value in `reactLoop` — never an `Agent` field, for the same reason the sink rides the context): a turn that calls a tool makes two or more LLM calls, and a per-call notice reached Telegram twice at the top of a reply and a third time glued mid-sentence onto the narration before the tool call (#339). Three rules. On the streaming path the notice is emitted **lazily, right before the first content delta of the turn** — eagerly it would surface for a tool-call-only response that shows no text — and `reactLoop` prepends the same notice to the *final* reply, so the session and every non-streaming consumer record what the user saw. **A tool-call iteration's stored message never carries it**: the model would read its own earlier reply as opening with a warning and echo it. And `streamChat` inserts a `\n\n` separator delta (sink only, not content) before a later iteration's first delta when the earlier narration did not end its line, so "Let me check that." and the answer are not one glued sentence on any channel. The same rule covers the replies the loop synthesizes itself: `narrationSeparator` (#347) puts the `\n\n` ahead of the timeout and max-iteration text on the sink only, deciding from the turn's last assistant message in the session (`sess.Messages[startSessionLen:]` in `Process`, `turnMessages` via `compactionState.turnStart` in `reactLoop`) because `turnStream` is a `reactLoop` local the timeout path in `Process` cannot see; it emits nothing with streaming off, when no delta could have preceded it. And **the full notice is once per outage, not once per turn (#348)**: the turn's callback compares `fallbackNoticeKey(n)` (addressed provider, plus `|retired` for 404/410) against `session.Session.FallbackNoticed` through `sameOutage` — a `cooldown` continues whatever outage is recorded for that provider, since it is the chain declining to dial a provider that already failed — and emits `formatFallbackMarker` (`↪ answered by X (model)`) instead of the full text when it matches. A deferred func in `reactLoop` records the key on the session when a notice fired and clears it when the turn had no notice **and** some LLM call succeeded (`turnStream.answered`); a turn where nothing answered leaves the key alone. `FallbackNoticed` rides the `.meta.json` sidecar with `omitempty`, counts as sidecar presence in `Save`, and is cleared by `ResetConversation`. A retired-model notice also carries the model picker on Telegram: `agent.WithFallbackObserver` fires with the notice **only when it is shown in full** (so the picker appears once per outage), `Picker.NoticeKeyboard` gates on `FallbackNotice.ModelRetired()`, and the gateway hands it to `TelegramStreamer.SetFinalMarkup` — the final edit swaps the interim Stop button for the picker, and a final markup forces the final edit even when the text is already shown, or the keyboard never appears — or to the bus reply's `reply_markup`. The observer is read after `Process` returns under a mutex, because the provider may fire it from another goroutine.
- **Telegram formatting is authored as Markdown and sent as HTML, and the plain-text fallback must send the *pre-conversion* source (#315).** `MarkdownToHTML` (`internal/channels/telegram_html.go`) runs at the wire in all three outbound paths -- `telegram.go`'s per-part text send, `telegram_attachment.go`'s caption, and `telegram_stream.go`'s `writeLocked` final edit -- flipping `ParseMode` from `Markdown` to `HTML`. Legacy Markdown rejects ordinary LLM prose with `400 can't parse entities` and the recovery then strips formatting off the whole answer; HTML escapes three characters where MarkdownV2 escapes eighteen. Four rules. **The fallback sends the Markdown source, not the HTML** (`plain`, `plainCaption`, `s.buf`): an HTML body delivered with no parse mode renders its entity references literally, so the reader sees `&amp;` where the model wrote `&`; `TestSendAttachments_CaptionFallbackSendsThePreConversionSource` pins it. **Splitting happens on the Markdown**, with the existing fence-aware `splitMessage`/`splitOnce`, so no tag can straddle a part boundary. **`TelegramStreamer.buf`/`shown` stay the Markdown source** -- only the bytes on the wire change -- so `Finish`'s `delivered && !broken && shown == buf` suppression contract is untouched. And **the 4096 limit is measured after entities parsing**, not in bytes: conversion adds bytes (`<pre>` vs ```` ``` ````, `&amp;` vs `&`) while only ever shrinking rendered length, so a raw payload over 4096 is still legal -- a test asserting `len(text)` there is asserting the wrong thing, which is why the rollover test measures `renderedLen`. The converter treats an unterminated marker as literal text (no shorter marker may claim it), never parses inside code spans or fences, and allowlists link schemes to `http`/`https`/`tg`.
- **`channels.telegram.api_url` raises an outbound cap only, and the cap is a memory bound (#280).** The key points the channel at a self-hosted `telegram-bot-api` server; empty means `api.telegram.org`. Four things. It is validated as an `http`/`https` URL with a host and a failure returns `fatalConfigError` — an ordinary validation error makes `config.Load` log "Config unusable, using defaults" and substitute `Defaults()`, discarding every provider, key and allowlist, which is the same trap `validateTimeout` sits in. There is **one** limits rule, `channels.TelegramAttachmentLimitsFor`, read by `TelegramChannel.AttachmentLimits` and — through `outboundAttachmentLimits` in `cmd/joshbot` and `tools.WithAttachmentLimits` — by `SendFileTool`; a second copy drifts and the symptom is `send_file` refusing a send the transport would have accepted. The raise is gated on `channels.telegram.enabled`, because an `api_url` in a config with Telegram off would otherwise raise the tool's cap toward a transport that never runs. And `LocalAPIDocumentMaxBytes` is 50 MiB, not the local server's 2 GB, because the payload is held in memory from the tool call until the upload finishes — raising it raises peak heap per turn, and #305 tracks the fd-carrying rework that would make a bigger number safe. Inbound limits (`providers.MaxImageBytes`, `providers.MaxDocumentBytes`) are deliberately untouched: they bound what a model is billed to read.
- **`channels.telegram.reactions` acknowledges on the *user's own* message, and three details decide whether the ack ever appears (#314).** `setMessageReaction` (Bot API 7.0) **sets** rather than appends, so 👍 replaces 👀 with no clearing call — do not add one. The completion emoji is 👍 and **not** ✅: ✅ is premium-only in Telegram's free reaction set and is rejected with `REACTION_INVALID`, so the ack silently never appears; `TestReactionEmojiAreInTheFreeSet` pins both emoji against the documented list. The gate is **opt-in with `omitempty`** for the `api.webui` reason — a `Config` bool without it is written into every saved config and its default can then never be flipped without a schema migration (the `streaming` v4→v5 trap) — and it is opt-in at all because a bot in a group lacking the reaction permission would log a failure on every single turn. `telebot.Bot.React` reads only the id half of `MessageSig()` (the chat comes from the recipient), so the target is a dedicated `ackTarget int` Editable: a bare `&telebot.Message{ID: n}` nil-dereferences its `Chat` inside `MessageSig`. The reaction fires from a goroutine off the reply path and its failure is logged at debug — a reaction is an ornament on the turn, never part of it — and it is **outbound only**, so no `allowed_updates`/`message_reaction` subscription is involved.
- **`channels.telegram.stream_drafts` streams through `sendMessageDraft`, and a draft is not a delivery (#308, #309).** With it on, `TelegramStreamer` pushes each delta into an ephemeral draft slot (`internal/channels/telegram_draft.go`) instead of the send/edit loop, and `Thinking()` shows an empty-text draft as Telegram's own "Thinking…" placeholder before the first token. Five things. **A draft write must never set `delivered`** — the reference calls a draft "a temporary 30-second preview" and requires an ordinary `sendMessage` to persist the text, so `Finish`'s `delivered && !broken && shown == buf` suppression rule stays about what actually reached the chat, and the persisting send still runs every turn; setting it there loses the whole reply on a turn that only drafted. **The first API refusal disables drafts for that turn and falls through to the edit loop on the same delta**, without setting `broken`: telebot v3.3.8 has no wrapper for the method so the call goes through `Bot.Raw` (which turns `{"ok":false}` into an error), and a Bot API server older than **10.0** — the version that allowed empty text, changelog dated 8 May 2026, *not* the 9.3/9.5 issue #308 claims — must cost the animation and not the answer. **It is private-chat only**: `privateChatID` requires a positive numeric id, because the reference documents `chat_id` as the target private chat and a group would spend a request per delta to earn an error per delta. **`draft_id` must be non-zero and is one per turn** (a package-level `atomic.Int64` whose `Add` starts at 1), since clients animate changes to drafts sharing an id — one id per turn is what makes the growing answer a single animated slot. And **`draftTail` cuts on a rune boundary**, not at byte 4096: a slice through a multi-byte rune is invalid UTF-8 and Telegram rejects the whole request. Note a test for that is only meaningful with **3-byte** runes — with 2-byte runes the cut parity can never land mid-rune, so the mutation stays green.
- Providers need `"enabled": true` in config to activate — omitting it silently disables them.
- Env var nesting uses `__`: `JOSHBOT_PROVIDERS__OPENROUTER__API_KEY`. Shorthand `JOSHBOT_OPENROUTER_API_KEY` still works.
- Session key is computed from `Channel:SenderID` — there is no `SessionKey` field.
- `internal/service/` is build-tagged (`factory_linux.go` / `factory_darwin.go` / `factory_other.go`) — all must export the same signature.
- A Telegram send with a parse mode set fails with `400 can't parse entities` on malformed Markdown/HTML, which is routine in LLM output. `isRetryable` does not cover it, so `Send` retries that part once with `ParseMode` cleared (`isParseEntityError`). Match narrowly on the description text; matching bare `400` would downgrade `chat not found` to plain text and hide real failures.
- Telegram hard-fails over 4096 chars; `Send` splits longer content via `splitMessage` (code-fence aware, byte-indexed).
- Telegram clears a chat action after 5 seconds, so "typing…" needs a keep-alive: `startTyping`/`stopTyping` run one goroutine per chat re-sending every 4s, stopped by `Send` or by `stopCh`. **The slash-command table is `internal/commands.All`** and everything renders from it: the agent's `/help` and `/start`, Telegram's `botCommands` menu and unknown-command reply, Discord's list, the CLI's Tab completion. Every channel forwards every command to the agent and **none answers one locally** — a local help text drifted from the agent's three ways, and a local "Starting new session…" ack made `/new` answer twice. Adding a command is one table entry plus a `case` in `handleCommand`; `TestCLICommandNamesAllHaveHandlers` catches a table entry with no case. The menu is **scoped to the allowlist** (#316): a `BotCommandScopeChat` menu per numeric `allow_from` entry, with the global all-private-chats menu deleted so a stranger sees nothing; a username-shaped entry keeps the global menu, since it cannot be resolved to a chat id until that user speaks, and an empty allowlist (which denies everyone) deletes it. **`SetCommands` cannot clear a scope** — telebot's `CommandParams.Commands` carries `json:"commands,omitempty"`, so an empty slice omits the field and the Bot API rejects it; clearing is `DeleteCommands`, which is why `telegramNotifier` declares both. A per-chat scope for an allowlisted user who never started the bot answers "chat not found", so the loop logs and continues and returns only the first error.
- Shell commands — and MCP server processes — run with an allowlisted environment (`internal/childenv`; `internal/tools/shell_env.go` keeps thin aliases), not the full parent env — no provider API keys, and anything credential-shaped by name (TOKEN, SECRET, API_KEY, etc.) is stripped even if otherwise allowlisted. A workflow relying on `GH_TOKEN`/`GITHUB_TOKEN` as an env var will not see it; use `gh auth login`'s on-disk config instead.
- `tools.shell_sandbox` (`"off"` default, `"workspace"`) applies OS-level containment per platform: **Linux** = Landlock via a re-exec helper (`__sandbox-exec`); **macOS** = Seatbelt via `/usr/bin/sandbox-exec` (deny-by-default SBPL profile, no re-exec helper); **other** = none, so enabling is a startup error. `tools.shell_sandbox_allow_network` (off by default) gates outbound TCP when sandboxed. On platforms with no sandbox available, the shell tool defaults to allowlist-only when `tools.shell_allow_list` is unset, since the deny list alone is bypassable. Each platform's implementation is in `internal/tools/sandbox_<os>.go`.
- **`tools.shell_approval` gates shell commands behind a human `y`** (`"off"` default, `"interactive"`, `"always"`). `ShellTool` holds only the mode; the `Approver` rides the request context (`tools.WithApprover`), like `agent.WithSink`, so concurrent Telegram turns cannot cross-deliver prompts. It fails closed structurally: `ApproverFromContext` returns `DenyAll` rather than nil when none is installed, and `Deny` is the zero `Decision` — so cron, the heartbeat, the gateway and piped `agent -m` are **denied immediately, never blocked**. `ExecuteAsync` is gated too (`async=true` would otherwise be a bypass), the gate runs *after* the deny list and allowlist so refused commands never prompt, and an unknown config value is a startup error. Two installers exist: `runAgentLoop` (terminal prompt, only when `isTTY(output)`) and the gateway (`gatewayDeps.approverFor` → `channels.ShellApprovalCoordinator`, #311), which asks in the Telegram chat with an inline keyboard — but only for turns whose inbound message carries its own chat id, so cron/heartbeat turns stay denied.
- The shell allowlist screens the **whole** command, not the first word: while an allowlist is in force, anything containing a separator (`;`, `&`, `|`, newline, `\r`, backtick, `$(`, `<(`, `>(`, `$'`) **or a redirection** (`>`, `<` — matched as substrings, so `>>`, `2>`, `&>`, `<<`, `<>` are covered) is refused. `defaultUnsandboxedAllowlist` (`internal/tools/shell.go`) contains only binaries that cannot themselves execute a second program: `find`, `go`, `git`, `rg` and `sort` are all excluded (`rg --pre PROGRAM`, `sort --compress-program=PROGRAM`). Adding an entry means meeting that criterion, not screening its flags.
- **The filesystem tool opens every path through `internal/tools/openat.go`**, never through bare `os.ReadFile`/`os.MkdirAll`/`O_NOFOLLOW`. `O_NOFOLLOW` constrains only the last component, so a symlink swapped in at an intermediate one (`ws/sub` → `/outside`) redirected writes and reads outside the workspace. The helper wraps Go 1.24's `os.Root`, resolving each component with `openat(2)` from a root chosen by `containmentRoot`. A new filesystem operation goes through `safeReadFile`/`safeWriteFile`/`readDirIn`/`mkdirAllIn` or it is a hole.
- Workspace skills (anything under `workspace/skills/`, as opposed to the bundled set embedded in the binary from `internal/skills/bundled/`) are inert until an operator runs `joshbot skills trust <name>`; trust is bound to a SHA-256 of the **whole skill directory tree** (all files' relative paths + content, sorted) stored in `~/.joshbot/skills.trust`, so editing, adding, or removing any file in a trusted skill dir — including a sibling script — revokes it. A legacy SKILL.md-only digest from an older joshbot no longer matches and safely revokes rather than crashing. `Loader.Create` (used by the skill_registry tool) writes but never approves. A workspace skill that reuses a bundled skill's name replaces it in the registry and is withheld until trusted — it does not silently "take over" the bundled behavior.
- The `cron` tool takes **durations** (`30m`, `2h`, `1d`, `1h30m`), never 5-field cron expressions — `internal/cron` only knows `delay:<d>` and `every:<d>`. It is registered only when a `cron.Service` is passed via `tools.WithCronService`, so the agent is never offered a scheduler that is not running.
- A one-shot cron job's countdown **survives a restart**: `AddJob` stores an absolute `Job.DueAt` (`due_at` in `jobs.json`), so a persisted `delay:30m` fires at the moment it was originally due, and an already-overdue job fires shortly after start instead of being dropped. Legacy jobs with no `due_at` are backfilled as due one duration from load (the old behaviour). Recurring jobs run until deleted; one-shot jobs delete themselves once they fire.
- **A turn is serialised per session key, and `handleResumeCommand` must call the unexported `a.process`**: a turn is a read-modify-write over one session file — `GetOrCreate` loads it, the ReAct loop appends, `Save` rewrites the whole thing. `Manager.mu` guards each Load or Save individually but is released between them, so two overlapping turns for one key both loaded the same prefix and the later save published a file missing the other turn's messages entirely (#236); it is reachable by default through the HTTP API, where two requests carrying the same `user` land on one session. `Agent.Process` now acquires `session.Manager.LockSession` for the whole span. Four things hold it together. `SessionLocker` is an **optional interface checked by type assertion**, like `session.Archiver`, so test doubles and alternative `SessionManager` implementations are not forced to implement it. The lock is acquired **after** the timeout context is built, so a turn queued behind a long one waits against its own deadline and reports a timeout instead of hanging — which is also why `keyLock` is a capacity-1 channel and not a `sync.Mutex`, whose wait cannot be cancelled. `Process` is split into a locking wrapper and an unexported `process` body **because `handleResumeCommand` re-enters the loop**; routing `/resume` back through `Process` deadlocks on a lock that goroutine already holds, and the symptom is a hang, not a failure. And the lock map is **reference counted and deleted when idle**, including on the cancelled-waiter path — session ids on the API surface come from the client's `user` field, an unbounded key space, so an entry outliving its last holder is a memory leak any authenticated caller can grow. The lock is process-local: two joshbot processes sharing one sessions directory can still interleave, which is the pre-existing state and is documented rather than fixed. One consequence lives outside the package: `bus.MaxConcurrentHandlers` is acquired on the **dispatcher** goroutine before the handler is spawned (`internal/bus/bus.go`), so a queued turn now holds its semaphore slot for `wait + turn` rather than just `turn`. That is the open loop #245 closed: because the slot is held across the key-lock wait, a flood on one session key -- every overlapping turn for that key parking on the one held token -- could once hold an unbounded number of dispatch slots and stall dispatch for every *other* user, bounded in practice only by `agents.defaults.timeout`. The per-key cap stops it. `acquire` (`internal/session/keylock.go`) gates the running per-key ref count under the same mutex that guards the token (`MaxConcurrentTurnsPerKey`, 8), so once the cap-th holds the token every later overflow turn for that key returns `ErrKeyLockBusy` at once -- no ref, no wait -- instead of parking. `Agent.Process` maps that to an in-band backpressure reply via `ReplyPrefix` ("too many turns in flight"), so a non-interactive caller still translates it out of the band the way it does every Process failure: `agent -m` exits 1 and the HTTP API answers 502, because a turn that did not run is a failure, not an answer; a `context.Canceled`/deadline on the gate is reported as a timeout, not a busy rejection. `TestLockSessionRejectsOverflowPerKey` pins the exact admission math (`busy == num - (MaxConcurrentTurnsPerKey - 1)`), which is red before the cap and green after.
- **`/new` is the one turn routed *ahead* of the per-key lock, and a `generation` fence is what makes that safe (#319).** A reset that queues behind the stuck turn the user is trying to escape is not a reset — and under `MaxConcurrentTurnsPerKey` it is not merely slow, it is refused outright with `ErrKeyLockBusy`. So `agent.Process` checks `isResetCommand` right after building the timeout context and calls `a.process` directly, bypassing `LockSession`. That bypass is only sound because `session.Session.Generation` fences it: `Manager.ResetConversation` clears the transcript and bumps the generation, and `Manager.Save` refuses any write whose generation is older than the sidecar on disk (`ErrSessionSuperseded`), so the concurrent turn that loaded its prefix before the reset cannot republish it. Five traps. **`Save`'s sidecar-presence condition must count `Generation > 0` as presence** — a reset clears every other metadata field, so the existing `else` branch would `os.Remove` the sidecar and erase the fence, and the very turn the reset was racing would then write its transcript back. **`readGenerationLocked` fails *open***: an unreadable or unparseable sidecar reads as generation 0, because this gate exists to drop a stale write and refusing every write over a momentarily unreadable sidecar loses live conversation to protect a reset that may never have happened. **Both `Save` call sites in `agent.process` must treat `ErrSessionSuperseded` as success** and log at debug — surfacing it turns the fence working into an error the user sees. **`SessionResetter` is optional, checked by type assertion**, exactly like `SessionLocker`, so a test double or an alternative `SessionManager` is not forced to implement it; a store that does not keeps the old clear-in-place-under-the-lock behaviour. And **the archive-based `Manager.Reset` in `internal/session/inventory.go` is a different method with the same exposure** — it deleted the sidecar outright, so it now calls `bumpGenerationLocked` instead; my clearing reset is named `ResetConversation` precisely because that name was taken. Note the filed issue's premise was wrong: the lock already covered `/new`, and Telegram's `handleNew` does no local clearing (it publishes to the bus with `is_command: true`), so the paths could not drift. `Generation` carries `omitempty` and is zero for a never-reset session, so no schema migration is needed.
- **`session.Manager.Load` reads the `.meta.json` sidecar even when the session has no messages**: it used to return early on an empty message list, before touching the sidecar, so a checkpoint, model override or personality set on a session with no transcript yet was silently dropped on the next load. Command turns are not appended to the transcript, so `/model` or `/personality` as the very first thing a user does hit exactly that case.
- Session files are written through `writeFileAtomic` (`internal/session/manager.go`) at mode `0600` — never `os.WriteFile` to a fixed `<path>.tmp`. The temp name must be unique per writer (`os.CreateTemp`), because the gateway and a concurrent `agent -m` share `~/.joshbot/sessions` and the `sync.RWMutex` only guards one process. `Load` is deliberately lenient: unparseable lines are skipped, not fatal, and the original file is copied to `<session-id>.jsonl.corrupt`. Do not "fix" that back into a hard error — there is one session per `channel:senderID` and no CLI to delete one, so a fatal parse means that user is permanently broken.
- **A compaction record is stored in the session and must stay singular**: once the history crosses `agents.defaults.compaction_threshold`, `checkAndCompactContext` summarizes it and `applyCompaction` replaces the summarized prefix with one `session.Message` carrying `Compaction: true`, always at index 0. Three rules keep it correct. The write-back happens **after** `reactLoop` returns, not inside it, because `Process` slices `sess.Messages[startSessionLen:]` for the history log and shrinking the session first would slice out of range. `buildMessages` holds the record out of the memory-window truncation — letting the window slide over it silently discards the whole earlier conversation. And the replaced messages are appended to `<session-id>.history.jsonl` via the optional `session.Archiver` interface before they leave the live session; if that append fails the compaction is abandoned, since recomputing a summary is cheaper than destroying history. Note `checkAndCompactContext` runs only **after tool execution** inside the ReAct loop, so a turn that answers without calling a tool never compacts at all — a test scripted without tool calls exercises nothing. Three more rules from #346, where every one of these was violated at once. **The live turn is never summarized**: `compactionPrefixLen` ends the prefix `compactionKeepTail` (6) messages *before* `compactionState.turnStart` — the index of this turn's user message, set in `Process` — backed up over any tool result so the kept tail never opens with one; the tail itself is taken from the request slice, not rebuilt from the session, so the turn's image and document bytes survive. The tail is **anchored to the turn start, not the end of the session**, because the turn grows with every tool iteration and an end-anchored boundary would move on every pass and defeat the "already compacted this exact prefix" check — and a prefix under a quarter of the threshold is skipped outright, since the excess is then in the tail and summarizing the prefix recovers nothing. **`context.Registry` must not default an unknown model to 4096**: every current hosted model is unknown to it, `ComputeBudget` then went negative against the 8192 `max_tokens` default and was clamped to 256 tokens, and compaction fired at ~700 chars of history; the default is now `DefaultContextWindow` (131072) and an over-reserved window falls back to a quarter of itself. And **`Compressor.CompressMessages` asks the provider to summarize the whole conversation whenever it has one** — it used to do so only above 50 messages, and its other provider path summarized a join already cut to the budget, so at a small budget the "summary" was one message. **A cheap, no-LLM-call tier runs ahead of the compressor call, and it is checked *after* the `st.active`/`prefixLen` re-entrancy guard, not before**: `maskStaleToolOutput` truncates old tool/assistant content (the transform `applyObservationMasking` already applied for `buildMessages`, factored out as `maskOldToolAndAssistantContent` so the two share one rule instead of drifting) over exactly the region `compactionPrefixLen` would otherwise summarize, and only falls through to the compressor when trimming alone does not get back under the threshold budget. It is checked after the re-entrancy guard, not before, because once a prefix is already compacted this turn `messages` no longer holds the old content for masking to find — trying first only spends an allocation to learn what the guard already knows for free. `protectTail` is measured against `sess.Messages`, not `messages`, on the same "the two grow in step from turn start" assumption the tail extraction below it relies on; if `messages` is ever shorter (an earlier memory-window truncation, or a compaction already folded into `messages` this turn) masking has nothing left outside the protected tail and fails closed rather than guessing. And the INFO-level "Compacting context" log line only fires once masking has already failed — it is the signal that an LLM summarization call is about to happen, and logging it unconditionally would make every masked-only turn look like one.
- **Everything joshbot prints or logs is redacted; session files are not**: `internal/redact` wraps the log writer (`internal/log/logger.go`) and `joshbot status`, so a credential appearing in a tool result never reaches the log. Session JSONL is deliberately exempt — rewriting content on save would mangle legitimate text and add a second corruption path, so data at rest relies on the `0600` mode instead; `TestSessionContentIsStoredVerbatim` pins that boundary, and `internal/redact` documents it. Three traps if you extend the patterns. **The scheme is kept and the token is redacted, never the reverse**: an `Authorization` value is `<scheme> <credential>`, and an earlier version recognised only `Bearer|Basic`, so GitHub's own `Authorization: Token <secret>` fell through to the assignment rule, which blanked the word `Token` and published the credential after it. Both the header rule and the assignment rule now capture an optional leading scheme word and preserve it. **A name fragment must end the identifier**, apart from a plural `s` and separator-led segments (`SECRET_KEY_ID`): matching it as a bare substring rewrote `Author:`, `unauthorized:` and `secretariat:`, all routine tool output. That is also why `AUTH` is in `redact.SecretNameFragments` — which widens the shell-environment screen in `internal/tools`, sharing the list on purpose — but is excluded from the assignment rule by `assignmentFragments()`. **And the cheap gate in front of each regex must never be narrower than the regex itself** — gating on the underscored `api_key` spelling silently let `api-key: <secret>` through. All-numeric values are exempt on purpose — `Max tokens: 8192` in `joshbot status` matches TOKEN plus a plural `s`, and no detected key class is bare digits. The assignment gate is a hand-written walk (`hasAssignmentCandidate`) rather than a substring test, because Go's regexp costs ~650ms per megabyte on a case-insensitive alternation and `token`/`key`/`secret` appear constantly in ordinary prose without being assignments; the walk mirrors the regex's name part exactly, so widening one means widening the other.
- **`joshbot sessions` is not a resume feature, and `.jsonl` alone does not identify a session**: sessions are keyed `channel:senderID` and loaded on every inbound message, so there is one per user per channel and nothing to select; the subcommands exist to inspect and clear. Two traps live here. `internal/session` now owns sidecars that also end in `.jsonl` — `.history.jsonl` (compaction archive) and `.jsonl.archive-<ns>` (reset) — so anything enumerating the sessions directory must go through `isSessionFile`, never a bare `strings.HasSuffix(name, ".jsonl")`; the compaction archive was reported as a phantom session named `<id>.history` until that was centralised. And urfave/cli v2 **stops flag parsing at the first positional argument**, so a flag written after an id is silently dropped — `prune <id> --force` declined without deleting, and `show <id> --last 2` printed the whole transcript. `parseSessionArgs` in `cmd/joshbot/sessions_cmd.go` reads those trailing flags — all three of them, including `--older-than`, whose omission made `prune <id> --older-than 30d` report an unknown flag; any new subcommand taking both an argument and a flag needs the same treatment. A third trap: an `Info` for a session that would not scan must carry the file's real mtime, because `PruneOlderThan` compares `UpdatedAt` and a zero time reads as infinitely old — a transient read error was enough to make `--older-than` delete a session of any age. Session IDs are attacker-influenced (the sender half comes from Telegram), so `ValidateSessionID` gates every path-building entry point.
- **`osKeyReader.peekByte` must leave the byte in `pending`**: it is a peek, and every caller (`readEscape`, `readCSI`) consumes it explicitly with `readByte`. The fresh-read path used to pop it while the buffered path did not, so `readCSI`'s "consume `[`" ate the sequence's final byte and every arrow key blocked until the next keystroke. A test for the CSI decoder hangs rather than failing when this regresses, so bound it with a timeout.
- **`go run` is detected by the go-build cache, never by `/tmp`**: `runningFromGoRun` in `cmd/joshbot/main.go` is the single source for this. Three call sites — `update`, `uninstall` and `detectRunningContext` — each carried their own `strings.Contains(exePath, "/tmp/")`, which is not a property of `go run` at all: it made a joshbot installed anywhere under `/tmp` permanently unable to update or uninstall itself, and reported the cause as `go run`. A guard like this fixed in one place is not fixed; grep for the other copies.
- **The bundled skills are embedded in the binary, not read from disk**: `internal/skills/bundled/` is pulled in with `//go:embed` (`internal/skills/bundled.go`). It used to be the repo-root `skills/` directory found via the *relative* path `filepath.Join("skills")`, which resolves against the process working directory — so the bundled set loaded only when joshbot was run from a checkout of its own source tree, and every real installation reported "No skills found" while `trust.go` claimed they "arrive with the binary". Consequences to keep in mind: a bundled skill's `Path` is now an embed path, not a filesystem path, so its content is cached at discovery and `Delete` refuses it; `Loader.bundledDir` is empty in production and exists only so tests can substitute a fixture directory; and adding a skill means adding a directory under `internal/skills/bundled/`, which requires a rebuild to take effect.
- **`agent.Process` reports LLM failures in band, so every non-interactive caller must translate them back**: it returns `"Error processing request: ..."` as reply *text* with a nil error, because a chat channel has to show the user something. `agent -m` exited 0 over a completely unreachable provider until `agentReplyError` (`cmd/joshbot/main.go`) turned that prefix back into an error — text mode exits 1, JSON mode sets `"is_error": true` on the result document and writes a `{"type":"error",...}` document to stderr. Any new non-interactive entry point calling `Process` needs the same translation; treating the string as a normal answer is the bug. The rule runs both ways: a **new failure path inside `Process` must use `agent.ReplyPrefix`**, not a prefix of its own. The session-lock acquisition returned `"Error: Failed to load session: ..."`, which `ReplyError` does not match, so a turn that gave up waiting reached the HTTP API as a 200 whose answer was an error string and `agent -m` as exit 0.
- **`providers.ListModels` refuses an empty `APIBase` instead of defaulting to OpenRouter**: the old fallback to `https://openrouter.ai/api/v1` meant credential validation for *any* other or unknown provider dialled openrouter.ai and printed "✓ validated". It now errors, which is what lets `configure.ValidateProviderCredentials` report "could not verify ... no API base URL configured" for the providers with no fixed endpoint (azure, custom, litellm). Do not reintroduce the default.
- **Credential validation is a one-token chat completion, never a models listing**: `providers.ProbeCredential` (`internal/providers/probe.go`) is what `configure.ValidateProviderCredentials` runs, because several providers' `/models` endpoint is unauthenticated — OpenRouter answers 200 to *any* Authorization header, so ListModels-based validation printed "✓ validated" for a typo'd key and the user's first real message got the raw 401. The return contract is three-valued and the middle matters: 401/403 is `ErrCredentialRejected` (say "your key was rejected"), a 429 is **success** (a rate limit is issued to an authenticated key), and every other failure — 404 model, network, 5xx — is indeterminate: report "could not verify", never print the checkmark. `ProbeCredential` still refuses an empty `APIBase` for the same reason `ListModels` does — dialling a default endpoint validates some other provider's credential.
- **Telegram and Discord can both be enabled at once.** `bus.OutboundChannel()` (sugar for `RegisterOutboundConsumer`) hands each channel implementation its own private copy of every outbound message — `processOutbound` fans out from the single arrival queue (`outboundCh`, still the thing `Publish` writes to and still the thing a full queue means "backpressure") to every registered consumer channel, non-blocking per consumer so one falling behind doesn't stall the others. Before this, every channel called the same method and got back the literal same channel, so two channels running together raced an ordinary Go receive over each message with no error anywhere (`internal/channels/discord.go`, `consumeOutbound`). `TestOutboundChannelAccess_TwoConsumersEachSeeEveryMessage` in `internal/bus/bus_test.go` pins that both consumers see every message regardless of which is addressed to them.
- **While a shell allowlist is in force, chaining is refused**: `checkAllowList` rejects `;`, `&`, `|`, newline, backtick, `$(`, `<(`, `>(` — the command reaches `sh -c` unchanged, so first-word matching admitted `echo hi; id`. `find`, `go` and `git` are no longer in `defaultUnsandboxedAllowlist`; each runs a program of the caller's choosing.
- **Workspace containment resolves every path component and writes with `O_NOFOLLOW`**: `EvalSymlinks` reports a dangling symlink as ENOENT like a missing file, so re-appending components lexically let `ws/evil -> /outside/x` through; and resolution alone leaves a TOCTOU window on the final component.
- **Allowlist entries are matched by shape**: an all-digits `allow_from` entry may only match the numeric user ID, on Telegram as on Discord — display names are attacker-chosen, so the cross-field match was an authentication bypass.
- **The macOS Seatbelt profile allowlists `mach-lookup` by service name** (`macMachServices`) — a blanket grant reaches XPC services that act outside the profile. `GOCACHE` is resolved via `go env` because macOS leaves it unset, and the workspace is created before the profile is rendered because a missing path is silently dropped from it.
- **Restartable objects keep per-run channels off the struct**: the bus threads its run's context into its goroutines, Discord allocates a fresh latched `stopCh` per `Start`, and `mcp.Client` gives each connected process its own `doneCh`. Each of these was a real bug — a data race, a dead restarted channel plus a double-close panic, and a client permanently reporting "server stopped".
- **`internal/heartbeat` has exactly one checkbox regex**: publishing and checking off must agree or a task re-fires forever, a task is checked off only after the bus accepts it, and `HEARTBEAT.md` is rewritten atomically.
- **A configured MCP server is inert until its advertised manifest is approved** (`joshbot mcp trust <name>`), mirroring workspace-skill trust: `internal/mcp/trust.go` stores a SHA-256 of every advertised tool's name, description and input schema (sorted, length-prefixed) in `~/.joshbot/mcp.trust` at `0600`, so any change to what a server advertises revokes it. `registerManifest` in `internal/tools/mcp_tool.go` is the single gate and is split out of `registerOneMCPServer` so it can be tested without spawning a process. The gate is on the **manifest, not on execution** — an unapproved server is still connected and asked for `tools/list`, because that is the only way to learn what it advertises; the store governs what may reach the model. `IsTrusted` is a nil-receiver method returning false, so a caller that forgot to load a store fails closed. `sanitizeMCPDescription` defangs joshbot's prompt envelope tags in descriptions and caps them at 1024 chars; `promptEnvelopeTags` must be widened whenever a new system-prompt section is added, which `TestPromptEnvelopeTagsCoverAgentContext` enforces against the real prompt builders.
- **`web_fetch` strips script/style/comment *elements*, and every tag match is ASCII case-insensitive.** `WebTool.removeTag` (`internal/tools/web.go`) once found `<script` and the next `>` and deleted only that span, so the *body* — script source, CSS, comment text — reached the model on every fetch: token burn plus a prompt-injection surface on attacker-controlled pages. It now finds the matching `</script>` and deletes the whole element, and a dangling open tag with no close drops the remainder rather than trusting it. Two rules keep it correct. **Matching folds case**, because tag names are case-insensitive in HTML and the *page* picks the case: a `strings.Index` search leaves `<SCRIPT>…</SCRIPT>` intact, which is exactly the bypass the strip exists to prevent — `TestWebTool_RemoveTag`'s uppercase and mixed-case subtests go red the moment it is narrowed back. And the shared `indexFold` (`internal/tools/mcp_tool.go`) **walks bytes instead of lowercasing the haystack**: `unicode.ToLower` can change a string's byte length, so an offset taken from a `strings.ToLower` copy does not index the original — and `sanitizeMCPDescription` slices at exactly that offset to defang envelope tags, so a description carrying one length-changing rune ahead of a `</skills>` would have mis-sliced and defanged nothing.
- **MCP servers are started by `cmd/joshbot` now** (`registerMCPServers` / `closeMCPServers`), fail-soft — any doc saying "not yet wired" is stale.
- **`setupComponents` starts background services nobody holds a handle to, so they must be stopped explicitly**: cron, the heartbeat and the memory consolidator are started at the end of `setupComponents`, and `learning.Consolidator.Start` runs its first pass *immediately* from a goroutine, writing into `workspace/memory`. Each one now registers its `Stop` with `registerBackgroundService`, and every long-lived entry point defers `stopBackgroundServices` next to `closeMCPServers`. Two things keep it correct. The stoppers are **one-shot** — `heartbeat.Stop` and `Consolidator.Stop` close a channel and panic on a second call — so `stopBackgroundServices` takes the slice and clears it under the lock, which is what makes it safe to call twice. And a **test** calling `setupComponents` must register the stop *after* its temp home is created (`setupConfig` does this), because `t.Cleanup` runs LIFO: registered earlier, the goroutines are still writing while `t.TempDir` is being removed, and the run fails with `TempDir RemoveAll cleanup: ... directory not empty` in whichever subtest lost the race. That flake took main CI red on `ac13b2f`.
- **Outbound attachments are a typed field, contained twice, and sniffed — `send_file` is its own tool for a reason.** `send_file` (`internal/tools/send_file.go`) is deliberately not a flag on `message`: `MessageTool.Execute` rejects empty content and a caption-less file send is legitimate. Six rules. The transport is `OutboundMessage.Attachments []bus.Attachment` (`internal/bus/attachment.go`), a **typed slice, never a `Metadata` key** — a mistyped map key sends nothing and returns success, which is the failure mode nothing detects. The path goes through **both** containment layers, `FilesystemTool.resolvePath` *and* the `containmentRoot` + `openInRoot` walk; mutation testing showed each refuses an escape alone, so removing "the redundant one" is removing half a boundary. **Content decides the type**: the head is sniffed with `http.DetectContentType` + `providers.IsSupportedImageMIME`, never `filepath.Ext` — same rule as inbound images. **There is exactly one egress route and it must stay that way**: `Data` is always populated, read through the very handle `openInRoot` opened, and `Attachment.SourcePath` is a workspace-relative *label* nothing ever opens. The earlier two-route design published an absolute `Path` above a 10 MB inline threshold and let `telebot.FromDisk` re-open it — an uncontained `os.Open`, on the channel goroutine, after a bus hop, again on every retry, with `att.Size` stale by then: swapping the leaf for a symlink to `~/.joshbot/config.json` exfiltrated the provider keys. Re-introducing *any* downstream open, or an absolute `SourcePath`, restores it. That is also why `DefaultDocumentMaxBytes` is 10 MiB and not Telegram's 50 MiB — the payload is in memory, so the cap is a memory bound and #280 raising it raises memory with it. And the size constants are reached through `AttachmentLimits()`/`Limits()`, not hardcoded per use site. **The recipient is not an argument**: the tool has no `channel` parameter; `Agent.process` sets `tools.WithChannel(ctx, msg.Channel)` before the ReAct loop and `send_file` reads it back, refusing an empty one rather than defaulting — the old `""`/`"same"` → `"cli"` fallback failed on Telegram with `no chat ID stored for channel: cli` and on the CLI *succeeded while delivering nothing*, which taught the model to pass an explicit address. On Telegram (`internal/channels/telegram_attachment.go`) the retry **rebuilds the payload every attempt** — a `telebot.FromReader` payload retried as-is uploads zero bytes — the parse mode is cleared for the **caption only** on a `can't parse entities` error, and a caption over `TelegramMaxCaptionLen` (1024) is re-sent as its own message rather than truncated. A channel that cannot send attachments must **degrade honestly** (`describeUnsentAttachments` in `internal/channels/discord.go` appends name, size and the workspace-relative `SourcePath` — an absolute one would print the operator's home directory into chat) — a silent drop looks like a successful send to the model, which then says the file was delivered. **The gate that closes the last gap (issue #304): `tools.send_file_approval` runs *after* both containment layers, never before** — a path already refused by containment must not reach a human as a prompt, the same ordering rule the shell deny list follows ahead of its own approval gate. It reuses `tools.WithApprover`/`ApproverFromContext` verbatim rather than a second mechanism: `SendFileTool.SetApproval` mirrors `ShellTool.SetApproval`, `ApprovalRequest{Tool: "send_file", Command: "send <file> (<size>) to <channel>"}` renders through the identical CLI/Telegram prompt code (both already keyed off `req.Tool`/`req.Command` generically, not hardcoded to shell), and an unattended turn is denied immediately for the same reason. `tools.shell_approval` and `tools.send_file_approval` are independent config values — an operator may trust one tool and not the other — but the CLI and Telegram install exactly one approver per process, so `combinedApprovalMode` (`cmd/joshbot/approval.go`) picks whichever of the two is more restrictive (`always` beats `interactive` beats `off`) to construct it, and each tool still gates on its own configured mode when deciding whether to ask at all. `tools.send_file_disabled` (inverted-polarity bool, `omitempty`, same reason `dream_mode` and `api.webui` are strings/opt-in rather than a bare bool — a `Config` bool without `omitempty` is written into every saved config and its default can never be flipped without a migration) removes the tool from the registry entirely for an operator who wants no outbound-file capability at all.
- **Images are carried as bytes on the turn, screened before the network, and never persisted**: `providers.Message.Images` is `json:"-"` and the wire form is produced by `Message.MarshalJSON`, which keeps a text-only fast path so an ordinary message serializes exactly as it did before attachments existed; images become a `content` parts array with `image_url` data URLs. Because every provider (Anthropic included) is dialled through the OpenAI-compatible serialization point, that one method covers them all — do not add a per-provider image path. Four rules hold the design together. **Content decides the type, never the name**: `providers.NewImage` sniffs the bytes, so a `.png` that is prose and a Telegram document declaring `image/png` are both refused; a declared MIME may only decide whether a download is worth spending (`providers.IsSupportedImageMIME`), never what the bytes are. **The capability gate runs before the first network call**, in `screenForImages`, from both `Chat` and `ChatStream` — `SupportsVision` fails closed on unknown models, because guessing "yes" turns a typo into a provider 400 mid-conversation while guessing "no" produces an error naming the model. **Sessions store `session.ImageRef` (type, size, SHA-256) and deliberately not the bytes**: session JSONL is exempt from redaction and relies on its `0600` mode, and stored images would be reloaded and re-billed on every later turn inside the memory window; `TestImageRefSurvivesRoundTripWithoutTheBytes` pins that boundary. **And on Telegram the download happens strictly after `IsAllowed`** — it carries a file id to the Bot API on the sender's behalf and confirms the bot is live — with an over-limit photo refused from its declared `FileSize` before any transfer and the body read through a `LimitReader` at `MaxImageBytes+1` so over-limit is distinguishable from truncated. A failed attachment ends the turn with an error in the chat; forwarding it as a text-only `[Photo]` gets a confident answer about nothing. `--image` paths on the CLI are **not** workspace-contained on purpose: containment exists to bound the model, not the operator, so `loadImageFlags` enforces only what the operator cannot see for themselves (a regular file, real image content). Text documents follow the same claims-vs-bytes rule via `isTextLikeDocument`/`readTextDocument` (`internal/channels/telegram_documents.go`): the declared MIME or extension decides whether to download, the bytes must be NUL-free valid UTF-8 to be inlined (capped at `telegramTextDocMaxBytes` with a visible marker), and a binary document is refused honestly rather than forwarded as its filename. Voice transcription (#276): `stt.provider` names an existing provider whose key and endpoint are reused (`buildTranscriber` in `cmd/joshbot/main.go` validates at startup — unknown/disabled/keyless provider, no api_base, no default model are all fatal, naming the key); `providers.TranscribeAudio` refuses an empty APIBase rather than defaulting one (the ListModels/ProbeCredential rule — note the pre-existing `Provider.Transcribe` interface stub still carries the openrouter-default anti-pattern and is unimplemented; do not wire it). The channel refuses over-limit voice from *declared* duration/size before any download, never persists audio, and with no transcriber wired keeps the honest refusal. The transcriber field is set once before Start and read lock-free on the message path.
- **PDF documents ride the same rail as images, with a *separate* capability list (#278)**: `providers.Document` mirrors `Image`, is carried on `providers.Message.Documents` (`json:"-"`), and is serialized at the same single point — `Message.MarshalJSON`'s text-only fast path is now `len(m.Images) == 0 && len(m.Documents) == 0`, and a text-only message must still serialize byte-identically (`TestTextOnlyMessageSerializesByteIdentically` compares exact JSON bytes). The wire form is OpenAI's Chat Completions `file` content part: `{"type":"file","file":{"filename":…,"file_data":"data:application/pdf;base64,…"}}`. Four rules. **`SupportsDocuments` is not the vision list** — llava reads images and cannot parse PDFs — so it is its own substring list (`internal/providers/documents_capability.go`), fails closed on unknown models, and its `ErrDocumentsUnsupported` **names the models tried**, which is the whole point of the gate. **`screenForDocuments` is a separate function from `screenForImages` and is called from BOTH `Chat` and `ChatStream`** — missing the `ChatStream` call site is a live bug class here, since streaming is on by default. **Content decides the type**: `NewDocument` requires the `%PDF-` magic, so a PNG named `report.pdf` is refused and a PDF named `shot.png` is not smuggled through the image path; the declared MIME and `FileSize` decide only whether a download is worth spending. And the caps are `providers.MaxDocumentBytes` (8 MiB) and `MaxTotalDocumentBytes` (16 MiB), refused from the declared size *before* the transfer and then read through a `LimitReader` at cap+1 so a lying declaration is refused rather than truncated — a compile-time assertion in `internal/channels/telegram_documents.go` keeps the per-document cap under Telegram's 20 MB bot-download ceiling. Sessions persist `session.DocumentRef` (label, type, size, SHA-256) and never the bytes, for the same reason images are not stored; a PDF is more sensitive than a photo, not less. A PDF that fails to read **ends the turn** with an honest chat error rather than degrading to `[Document: x.pdf]`, following `attachTextDocument`'s `(value, bool)` contract. There is no `--document` CLI flag: this is a Telegram inbound path only.
- **GitHub Copilot authentication is two-step, and the OAuth token is not the API credential**: the device flow stores a GitHub OAuth token, which `api.githubcopilot.com` rejects. It must be exchanged at `GET https://api.github.com/copilot_internal/v2/token` (`authorization: token <githubToken>`) for a short-lived Copilot token used as `Authorization: Bearer`; `CopilotProvider.ensureAPIToken` caches it until a minute before `expires_at` and clears it on a `401`/`403` so a stale exchange is not replayed. Three traps live here. `CopilotAPIURL` **has no `/v1`** — chat is `<base>/chat/completions` and models is `<base>/models`; adding the segment 404s every request. **A zero `expires_in` means no expiry, not expired now** — GitHub's OAuth-App device flow returns none, and the old unconditional `now + expires_in` stamped every fresh token as already dead, which `LoadToken` then rejected on the next read. And `https://models.github.ai/catalog/models` is the **GitHub Models catalog, a different product** — it is not what Copilot will accept as model ids. Requests also need the integration headers (`Copilot-Integration-Id: vscode-chat`, `Editor-Version`, `Editor-Plugin-Version`, `Openai-Intent`, `X-Github-Api-Version`), all set in one place by `setCopilotHeaders`.
- **Flipping a bool config default needs a schema migration, because the field is serialized either way**: `Config` bools have no `omitempty`, so every config joshbot has ever saved contains `"streaming": false` — written by onboard, by `configure`, by any save at all — whether or not the operator ever saw the key. `loadFileConfig` does `cfg := Defaults()` then unmarshals over it, so a stored `false` beats the new default and a straight flip in `Defaults()` reaches nobody upgrading. `agents.defaults.streaming` going on by default (#119) is therefore a v4 → v5 migration in `migrateConfig` that resets an inherited `false` once and logs it; a `false` stored at v5 is a genuine opt-out and is left alone. Migration is in-memory only — `loadFileConfig` does not rewrite the file — so the reset re-runs on every load until something saves the config, which is correct but means the log line is not once-per-install.
- **A `time.Duration` in a config struct decodes as nanoseconds, so every timeout key is a `config.Duration`**: `encoding/json` marshals and unmarshals a `time.Duration` as its underlying `int64` of nanoseconds, and joshbot's config decoding is plain `encoding/json` — the `mapstructure:` tags are vestigial, there is no viper. So `"timeout": 600` set a six-hundred *nanosecond* timeout and every request to that provider failed instantly with `context deadline exceeded`, a symptom indistinguishable from a dead provider (#240). `config.Duration` (`internal/config/duration.go`) reads a duration string (`"600s"`, `"10m"`, `"1h30m"`) or a bare number of seconds and always marshals the string form back, so a config joshbot saves is one a human can edit. Four things to keep straight. A bare integer **at or above `legacyNanosecondCutoff`** (one second in nanoseconds) is still read as nanoseconds, because that is what an older joshbot *wrote* — `joshbot configure` set `p.Timeout` and saved, so configs in the wild carry `900000000000`; as a seconds value that is over thirty years, so the ranges cannot collide in practice. **`Config.Validate` rejects a nonzero timeout under a second**, naming the key, because the parser cannot catch a genuine unit mistake like `"500ms"` and an unvalidated one fails at the first request and blames the context. **Zero means unset everywhere** — `agents.defaults.timeout` carries `omitempty` and `agent.WithTimeout` ignores a non-positive value, which is what lets `cmd/joshbot` pass the config value through with no special case and no schema migration (the trap the `streaming` bool hit at v4→v5). And **a new timeout key must use this type, not `time.Duration`** — a plain field is the bug, restored.
- **`providers.<name>.timeout` reaches every provider, and a bad timeout is a *fatal* config error**: the key was consumed only by ollama while the docs described it as universal, so `registerProviders` (`cmd/joshbot/main.go`) now passes `p.Timeout.Duration()` into every `providers.Config` — a zero is defaulted by each factory (300s for ollama, 120s elsewhere), which is what makes passing it unconditionally safe. `agents.defaults.timeout` also reads from `JOSHBOT_AGENTS__DEFAULTS__TIMEOUT` via `parseDurationEnv`, under exactly the file's rules, so a bare `600` means seconds in both places; an unparseable value is reported, never dropped, because an ignored override leaves the operator on the default they were raising. And `validateTimeout` returns a `fatalConfigError`, not a plain error: `config.Load` answers an ordinary validation failure by logging "Config unusable, using defaults" and substituting `Defaults()`, so a mistyped `"500ms"` would silently take every provider, API key and allowlist with it. Note the duration grammar is `time.ParseDuration`'s exactly — `internal/cron.ParseDuration` additionally accepts a `d` suffix, and `"1d"` in a config timeout is an error, not a day; `internal/config` cannot import `internal/cron` to share it, because cron imports `internal/bus`.
- **A registry-backed provider registers through the generic arm, not a new bespoke `if` arm.** `registerProviders` (`cmd/joshbot/main.go`) has a bespoke arm only for the providers whose registration carries logic a generic form cannot express: openrouter (the default), nvidia/groq (fallback priority), poolside (a default model), ollama (a default base + 300s timeout) and github-copilot (token auth). Every other registry-backed provider -- openai, anthropic, azure, custom, litellm, and any that joins `providers.IsProviderRegistered` later -- routes through one `for name, p := range cfg.Providers` loop, gated on `providers.IsProviderRegistered(name)` and skipped for those six names. **Do not add a new bespoke `if p, ok := cfg.Providers["x"]` arm for a plain LiteLLM-based provider**: it duplicates the generic arm (the register map dedupes by name, but then two code paths have to stay in step), and a hand-copied config field list is exactly how a field silently falls out of sync -- the bespoke `custom` arm's `model := p.Model; if model == "" { model = p.Model }` was a no-op that #235 removed by folding `custom`, `openai` and `anthropic` into the one generic arm. Gate on the registry so a configured-but-unknown name still fails loudly (`noProvidersRegisteredError`, #71) rather than silently. `TestRegisterProvidersRegistersOpenAICentricProviders` pins that `openai`/`anthropic`/`azure`/`litellm`/`custom` all register through that one loop; before it, a legacy config for any of them registered nothing while a valid `configure` kept writing it. **And every name in that loop is canonicalized first** (`providers.CanonicalProviderName`): the registry aliases and lowercases (`local` -> ollama, `nim` -> nvidia, `Ollama` -> ollama), so a skip list, a fallback-order lookup or a `Register` call keyed on the raw config name disagrees with the registry it is gating on -- a config key of `local` slipped past the exact-match skip and registered a *second* ollama entry in the chain, built without the bespoke arm's default base and 300s timeout, under a name nothing else looks up. Neither duplicate errors. `TestRegisterProvidersSkipListMatchesAliasAndCaseVariants` pins it.
- **`config.Load` returns `Defaults()` with a *nil* error when the file is unreadable or unparseable**: it is deliberately lenient so joshbot still runs. Any caller that intends to `config.Save` back must use **`config.LoadStrict`** (or `LoadStrictFrom`), or a damaged config file is silently replaced by defaults — every provider, key and setting gone. Checking the error from `Load` does not help: there is no error. `joshbot auth github-copilot` shipped exactly that bug (#39), and a "fixed" version that still called `Load` was equally destructive. Distinguish "no config file yet" (safe to write) from "file present and unusable" (never write) with `os.Stat(config.ConfigPath())`.
- **A provider with no streaming endpoint returns `providers.ErrStreamingUnsupported`, never a bare error**: streaming is on by default and `internal/agent` picks `streamChat` whenever a sink is attached, so a plain error there kills every interactive turn on that provider. The ReAct loop falls back to `Chat` when `errors.Is(err, providers.ErrStreamingUnsupported)` matches — safe only because the stream never opened, so nothing has reached the sink. `github-copilot` is the only such provider today (`internal/copilot/provider.go`).
- **A stream that dies before any content retries invisibly; one that dies mid-text keeps the marker**: `streamChat` returns the `errStreamDiedEmpty` sentinel (wrapped, so `errors.Is` matches) when the accumulator rejects a stream and `accumulatedContent` is still empty — nothing has reached the sink, so `reactLoop` retries once through `a.provider.Chat`, which brings the whole retry/fallback chain with it, and the reply arrives unstreamed (the `ErrStreamingUnsupported` delivery path, which every sink consumer already handles). The empty-content check is the whole safety argument: retrying after a delta has been emitted would duplicate text on screen, so the mid-text paths still append the visible `[stream error: ...]` marker and return the partial as a successful response. The old behaviour — marker even when nothing had streamed — existed to avoid the "I've processed your request." non-answer; the retry supersedes it, and the doubly-failed case now surfaces the real error via the in-band `ReplyPrefix` contract instead.
- **Telegram streaming state is per-turn and lives on `TelegramStreamer`** (`internal/channels/telegram_stream.go`), created in `runGateway` per message and reached only through `agent.WithStreamSink` — a field on `TelegramChannel` would cross-deliver one chat's text into another, exactly as a struct-field sink did for tool progress. Three rules hold it together. **Interim edits are plain text; the parse mode — Markdown by default since the Telegram-UX pass — is applied only to the final edit** — a half-written code fence would otherwise fail every interim edit with `400 can't parse entities`. **The buffer advances only after the head write lands** on a 4096-byte rollover, and the remainder comes from `splitOnce` (`internal/channels/telegram.go`), which returns head and tail together. Neither re-join `splitMessage`'s later parts — their per-part fences would compound into `` ``````  `` on every lap — nor re-derive the tail by trimming a closing fence off the head: that cannot tell a fence `splitOnce` added from one the model wrote, so text that genuinely closed a block right at the split point had a spurious fence prepended and every later part rendered inverted. **And the bus publish is suppressed only when `Finish` reports the *whole* answer reached the chat** (`delivered && !broken && shown == buf`), mirroring the CLI's `didStream()` rule. Both halves of that are load-bearing. Returning true because *something* landed loses the entire reply to one failed final edit — a deleted in-progress message, a transient 400 — with the bus fallback that exists for exactly that case suppressed by the same bug; a partial stream plus the bus copy is duplication, and duplication beats loss. Conversely `broken` is set only when nothing has ever been delivered, never on `s.msg == nil`, which a rollover clears while whole messages are already on screen. `Finish` also takes `agentReplyError(response)` on the success path, because `Process` reports LLM failures in band as reply text with a nil error. `retry_after` on a 429 must also be parsed out of the error *text*: `telebot.FloodError` embeds an unexported error and telebot fills `RetryAfter` only for descriptions in its static table. **Tool progress rides the same message slot**: `TelegramStreamer.Status` shows a best-effort progress line that the first content delta then edits away in place — it is skipped (never queued) inside the throttle window, refuses to write once `buf` is non-empty, must never set `delivered` (that means reply text landed, and `Finish`'s suppression contract depends on it), and `Finish` deletes a status message no reply ever replaced so the bus-fallback answer does not land under a stale "⚙️ ..." line.
- **Anything derived from the user's words and injected into the prompt must be labelled as derived, and never cut mid-word with an ellipsis.** `inferTopic` once produced `Current topic: ha! you son of a gun!  i'm actually wanting to do a new topi...` and the model answered that "cut-off message" instead of the real one. `session.ConversationSummary` now labels the line `Topic hint (auto-derived ..., not a message)`, `inferTopic` cuts on a word boundary (`topicMaxLen`) with no `...`, and the prompt states a tool result is the agent's own output. The live-eval probe `tool_result_is_not_user_input` covers the tool-result half.
- **The Stop button cancels the turn *directly* and is keyed by a per-turn token, not the session (#310).** `channels.StopCoordinator` (`internal/channels/telegram_stop.go`) owns the `stop` namespace; `gatewayHandler` wraps a streamed turn's context in `WithCancel` and `armStop` registers the cancel func, so a press on the poller goroutine calls it at once. Three rules. **It must never go through the bus or `LockSession`** — the turn being cancelled holds both, and a Stop queued behind it is a no-op until the turn ends on its own (and under `MaxConcurrentTurnsPerKey` it would be refused outright). **A token is honoured only while its turn runs and only from its chat** (`Release` on settle, `chatID` match on press); the token is a base-36 counter, so `callback_data` carries no sender or chat id. **A stopped turn is reported as `errTurnStopped` ("stopped by you") through `Finish`, or `stoppedReply` when nothing streamed** — never the raw `context canceled`, and `streamChat` skips its `[stream error: ...]` marker when `ctx.Err()` is `Canceled` so the chat does not show two failures for one press. The button is `TelegramStreamer.interimMarkup`: on every interim send/edit (status line included) and omitted from the final edit, which is what removes it; drafts cannot carry it.
- **The `/model` and `/personality` pickers reuse the command turn; a press is the presser's own session, and a switch never resets (#313).** `channels.Picker` (`internal/channels/telegram_picker.go`) owns the `model` and `persona` callback namespaces; the gateway attaches its `Keyboard` to a *bare* `/model`/`/personality` reply on Telegram only, and only when `agentReplyError` is nil (a picker under an error invites a press into the same failure). A press synthesizes an inbound `/model <spec>` with `SenderID: telegram_<presser>` and calls `agent.Process` — so it queues on the per-key session lock like a typed command, the payload is exactly an `agent.Choice.Spec` that `resolveModelSpec` accepts, and nothing a button can send bypasses the command's validation — then edits the picker message in place through `pickerTarget` (which carries the chat id: `Edit` reads both halves of `MessageSig`, unlike `React`). A spec whose envelope exceeds 64 bytes is left off the keyboard, never truncated, because a truncated envelope decodes as a *different valid* choice. The agent and channels packages do not import each other; `pickerBackend` in `cmd/joshbot` converts `agent.Choice` to `channels.PickerChoice`. And the keep-history decision is deliberate and stated in the switch reply: a one-tap button must not wipe the transcript.
- **A Telegram inline button is a routed action, not a synthetic user message** (`internal/channels/callback.go`): `handleCallback` decodes `callback_data` as a `namespace:action:payload` envelope and hands the registered `CallbackHandler` a typed `CallbackPress`; only data that fails to decode falls back to the legacy `[Callback: %s]` bus inbound. That fallback is the compatibility path, not the design -- re-typing a payload the code produced as user text spends a whole ReAct turn to re-derive it, and the model may decline. Four rules. The envelope is split with `SplitN(data, ":", 3)`, so **only the first two fields are structural** and a payload may contain `:` (a model id is `openrouter/z-ai/glm-5.2`). `Encode` **errors at build time** on the 64-byte `callback_data` cap rather than truncating, and returns `""` on failure: a truncated envelope decodes as a *different valid action*, so a caller ignoring the error must not be able to send anything. `DecodeCallback` trims a leading `\f` -- telebot prepends it to the data of a unique-endpoint button. And `RegisterCallback` refuses a duplicate namespace, because a silently-replaced handler routes another feature's buttons. `ctx.Bot().Respond(cb)` is called **before** the dispatch decision, so a slow handler does not leave the client's spinner turning. Related trap: `buildReplyMarkup` asserted `markup["inline_keyboard"].([][]map[string]any)`, a concrete Go type JSON-decoded metadata can never satisfy (`encoding/json` yields `[]any` of `[]any` of `map[string]any`) and which no in-process producer used either -- both keyboard branches were dead code returning an empty markup with no error. `normalizeKeyboardRows` accepts both shapes; in-process callers should pass a `*channels.Keyboard` instead.
- **A proactive reply resolves its recipient from the persisted chat-id map, and an id-less inbound must never clobber it**: cron and heartbeat inbounds carry no chat id, so `resolveChannelID` (`cmd/joshbot/main.go`) falls back to `BusMessageSender.GetChatID`, whose map survives restarts via `EnablePersistence` (`~/.joshbot/chat_ids.json`, 0600, atomic temp+rename). Two rules: `gatewayHandler` stores an inbound's chat id only when it is non-empty — a cron inbound used to overwrite the stored id with "" and erase exactly the recall its own reply depended on — and a live in-memory id beats a stale persisted one at load. A damaged file degrades to an empty map rather than failing gateway startup: the cost is no recall until the user speaks, which is the pre-persistence behaviour.
- **A non-`Always` skill's full content is reachable only through `skill_registry`'s `get` action, never `read_file`.** `Loader.LoadSummary` (`internal/skills/skills.go`) never carries a filesystem path for a skill in its XML summary, so telling the model to "use read_file to load full skill content" gave it an instruction with no way to satisfy it — and a **bundled** skill (5 of the 6 shipped skills, all `always: false`) has no real path at all: it ships embedded via `//go:embed` (`internal/skills/bundled.go`) and its `Path` is a virtual `bundled/<name>` string `read_file` cannot resolve. `Loader.LoadFullSkillContent` always worked correctly (it reads `Skill.content`, pre-populated at discovery for bundled skills, cached from disk for workspace ones) — it just was not wired to anything the model could call. `SkillRegistryTool.getSkill` (`internal/tools/skill_tool.go`) is that wiring, and it enforces the same trust boundary `LoadSummary` does: an unapproved workspace skill refuses to load by name, so `get` cannot be used to bypass `joshbot skills trust`.
- **`afterReActDetection`'s skill-extraction LLM call runs in its own goroutine with its own bounded context, never inline on the turn's context or on `context.Background()` unbounded.** It used to do both — call `a.extractor.Extract(context.Background(), ...)` synchronously, before `Process` returned the reply. That meant an ordinary tool-using turn (>=3 tool calls plus a word like "steps" in the answer is enough to cross `SkillDetector`'s confidence threshold) could hang the user-visible reply behind a *second* full LLM call that entirely ignored `agents.defaults.timeout` — up to the provider's own client timeout (300s for ollama). `extractAndCreateSkill` now runs via `go a.extractAndCreateSkill(...)` under `skillExtractionTimeout` (60s). - **Dream is off by default and its mode is a string, not a bool**: `agents.defaults.dream_mode` is `""`/`"off"`/`"record"`/`"full"` with `json:"dream_mode,omitempty"`, precisely so it needs no schema migration — a `Config` bool has no `omitempty`, is written into every saved config, and therefore cannot have its default flipped without one (see the `streaming` v4→v5 note above). Three more things to know. `Manager.AppendHistory` is the **only** Stage-1 hook; a turn that never appends history records nothing, so a test that skips it consolidates an empty log and passes vacuously. `SearchSimilar` reads `dream_consolidated.jsonl` off disk, **not** the in-memory vector store — the store is rebuilt per `Consolidate` and holds raw records, so a restarted process would otherwise find nothing; and it truncates to `k`, so `SearchSimilar(ctx, "", 0)` returns nothing, which is why `ListConsolidated` exists for "show me everything". - **A subagent output schema errors rather than returning prose, and a background run must convert its own cancellation**: `subagent.Config.OutputSchema` is a deliberate small subset of JSON Schema (required keys, optional per-key types). Three things hold it together. The required keys ride the **user turn**, not the system prompt, next to the task they apply to. A mismatch gets **exactly one** repair round-trip and then errors — returning the prose as success repeats the `agent -m` anti-pattern of reporting success over work the caller cannot use. And the repair gets its **own** turn via an internal `repairBudget` rather than spending one of the caller's `MaxIter`, because a `MaxIter` of 1 would otherwise make every schema'd run fail by construction. Separately, `Runner.RunBackground` settles the `*Handle` (store result, `close(done)`) **before** calling `notify`, so a callback that inspects the handle does not race it, recovers a panic into the error instead of taking the process down, and re-checks `runCtx.Err()` — because `Runner.Run` reports a cancelled context as a `TimedOut` result with a **nil error**, which is right for a chat turn that should still show partial output and wrong for a handle nobody is reading partials from.
- **Every spawning tool shares one gate, and `concurrency` is not a limit**: `parallel_subagent`, `chain_execution` and `delegate_subagent` all go through `spawnGate` and `childContext` (`internal/tools/subagent_limits.go`) — the guard was duplicated in `delegate_tool.go` only, and the other two had neither a width cap nor a depth increment, so one top-level call fanned out to an unbounded number of full ReAct loops with shell access, all at the caller's own depth and therefore outside the nesting budget `Runner.Run` enforces. Three things to keep straight. **`concurrency` bounds simultaneity, never total volume** — capping it does nothing about cost; only `MaxParallelTasks` (8) and `MaxChainSteps` (16) do, and both are checked before any subagent starts, because a limit that reports an error after the work has run has not limited anything. **The runtime gate must test `depth >= 1` *and* `role == RoleLeaf`, never role alone**: `RoleLeaf` is the zero value, so the top-level agent — which is not a subagent at all — also reads as leaf, and a gate on role alone refuses `parallel_subagent` for every ordinary turn. **And a subagent spawned with `Config{}` is a leaf**, so `depth >= 1` with no role set is correctly refused; a test that wants an allowed nested call must set `RoleOrchestrator` explicitly.
- **The HTTP API serves the agent, not a provider, and has no unauthenticated mode**: `internal/api` runs every `POST /v1/chat/completions` through `agent.Process`, so `GET /v1/models` advertises exactly one id (`api.ModelID` = `joshbot`) and the request's `model` field is accepted and ignored — a client hardcoded to `gpt-4` must keep working. Four rules hold it together. **`api.New` fails closed**: it drops blank entries from `api.api_keys` and returns `ErrNoAPIKey` when nothing usable is left, before anything is listening, because a caller reaching this endpoint reaches the shell and filesystem tools; keys are compared with `subtle.ConstantTimeCompare` and every configured key is checked even after a match. **A client `system` message is dropped, never forwarded** — joshbot's own system prompt carries the tool and safety rules and a caller prepending to it is a way to argue the agent out of them; only the last `user` turn is used. **The `user` field becomes a session key (`api:<user>`), so it goes through `session.ValidateSessionID`, a separate `:` check, a 64-character cap and a letters/digits/`.`/`_`/`-` charset** before it can build a path — `ValidateSessionID` stops traversal but says nothing about length or shape, and this value ends up as a filename and as a name an operator reads in `joshbot sessions`. Two requests carrying the same `user` are **serialised, not parallel** (#236) — see the session-lock gotcha below. One limit is documented rather than fixed: a client that disconnects mid-turn cancels the context and drops that turn from the session. And **`agent.Process` reports LLM failures in band**, so the handler translates them with `agent.ReplyError`: pre-stream that is a 502, mid-stream it is an error in the stream with no `finish_reason: "stop"`, never a 200 carrying `"Error processing request: ..."` as the answer. Streaming replays only the remainder of the reply when the deltas are a prefix of it, and usage rides the final SSE frame only. **Error bodies split on origin (#238)**: `writeError` sends joshbot's own package constants verbatim and `writeUpstreamError` redacts anything whose text came from outside. Running everything through `safeErrorMessage` made the 401 read `Send it as 'Authorization: Bearer [REDACTED]'.` — `redact.String`'s `Authorization:` header rule ate the `<key>` placeholder that tells a caller what to present. The redaction is not optional on the other side: a provider error carries the operator's upstream key, and an API caller is authenticated but is not the operator. The mid-stream error frame is built by hand rather than by `writeError`, so it needs `safeErrorMessage` applied explicitly — it was missing there, which is a leak a non-streaming caller was protected from.
- A bundled skill that names a tool joshbot does not have fails only at runtime, as a confident-sounding error. `TestBundledSkillsOnlyReferenceRegisteredTools` in `internal/tools` catches this — it keys off the phrase ``the `x` tool``, so keep that phrasing when documenting a tool in a skill.
- **`POST /v1/audio/transcriptions` is the one API route that is not the agent, and three rules keep it safe.** It transcribes with the `stt` provider directly -- no ReAct loop, no session -- and answers **501 naming `stt.provider`** when none is configured, because a 404 reads as "joshbot cannot do this" and a 200 with an empty transcript is indistinguishable from silence. The body goes through `r.MultipartReader`, never `ParseMultipartForm`: the latter spills past its memory budget to temp files, so an authenticated caller gets a disk-fill primitive and the audio touches disk unredacted. The size cap is enforced twice -- `http.MaxBytesReader` on the whole request and a `LimitReader` at `providers.MaxAudioBytes+1` on the part, the +1 being what makes over-limit distinguishable from truncated. And **content decides the type**: `providers.SniffAudio` reads the bytes, because the multipart filename and its declared Content-Type are both caller-written, so a 25 MiB text file named `voice.mp3` would otherwise be uploaded to the operator's provider and billed. Provider errors go through `writeUpstreamError` (redacted), joshbot's own through `writeError` (verbatim).
- **`POST /v1/embeddings` orders vectors by the response's `index`, never by array position, and its caps run before the provider is dialled.** The OpenAI schema carries an `index` on every embedding object precisely because the array may come back reordered, and a vector attached to the wrong input is the one failure mode nothing detects: the caller stores it, retrieves the wrong text, and no error is ever raised -- so `providers.Embed` (`internal/providers/embed.go`) places by index and treats a duplicate, out-of-range, missing or empty vector as an error rather than a best effort. Three more things. The route is **not exempt from `MaxRequestBytes`**, and `maxEmbeddingInputs` (128) and `maxEmbeddingInputBytes` (64 KiB) are checked in `parseEmbeddingInput` *before* `s.embedder` is called, because a limit reported after the upstream call has already been billed has not limited anything. **`buildEmbedder` deliberately does not require an API key** -- the one place it diverges from `buildTranscriber` -- because ollama is keyless and is the main local case; everything else (provider configured, enabled, resolvable `api_base`, resolvable model) is still fatal at `serve` startup naming the key, never a per-request 501 the operator reads as a missing feature. And `embeddings.timeout` is a `config.Duration`, not a `time.Duration`: a new timeout key written as the latter is the #240 nanosecond bug, restored.
- **The web UI is a second authentication path bolted beside the bearer one, and the bearer path must stay first and ungated.** `requireAuth` (`internal/api/server.go`) checks `Authorization: Bearer` first and returns immediately on a match -- no origin check, no CSRF header, no cookie -- because every existing OpenAI client depends on that being the whole story; the cookie rules live entirely in `cookieAuthOK` and run only when no valid bearer was presented. Five things hold it together. **`api.webui` is the single gate and it must be a real one**: `New` allocates `webuiSessions` *unconditionally*, so a cookie is refused because `s.webui` is false and not because a map happened to be nil -- gating by accident is not a guard, and the mutation test for it stays green when the map is the gate. With it false, `registerWebUI` is never called and every route (`/`, `/webui/static/`, `/webui/login`, `/webui/logout`, `/webui/config`, `/webui/session`) 404s as if absent, which is deliberate: the page is a login form accepting an `api_keys` value that reaches the shell tool, and it must not appear on every existing bind at upgrade. **`api.webui` carries `json:"webui,omitempty"` and defaults false**, which is the only reason it needs no schema migration -- a `Config` bool without `omitempty` is written into every saved config and its default can then never be flipped (the `streaming` v4->v5 trap). **The login route reuses `keyMatches` and `s.rejections.note()`**, not a second comparison and a second limiter: a bespoke check is how one path ends up non-constant-time or unthrottled while the other is audited. **CSRF is checked only on the cookie path and only on non-GET/HEAD**, constant-time against a per-session token that `GET /webui/config` serves *only* to cookie sessions -- serving it to anyone makes double-submit meaningless. And **`/` is not a catch-all**: Go's `ServeMux` matches `/` as a prefix, so the handler 404s any path that is not exactly `/`, or every unknown URL would return the app shell with a 200 and the missing-route signal would be gone. The transcript route is read-only by design (`transcriptReader` in `cmd/joshbot/serve.go` filters to user and assistant turns, dropping tool, system, compaction and empty-content messages); "New conversation" rotates the browser's session key and deletes nothing, because a destructive button should not be reachable through a cookie.

## Website (site/)

Two pages in `site/`:
- `index.html` — Landing page (what/how/why)
- `architecture.html` — Official architecture docs + diagrams

**Both MUST stay in sync with the codebase.** Update when major features, architecture, config, or capabilities change.

## HARD RULE: documentation ships with the change

**Every change that alters observable behaviour updates the docs in the same PR.** Not
a follow-up, not an issue — the same PR. A change is not done until the docs match.

This applies to `*.md` and `*.html` alike:

| If you change | Update |
|---|---|
| A CLI command, flag or its output | `README.md`, `docs/INSTALL.md` |
| A config key, default or its semantics | `README.md`, `docs/INSTALL.md`, `site/architecture.html` |
| A security boundary or its limits | `SECURITY.md`, `AGENTS.md` gotchas |
| Architecture, packages, data flow | `site/architecture.html`, `CLAUDE.md` layout |
| A capability users would notice | `README.md`, `site/index.html`, `CHANGELOG.md` |
| A behaviour that would trip up an agent | `AGENTS.md` gotchas, `CLAUDE.md` gotchas |
| Anything in `internal/tools/` the agent calls | the relevant `internal/skills/bundled/*/SKILL.md` |

Rules that make this stick:

- **Verify, do not assume.** Every documented command, flag, config key and code path
  gets read in the source — or run — before you write it down. Config keys must match
  the `json:`/`mapstructure:` struct tags exactly.
- **No unverifiable numbers.** LOC, test counts, tool counts and binary sizes must be
  measured at the time of writing or removed. A stale number is worse than none: it
  reads as authoritative.
- **Stale claims count as bugs.** Deleting a claim that is no longer true is as
  important as adding one that is. Drift runs both ways.
- **`site/*.html` is not optional.** It is the public face and it drifts fastest,
  because nothing fails when it is wrong.

Prose alone has already failed once: this file said the site MUST stay in sync while
the site sat eight releases out of date. Treat the checklist below as the gate.

## Pre-release checklist

```bash
go build ./cmd/joshbot
go vet ./...        # CI gates on this
gofmt -d .          # MUST be empty
go test -race ./... # MUST pass
# CI also fails if total coverage drops below 85%, or if cmd/joshbot or
# internal/service fall below their per-package floors (.github/workflows/ci.yml)

# Security scanning (.github/workflows/security.yml). gosec/CodeQL/gitleaks
# block (a red job is a real regression); govulncheck is advisory because
# some of its findings are stdlib CVEs with no Go release that fixes them
# yet — check the Security tab before a release regardless, since none of
# these are wired into main's required status checks (no branch protection
# rule requires them today, so a red job does not by itself block a merge).
go install golang.org/x/vuln/cmd/govulncheck@latest && govulncheck ./...

# LIVE prompt-behaviour eval — opt-in, never in CI (cost + flakiness).
# Run once pre-release against the configured provider; it exercises fact
# recall, tool selection, cron duration formatting, denied-command refusal and
# the workspace boundary against a real model (issue #156).
go test -tags liveeval -run TestLiveEval ./cmd/joshbot/ -v
# Reliability knobs: JOSHBOT_EVAL_K (runs per task, pass^k, default 3) and
# JOSHBOT_EVAL_MIN_PASS (default 0.8). Each run logs one `LIVEEVAL_RESULT {...}`
# JSON line — save it per release and diff, because the pass/fail gate cannot
# see slow drift.
```

Then, before tagging — no code change ships without this:

- [ ] `README.md` — commands, flags, config keys and examples match the code
- [ ] `docs/INSTALL.md` — install path, first-run flow and command list are current
- [ ] `site/index.html` / `site/architecture.html` — capabilities, architecture, counts
- [ ] `SECURITY.md` — the security model matches what is actually enforced
- [ ] `CLAUDE.md` / `AGENTS.md` — gotchas cover anything that would surprise an agent
- [ ] `internal/skills/bundled/*/SKILL.md` — bundled skills do not instruct the agent to do something
      the tools no longer permit
- [ ] `./scripts/test-install.sh` passes — not in CI (it downloads real artifacts), so it only runs if you run it
- [ ] `CHANGELOG.md` — an entry exists under `[Unreleased]`
- [ ] the Security tab has no new unreviewed finding since the last release
- [ ] `go test -tags liveeval -run TestLiveEval ./cmd/joshbot/` ran green against a
      real provider (opt-in live prompt-behaviour eval; not run by CI)
- [ ] Any count or size quoted anywhere was re-measured, not carried over

## PR & release

See `.github/PR_RULES.md`. Branch from main (never commit directly), conventional commits,
squash & merge. Releases: **cut the CHANGELOG section first** (move `[Unreleased]` entries under a
`## [X.Y.Z]` heading and merge that to main) → wait for CI green → then `git tag vX.Y.Z && git push origin vX.Y.Z`.
The release workflow refuses a tag with no matching section (`cmd/relguard -require-section`, #293) — tagging
first no longer ships and then breaks changelog-guard for every later PR.
